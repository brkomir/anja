A compiled CLI and TUI (Rust; 23 crates under `crates/`, one `edda` binary published on crates.io) that keeps "local, append-only state in `.edda/`" (README.md:59) for coding agents: a hash-chained SQLite ledger of decisions, sessions and tasks; a peers board with claims, heartbeats, requests and acks; bridges that install hooks into Claude Code, Codex, Cursor, OpenClaw and Hermes; a review gate and a verdict gate bound to commit shas; and a session-end post-mortem that learns rules and fades them. The repository's own description: *"Local, tamper-evident ledger for coding agents — decisions that survive sessions, coordination that survives agents."*

## When to consult me

- **Reviewer independence as CODE, not convention.** edda refuses a reviewer whose session authored the commits and grades the reviewer's model. If your commits carry a session identifier, ask whether anything compares it with the reviewer's before adding a self-review check.
- **Verdict precedence.** edda's PR gate unions standing verdicts (any non-LGTM blocks; an unqualified LGTM is only Provisional) and fails closed on an unstated severity count, while its conductor's plan-phase gate takes the newest fresh verdict. A newest-wins ledger is right for one reviewer's sequence and wrong for two reviewers disagreeing on one sha — edda keeps both rules, one per use.
- **Head and base pinning at merge.** Approval pinned to the head sha (the forge's `--match-head-commit`) and a review voided when the base moves over a changed file.
- **Peer claims, heartbeats and leases** with TTLs, on a local board, advisory by default and enforceable by a switch.
- **A rule lifecycle that decays** (active, dormant, settled, dead at 30/60/90 days; a cap of 15; two confirmations to activate) and a consequence of how its "hit" is defined: a rule that prevents its failure never "hits" again and so dies.
- **A hash-chained ledger** and what "tamper-evident" does and does not mean (plain SHA-256, no key: anyone who can write the file can rebuild the chain).

Not for: per-session working plans, a review hub run as its own session, promotion of a warning to a block on measured fires, incident records — edda has none of these. Decisions by a human authority only in part: `edda ratify` separates a recorded decision from a binding one with an append-only ratification whose `ratified_by` prefix names who asserted it — a person, `evidence:pr#N@sha` or `rule:cited-authority` (`crates/edda-cli/src/cmd_ratify/mod.rs:1-19`; README.md:160) — but `--by` is self-asserted, not verified (`:40-42`), and the rule never ratifies `product.`, `commercial.` or `spend.` keys (`cmd_ratify/rule.rs:20-22`).

## Architecture (CODE unless marked)

- **Ledger.** SQLite at `.edda/ledger.db`; each event carries a SHA-256 of its canonical JSON plus `parent_hash` (`crates/edda-core/src/event.rs:32-52` finalize, which hashes the event minus `hash`, `digests` and `schema_version`; `crates/edda-core/src/hash.rs:4-8`); `edda verify` recomputes the chain and names the first broken event (`crates/edda-ledger/src/ledger.rs:209-285` verify_chain_report; `:205-207` is the older error-string `verify_chain`). Plain hash, no key or signature.
- **Bridges.** `edda hook claude` writes one command into `.claude/settings.local.json` on 12 events — PreToolUse, PostToolUse, PostToolUseFailure, SessionStart, UserPromptSubmit, PreCompact, SessionEnd, Stop, SubagentStart, SubagentStop, TaskCompleted, TeammateIdle (`crates/edda-bridge-claude/src/admin.rs:11-24`, written with matcher `""` at `:84-108`); the same install registers an MCP server `edda mcp serve` (15 tools, no ratify and no verdict tool) and, unless `--no-claude-md`, writes edda sections into CLAUDE.md (`admin.rs:110-141`). SessionStart injects a context pack summarising earlier sessions; PreCompact rebuilds it; Stop nudges Ready rail tasks assigned to the session's label through `{"decision":"block","reason":…}`, at most once per task per session (a watermark written before the emit) and never when `stop_hook_active` (`crates/edda-bridge-claude/src/task_nudge.rs:86-141`, routed at `dispatch/mod.rs:193-208`); SubagentStop writes a subagent summary to the peers board and a ledger note (`dispatch/mod.rs:244-285`). The SessionStart pack also carries the most recently modified `~/.claude/plans/*.md` with step progress (`dispatch/helpers.rs:89-114`), a doctrine pack, active decisions and held task briefs (`dispatch/session.rs:752-990`). Sibling bridges for Codex, Cursor, OpenClaw and Hermes; an MCP server (`edda-mcp`).
- **Tool policy.** PreToolUse returns `permissionDecision: "block"` for a `git commit` (not `--amend`) on a branch other than the one in the session's heartbeat (guard ON by default, `EDDA_BRANCH_GUARD`, `crates/edda-bridge-claude/src/dispatch/tools.rs:24-59`) and for Edit/Write on a live peer's claimed path only when `EDDA_ENFORCE_OFFLIMITS=1` or `bridge.enforce_offlimits` is set (off by default, `:61-94`; `**/*` claims skipped, `:246`). "block" is not one of Claude Code's documented PreToolUse values (allow/deny/ask), the bridge emits "deny" nowhere, and its own test asserts "block" (`dispatch/tests.rs:2957`), so whether either guard stops a call is UNVERIFIED (nothing was run). Auto-approve is on by default: `EDDA_CLAUDE_AUTO_APPROVE` defaults to 1 (`:96`) and every tool call, Bash included, then returns `permissionDecision: allow` (`:149-153`; test `dispatch/tests.rs:100-111`), so Claude Code shows no permission prompt for it; the guide describes this as "Auto-approves `edda` commands" (`docs/guides/claude-code.md:22`).
- **Peers.** Claims = a label plus path globs appended to `~/.edda/projects/<pid>/state/coordination.jsonl` (local, NOT hash-chained); claim TTL 86,400 s; a session is stale after 120 s without a heartbeat; requests and acks between sessions expire after 7 days (`peers/mod.rs:13-48`); `edda claim check` exits 1 on overlap, 2 when undecidable (`crates/edda-cli/src/cmd_claim.rs:7-23`); it reads the board fail-closed — an unreadable or damaged line is exit 2, never "clear" (`:340-441`) — counts a heartbeat-less bare-CLI claim as a conflict until `EDDA_CLAIM_TTL_SECS` (`:139-172`), and decides glob-vs-glob overlap with a product of two NFAs (`:730-744`); `edda peers` separates live from stale sessions (`cmd_bridge/peers.rs`, `peers/discovery.rs`). Task leases with `expires_at` + heartbeat in SQLite (`crates/edda-ledger/src/sqlite_store/task_leases.rs`); across machines an agent claims a GitHub issue by a `taking: <machine>/<role>` comment, which the code's own comment says "is not a distributed lock" (`crates/edda-cli/src/claim_guard.rs:585`, context `:583-618`): the first `taking:` line by another machine anywhere in the issue's comments refuses dispatch with no expiry (`:650-679`), an open or merged PR naming `gh-<N>` refuses it too (`:620-635`), and the machine name must be explicit — `--machine` or `EDDA_MACHINE`, never the hostname (`:126-164`).
- **Verdicts and reviews.** `edda verdict` records approve/reject tied to one full sha and gates a conductor plan phase; a verdict recorded before the gate opened is ignored (`crates/edda-cli/src/cmd_verdict.rs:1-15`); a rejection must carry a comment, which is fed back as the agent's next turn (`:129-139`; `on_reject: redispatch` by default, `crates/edda-conductor/src/plan/schema.rs:113-123`), and a gate timeout never auto-approves (default `halt`, `schema.rs:125-140`). - **Post-mortem.** Runs at SessionEnd when a session had a tool or command failure, ran over 20 user prompts, edited one file 3+ times, superseded a decision or hit a multi-agent conflict; the two numbers are env-overridable (`crates/edda-postmortem/src/trigger.rs:8-28, :75-134`; `dispatch/session.rs:503-542` run_postmortem, off with `EDDA_POSTMORTEM=0`). ## What edda does not do (at `46bf30ec`)

- No review panel with more than one reviewer lens on one change: the gate is one reviewer and one grade.
- Auto-claims skip hidden directories by design (`autoclaim.rs:73`), so an edit under `.claude/` claims nothing.
- No promotion of a warning to a block on measured fires: the learned-rule path warns (`tools.rs:104-105`), and `Enforcement::Block` has no constructor call.
- No incident records, corrections registry or pre-registered experiments on whether its rules change behaviour. What it does measure: reviewer catch rate on known-answer canaries (`tests/canaries/`, 14 files) and decision recall (`evals/recall/`).
- Its human-authority tier, `edda ratify`, records who asserted a ratification without verifying it (`cmd_ratify/mod.rs:40-42`).

## What a reader might take from it, and what to leave

- **Take:** a check that a reviewer did not author the commits it reviews, when your commits carry an identity to compare (`identity.rs:71-77` is the shape). A "standing disagreement" output beside newest-wins, once two reviewers have disagreed on one sha at least once. A base-window check at promote, copying the `-z`, `--no-renames`, `--literal-pathspecs` flags and their reasons from `gate.rs:151-181`. Reporting rule SHOWS and HITS as separate columns.
- **Leave:** auto-approve as a default; a rule decay keyed on the failure recurring; a single shared message board as the whole of inter-agent review.

## How I think

Cite the code line, never the module comment or the guide — general advice for reading any catalog, this one included: a doc comment and the function below it can say different things at the same sha, so a claim about behaviour names the line that runs. In edda the pairs worth reading side by side at `46bf30ec` are `hooks.rs:3-4` with `tools.rs:104-105`, `docs/guides/claude-code.md:22` with `tools.rs:149-153`, REVIEW.md:64 with `crates/edda-cli/src/cmd_review/`, and `scars.rs:15` with `:33`; the README's "advisory by default" for claims (README.md:131) matches `dispatch/tools.rs:61-94`. Split every "my system has that too" into the three parts edda keeps apart — who may review (identity), what the standing verdict is (precedence), what the approval is pinned to (head, base).
