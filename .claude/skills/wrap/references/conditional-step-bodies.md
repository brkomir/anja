## Step 1c — the 3-part test, auto-fix rule and output shape (fires at ≥5 session defers) — from `SKILL.md` § Process

   **For each defer, apply the defer-sweep 3-part test inline:**
   - **(a) Citation verification.** For every file path / script / function / enforcement claim in the rationale, run `ls` or `grep -l` to verify it exists. If any cited path doesn't resolve → **rationale is hallucinated** → promote to launch-blocker OR replace with ship-now fix. Evidence: a defer can cite an enforcement script that does not exist; the citation reads as protection until the path is checked.
   - **(b) Skeptical mindset.** Reframe each defer from "defer unless…" to "ship unless…". If the rationale survives the inverted framing, defer is valid. If not → promote. Corresponds to the "skeptical re-pass" applied proactively rather than reactively.
   - **(c) Blast-radius + effort weighting (a refinement of the test).** If the fix is <10 LOC AND the current state has a catastrophic blast (data integrity / content safety / revenue / billing or entitlement ledger / cross-feature invariant drift), promote regardless of "which fix is optimal" uncertainty. Evidence: a rate-limit defer cited "needs prod data to pick the right cap" when a cap raise was a few LOC and the existing cap was provably wrong for users behind shared IPs regardless of the optimum. A defensible partial improvement beats the broken status quo.

   **Auto-fix rule (≤15 LOC per defer):** if a defer fails the 3-part test AND the promotion fix is ≤15 LOC, execute the promotion inline during /wrap — edit the tracker/todo row to promoted status, write the fix, re-run relevant test, commit in Step 8. Larger promotions surface as proposals for user decision before continuing to Step 2.

   **Output shape:**
   ```
   Defer-sweep: N defers added this session, M passed 3-part test, K proposed for promotion
     - {defer ID}: [PASS|PROMOTE — {reason}]
   ```

## Step 5d — why, detection, scope, scaling, verification and skip rules (fires when this session touched messages/*.json) — from `SKILL.md` § Process (tail of the paragraph, split at a sentence boundary)

**Why:** feature/agent work translates new i18n keys inline but routinely SKIPS a dedicated translation review — so session-added translations ship with register drift (formal-leak), ICU-arm grammar bugs, brand-name transliteration ("Coaching Brief" → katakana), and EN-source truncation that the hard-block guard (`tests/translation-untranslated-guard.test.ts`, which only proves *not-English*) does NOT catch. This is the session-end content safety net — the i18n-content analogue of 5b/5c (session-touched-filetype quality gate before commit). **Detect:** derive the changed KEY PATHS from this session's `messages/*.json` diff (committed + working-tree) vs the session base — **SESSION-OWNED commits only: EXCLUDE peer commits interleaved on `main`** (match your own authorship/work, never a fleet-wide `--since` window; 5e already carries this clause and 5d did not — measured 2026-08-16: all 37 `messages/` touches in a wrap window were peers' and a fleet-scoped 5d false-fires; the obligation is session-scoped, the instrument was fleet-scoped) — compare en.json keys + each locale's values. **Scope to the session-changed keys ONLY** — NEVER the whole bundle (that is the owner-invoked broad sweep, not a per-session gate). For each, QA against the en source + the per-language reference your project keeps, if it has one, + the keep-English allowlist (`tests/i18n-keep-english-allowlist.json`). Checks: ICU arg/tag parity vs en (highest severity — breaks throw at render), register/formality per the lang reference, photography terminology, accuracy/completeness vs en meaning, brand-keep-English, non-allowlisted untranslated-English. **Scale agent count to volume:** ≤~30 changed keys → ONE general-purpose helper, briefed as a translation reviewer, covering every non-EN locale (auto-run); >~30 (a bulk batch) → SURFACE a one-line offer to fan out parallel per-locale agents (11, each owning its own `messages/<code>.json` — no cross-agent file conflict) and confirm before spinning, per the recommend-AND-execute carve-out for expensive fan-outs. **Verify after:** all 12 JSON parse + run the i18n unit suite (`translation-completeness` / `-untranslated-guard` / `-allowlist-coverage` / `-register-guard` / `i18n-key-resolution`); read pass/fail COUNTS, not exit code (a `tee` pipe masks the exit code). A direct ICU AST parity check (`@formatjs/icu-messageformat-parser`, run from repo root so `node_modules` resolves) is cheap insurance on the highest-severity class. Fixes land in Step 8's commit. **Skip when ANY:** session touched no `messages/*.json`; trivial session (<5 messages); OR the session's translation changes already went through an explicit translation-review pass this session (cite the artifact — same shape as the Step 2 <15-min exception). **Out-of-scope drift** the agents notice in NON-session keys (pre-existing register/brand drift elsewhere in the bundle) → surface as a NOTE (candidate for an owner-invoked full-file sweep), do NOT fix inline (scope-creep + cost).

## Step 7f — triage procedure and auto-fix rule (fires when the scan returns N ≥ 1) — from `SKILL.md` § Process

   **Procedure (when N ≥ 1):**
   1. Run `python3 scripts/meta-corrections-scan.py --current` to list candidate events for the active session. (Canonical: `/meta corrections --scan --current`.)
   2. For each candidate, orchestrator pre-classifies (real / FP / dupe + pattern tag, choosing from the taxonomy in `.claude/meta-corrections-registry.md` "Pattern-tag taxonomy" section OR in /meta SKILL.md "Process — Corrections" pattern-tag list). Use `python3 scripts/meta-corrections-scan.py --dig <session-prefix>:<idx>` (canonical: `/meta corrections --dig <prefix>:<idx>`) for any ambiguous quote-and-react event (the script's default 400-char excerpt can mask owner reactions on long quote-and-react patterns).
   3. Grep registry for each candidate's session-prefix + idx to filter out events already entered (avoid duplicate writes when /wrap fires on a session that's already been partially triaged).
   4. Show the pre-classification table in the wrap readout: `| # | idx | Excerpt | Cls | Pattern | New ground |` (same format as the 2026-05-24 bulk triage workflow that built the initial registry) — a record the owner can veto, not a question (the auto-fix rule below).
   5. Write the rows you classified real; the owner corrects after the fact if the owner disagrees (the auto-fix rule below).
   6. For each approved TRUE entry, orchestrator runs (canonical: `/meta corrections --add` with same flags):
      ```bash
      python3 scripts/meta-corrections-scan.py --add-entry \
        --date "$(date +%Y-%m-%d)" --session <sess-prefix> \
        --topic "..." --proposal "..." --pushback "..." \
        --correction "..." --new-ground "..." \
        --pattern <primary-tag> --codified <yes|no|pending>
      ```
      Optional `--pattern-secondary` for entries with co-occurring patterns.
      `--codified`: if Step 2's `/meta learn` carried this event (match by `idx`) and turned it into an L# or a watch-tier row, write `yes — L####` or `pending — watch <tag>`; a bare `no` there undercounts the registry's codification rate.

   **Auto-fix rule:** **INTERACTIVE surface** (same shape as Step 7a /me learn-session, not Step 7e read-only). Step 7f auto-invokes the scan, **triages the candidates ITSELF, and writes the real ones** — the owner does not review the real-vs-FP calls, because they are effectively never corrected. ⛔ **This REVERSES the prior REQUIRES-owner-triage clause.** The ~20-30% FP rate obliges careful classification, not owner classification; the calls are reportedly never overturned (a report, NOT measured — no overturn field exists in the scanner or the registry), so routing them costs a round-trip and returns nothing. Drop REQUESTS, DIRECTIVES, tooling QUESTIONS and duplicate records of one utterance; keep only proposal→correction→shift. Measured when this rule was adopted: 13 candidates → 8 real. Promotion to an L# or a spec edit stays gated. Approved entries land in `.claude/meta-corrections-registry.md` which IS committed in Step 8 (the registry is git-tracked so entries survive across machines + are PR-reviewable).

## Step 11 — attributing a recovered Memory-Update block (when one is recovered) — from `SKILL.md` § Process

⚠ **A Memory-Update block recovered at Step 11 is USUALLY ATTRIBUTABLE — CHECK BEFORE DECLARING IT ANONYMOUS.** ⛔ **This sentence read "`queue-operation` records carry no agent name, `subagent_type` or task-id" until 2026-08-26 and was FALSE ON TWO OF THREE LEGS, in the direction that licenses the drop** — measured twice independently over the Agent-dispatch notifications of ONE wave (30 records): **`<task-id>` 28/30 · agent NAME 24/30** — a property of that wave's TASK MIX, not of queue-operation records generally (whole-session the same fields read 233/298 and 20/298 across 34 unique ids: 10 Agent, 19 Background command, 5 Monitor) (from `<summary>Agent "<name>" finished</summary>`) · structural `subagent_type` **0**, the one leg that holds. **Decode the record before counting** — a `json.dumps` round-trip re-escapes the quote, so a raw `Agent "` grep reads **0** where the decoded walk reads 24; that false zero is what made the original sentence look right. So: take the task-id and the agent NAME from the notification, and fall back to "lens inferable from content only" ONLY when both are genuinely absent — never as the default.

## Commit procedure 7 — the announce, the durability-show and the one-grep bound (HIGH overlap only) — from `SKILL.md` § Commit procedure (shared with /audit-check Post-Gate Action)

   - **(a) Announce** to peers: `python3 scripts/session-manifest.py mail-send --to all` a one-liner stating your shared-file commits (`<sha>` + paths), what you SWEPT (peer appends that rode into your commit, additions-only), and your did-NOT-touch list (peer WIP you left dirty). A peer mid-committing the same file then reconciles KNOWINGLY instead of via a confusing git "already-applied" / "no changes". Mail is free + advisory + needs no approval — send-then-report.
   - **(b) Durability-show** in the /wrap summary: commits reachable-from-HEAD + your content present-in-HEAD *after* the peer commits landed + nothing-of-yours-uncommitted.
   **Bounded to high-overlap moments** — skip on low-overlap sessions (read-only scans + first-commit-wins keep the common case safe; announcing every wrap is noise). **Do NOT over-investigate the collision:** ONE `git show HEAD:<file> | grep '<your content>'` per shared file confirms survival — resist the multi-command who/why/lost archaeology (a `M`-you-didn't-make is EXPECTED, never data loss; trust it, one grep, move on). **Exception — owner-asked airtight check:** when the owner EXPLICITLY asks to verify nothing was overridden/reverted (not merely "is it committed"), the per-file `git diff <your-commit> HEAD -- <file>` (empty = byte-identical = intact; any `-<your-line>` = a peer reverted/overrode it) IS warranted — owner-directed proof is the exception, not a spiral. Evidence: a 6-scan forensic spiral on a live meta-file collision that the one-grep rule was meant to pre-empt; both the skipped announce (coordinate through the mail system) and the durability-show (confirm no work was lost) had to be prompted from outside the session.
