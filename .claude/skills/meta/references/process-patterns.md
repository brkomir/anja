Cross-expert synthesis only. No memory-gardener, no roster audit, no self-audit. Pure pattern-recognition across all `.claude/skills/*/MEMORY.md` files. Use when seeking *insight* (what themes recur, what experts contradict each other, what's emerging across the system) rather than *hygiene* (what to prune).

**When to run:** after big multi-expert sessions where 5+ experts wrote memory entries in a short window, or monthly as a system-health read. Cheap when done with a reading agent; costs ~3-5 min wall-clock.

**Steps:**

1. **Cross-expert contradiction scan (Phase 2b-intensified).** Walk every expert MEMORY.md. For each decision with the pattern "X is correct" or "Y is wrong", search sibling memories for opposing stances on the same topic. Contradictions are highest-value output — they indicate the system hasn't converged and will produce inconsistent recommendations depending on which expert fires.

2. **Convergence patterns.** The inverse of (1): when 3+ experts independently reach the same conclusion on a topic, it's a candidate for promotion from per-expert memory to a project-wide rule (`.claude/rules/`) or meta lesson. Surface these as promotion candidates. **Codification-check before claiming un-codified.** A convergence is a PROMOTION candidate ONLY if it is not already codified — BEFORE surfacing it as un-codified, grep the codified state: `.claude/rules/*.md` + meta/MEMORY.md L#s (`architecture-counts.mjs list → maxL`, never a prose grep) + the Watch-tier register + `DECISIONS.md` + `DECISIONS-ARCHIVE-*.md`. If an existing L#/rule/watch-entry/DECISION already covers it → record "already-codified (cite the anchor)", NOT a promotion candidate. This sweep has no codification-check, so it over-reports "un-codified" (N=2 2026-06-25: all 4 surfaced "convergences" were already codified — two as recorded lessons, one as a watch-candidate, one as a haines doctrine; and all 3 "open disputes" were already settled in code or a recorded decision). The same check applies to the Step-1 contradiction/"dispute" surfacing: a dispute already resolved in code or `DECISIONS.md` + `DECISIONS-ARCHIVE-*.md` is STALE, not open.

3. **Stale cross-reference sweep.** Grep every memory for references to files/functions that have been renamed, moved, or deleted (git log --oneline --diff-filter=D, --diff-filter=R since the memory's last-modified date). These are "time bombs" — memories that still read correct but cite code that no longer exists.

4. **Emergent-theme detection.** If 3+ experts mention a theme NOT yet in project memory or rules (e.g., "parallel-session coordination" was emergent across 8 sessions before a lesson codified it), flag for user — the theme wants a dedicated rule or memory entry.

5. **Capability-gap analysis (Phase 2c intensified).** For each expert, count findings generated in last 30 days. Zero-finding experts for 60+ days are dormant — flag for potential consolidation. Many-finding experts (>20 in 30 days) may need scope decomposition.

6. **Panel-effectiveness rollup.** Cross-reference the `Panel Playbook` sections in the meta `MEMORY-ARCHIVE-*.md` shards (grep `Panel Playbook` across `.claude/skills/meta/`; the `MEMORY.md` router holds none) with outcomes (defer-promotion rates, finding-to-noise ratios per expert per audit). Update the "Who finds real bugs" and "Reliable pairs" sections if evidence has shifted.

7. **Demand-side capability-gap sweep (the lesson's cause-fix #2).** The catalog of un-adopted solutions is SUPPLY-side only — anti-scope `### REJECTED` rows, Adoption Queue QUEUED items, and `🟡`-partial COMPARISON.md cells — and its revisit-triggers are PASSIVE (nothing watches them against accumulated pain). So a pattern solved elsewhere can sit un-adopted for weeks while the matching pain recurs (the session-lifecycle signal sat unbuilt while re-wrap friction recurred 2-5×/session). This step performs the demand→supply MATCH the passive triggers never do: take the dominant pains from `scripts/meta-corrections-scan.py --analyze` (top pattern-tag distribution) + `--rule-repeats --since <the previous maintain run's date>` (saved rules named again after they were written; it counts mentions, not proven breaks: hand-read each top row's entries and match only those that say the rule was loaded and not applied — a later entry also names a rule when the correction's new clause was written into it, which is the rule growing, not a break: 4 of one saved rule's 6 rows at the first reading) + any friction surfaced this window, and for each, scan the three un-adopted catalogs for a solution that addresses it — (a) anti-scope REJECTED (is the rejection's revisit-trigger now firing?), (b) Adoption Queue QUEUED (is the LOC-cheap item's trigger met?), (c) `🟡`-partial matrix cells (is the cited missing slice now the pain?). Surface any match as a promotion candidate (→ `/meta learn` for D+I+S + build). Cheap — reuses the `--analyze` output + reads three already-existing catalogs; the value is the ACTIVE pain↔catalog match. NOT a new subsystem (don't meta-meta) — it's a reading step inside `/meta patterns`.

**Output:** contradiction table (X vs Y, with file:line citations), convergence list (N experts agree on Z → promote to rule?), stale-reference list (file paths that no longer exist), emergent-theme proposals, dormant/hot-expert flags, panel-playbook deltas, **demand-side promotion candidates (recurring-pain ↔ un-adopted-catalog matches)**, and the top 3 `--rule-repeats` window rows with their hand-read break count, whether or not anything matched (show them at `/meta maintain`).

**Scope boundary:** no writes to memory files during `/meta patterns` — surface-only. Writes belong to `/meta memory-audit` (hygiene) or `/meta learn` (new lessons). Patterns is read-and-analyze; its output drives subsequent `/meta memory-audit` + `/meta learn` work.
