# Review Hub — dedicated cross-session `--code` review session

Dedicates THIS session to absorbing the fleet's Step-2b `/expert-review --code` reviews, so working sessions can DELEGATE their reviews + not serialize. The hub arms a real-time inbound-mail listener, runs an independent builder≠breaker panel per delegation, verifies every finding itself, and mails verdicts back — applying nothing, pushing nothing (REVIEW-ONLY).

Validated across the founding session 2026-06-25 (6 delegations + 2 A/B/same-vs-peer experiments; the instrument is `.claude/delegated-review-experiment.md`).

## When to use
- The owner designates a session as the fleet's `--code` hub (e.g. the owner tells it that it is now the session dedicated to `--code` reviews and should arm the listener, broadcast and keep listening). Run `/review-hub` on that session's **first turn**.
- NOT for a one-off review — for that just run `/expert-review --code <ref>` inline. The hub is for a session DEDICATED to absorbing MANY delegations over its lifetime.

## Entry points

- **`/review-hub`** — become the hub on a FRESH role, no incumbent. Phases 1-3 below.
- **`/review-hub --await [<incumbent sid|name>]`** — ⛔ **THE INCOMING SESSION'S FIRST STEP.** Declares that this session is about to become the hub and then WAITS for the incumbent's signal. Stamps an AWAITING marker, arms the listener so the signal can land, and **claims nothing, stamps no hub marker, and does not broadcast to the fleet.** §A below.
- **`/review-hub --handover <sid|name>`** — ⛔ **THE CURRENT HUB'S STEP.** Announces to the fleet that the named session is taking over, partitions the work, and begins the wind-down. §B below.
- **`/review-hub --retire`** — STAND DOWN via Phase 4, in a FIXED ORDER. **TWO terminal states, not one:** a declared VACANCY + election, OR a successor CONFIRMED-BY-ACK (its own step 4). ⚠️ **That ack branch is NOT dead and this line said it was:** `session-manifest.py` cites `--retire` step 4 in three comments as the writer of the successor sid, and a peer who ACKED but never ran `--await` is routable by that branch and by nothing else. It BYPASSES §B.1's STOP gate (an ack, not an awaiting marker), so prefer `--handover`; do not delete the branch.
- **`/review-hub --pause`** · **`--resume`** — hold new reviews, panels and subagents; the running seats finish and their verdicts go out, everything else is ACKed as held; § ⏸ below.
- **`/review-hub --pause --when usage>=N`** — the same pause, entered by a watch when this session's five-hour usage reaches N%, and lifted by a second watch at that window's reset, or sooner on a switch to an account below N; a pause the owner types still waits for the owner's word. § ⏸ steps 6-10.
- **`/review-hub --takeover`** — ⏸ **SUPERSEDED 2026-09-12 by `--await` + `--handover`.** Section moved to `references/takeover-superseded.md` 2026-09-29 (pointer below); kept for the unresponsive-incumbent case and for its warrant mechanics; do not reach for it as the normal path.

### ⛔ THE HANDOVER PROTOCOL — five steps

**It REPLACES the `--takeover` warrant dance and the seat-routing table that stood here for ~15 minutes before it.** That table said: incumbent-seat ⇒ `--retire (in favor of X)`, successor-seat ⇒ `--takeover` after a prose instruction, no-hub ⇒ vacancy. It was judged insufficient. **What was wrong with it:** it routed by which seat the owner happened to be sitting in, so the protocol changed shape depending on an accident of where the owner typed — and BOTH branches still ended with the incumbent improvising the wind-down. The five steps below are seat-independent and the wind-down is specified.

⛔ **THE DIRECTIVE BEHIND THE FIVE STEPS — IT IS RESTATED HERE BECAUSE IT LIVED NOWHERE DURABLE.** A review of this
very commit found it survived only on planes that expire: the mail store (24h read / 72h unread), a log, and two session
transcripts. A protocol whose source of authority prunes in a day cannot be checked against its own intent, which is what
makes every interpretation below unfalsifiable from the artifact. So its substance is recorded here, step by step:

1. A new session runs `/review-hub --await`, which declares that it will soon become the new review hub and waits for
   the current hub's signal.
2. The current hub runs `/review-hub --handover <session id or name>`, which broadcasts to the fleet that the new hub
   is taking over.
3. Any unfinished but started work from the current hub's queue transfers to the new hub; other work that is ongoing or
   in an unclosed review loop finishes in the retiring hub.
4. After the unfinished work is complete, the retiring hub announces that it is done and will not respond to new
   requests; any new request it receives is forwarded to the new hub.
5. Once everything from the previous steps settles, the retiring hub updates its working plan and notifies the owner
   that it is ready for `/wrap`.


⛔ **THE WARRANT APPARATUS IS GONE FROM THE NORMAL PATH, DELIBERATELY.** `--handover` is invoked IN the incumbent, which is the seat that must act, so there is nothing to relay and nothing to authenticate. No `authorized-by`, no `_validate_authorized_by`, no quote-grep. Those survive only on the unresponsive-incumbent path: the successor's half in `references/takeover-superseded.md`, the incumbent's half in § Receiving a `hub-retire-demand` below.

| step | seat | command / act |
|---|---|---|
| **1** | incoming | `/review-hub --await` — declare intent, stamp AWAITING, arm the listener, WAIT |
| **2** | current hub | `/review-hub --handover <target>` — **stamp `.retiring` with the target FIRST, then broadcast.** ⛔ NOT the other order: this row said broadcast-then-stamp until a review caught it, and the inverted window is the election this protocol exists to close |
| **3** | both | partition the work by the discriminator below — some TRANSFERS, some STAYS |
| **4** | retiring hub | when the retained work is done: broadcast DONE + FORWARD-ONLY |
| **5** | retiring hub | update the working plan, notify the OWNER it is ready for `/wrap`, and HOLD |

### §A — `/review-hub --await [<incumbent>]` (the incoming session)

1. **STAMP THE AWAITING MARKER AND WRITE YOUR SESSION MANIFEST** — `date -u +%FT%TZ > .claude/state/review-hub-awaiting-<your-sid8>`, then `python3 scripts/session-manifest.py write`. This is a DIFFERENT marker kind from `review-hub-active-*` and must never be confused with one: an awaiting session is **not** a hub and must not be delegated to.
   ⛔ **THE MANIFEST IS NOT HOUSEKEEPING — THE WHOLE ELECTION SUPPRESSION GATES ON IT.** `_successor_is_live` returns False unless `active-sessions/<sid>.md` exists, so a successor with no manifest makes `hub-discover` print its review-hub vacancy notice (`🚨 … VACANCY`) and the election command **instead of** `NO ELECTION — SUCCESSION IN FLIGHT`. Fixture-measured with a positive control on this section; conditional today only because 11 of 11 live sessions happen to have manifests.
   ⚠️ **THIS MARKER HAS NO REAPER, NO LIVENESS CHECK AND NO ACK, AND THAT IS A KNOWN HOLE, NOT AN OVERSIGHT YOU SHOULD RE-DISCOVER.** Nothing removes it: no `rm -f` in this file names it (they name the base marker, `.retiring` and the paused marker), and the GC globs `review-hub-active-*`. So §B.1's STOP — the protocol's ONLY refusal — is satisfiable by a corpse forever. **If you abandon an await, `rm` your own marker.** And §B.1's existence test is weaker than what `--retire` step 4 requires of a successor (an ACK, from a seat that demonstrably ran); treat a bare `test -e` as the floor it is.
2. **ARM `mail-listen`** (`--poll 30`) so the incumbent's signal can land. **Do NOT arm the staleness poller yet** — you hold no queue, so it would poll an empty set. ⛔ **THIS DEFERRAL IS RESUMED AT §B.4 AND NOWHERE ELSE — DO NOT LEAVE IT DANGLING.** An earlier version of this section deferred it here and resumed it in no step at all, which silently re-armed a measured incident (a hub armed 10.4h with three requests at 83/80/56 minutes and no alarm) for every hub arriving by handover. ⭐ **The general form, which is the better half of that finding: a "not yet" inside a numbered protocol is a DEFERRAL WITH NO TRIGGER — grep the file for its resumption before you credit it. The dropped step is always the one the owner never had to say.**
3. **MAIL THE INCUMBENT**, naming yourself as the awaiting successor, so it knows who to hand to and does not have to guess or ask the owner. If you were given no incumbent, resolve one with `hub-discover`.
4. ⛔ **DO NOT BROADCAST TO THE FLEET, DO NOT `fleet-claim`, DO NOT STAMP A HUB MARKER.** The fleet switches on the INCUMBENT's step-2 broadcast and on nothing else. An awaiting session that announces itself creates a window where peers believe two hubs are live — the one failure this whole protocol exists to prevent, arriving through eagerness rather than through a crash.
5. **WAIT.** Do other work; the listener re-invokes you when the signal lands. **Do not poll the incumbent and do not re-ask.** If nothing arrives and the owner asks, say you are awaiting and name the incumbent — do not escalate to `--takeover` on your own judgment.

### §B — `/review-hub --handover <sid|name>` (the current hub)

1. **RESOLVE THE TARGET ONCE, INTO A VARIABLE, AND VERIFY IT.** `T=<sid8>` — then confirm `review-hub-awaiting-$T` exists. **If it does not, STOP and say so**: handing to a seat that never ran `--await` hands the role to a session with no listener, no marker and no expectation, which is a vacancy wearing a successor's name. A sid or a session NAME is acceptable input; resolve a name with `session-manifest.py who`.
   ⛔ **TYPE THE SID EXACTLY ONCE. Every later use is `$T`.** Hand-typing it into both the verification and the `.retiring` stamp means nothing compares them, and a SHAPE-VALID transposition passes the `[0-9a-f]{8}` validator: it then suppresses the fleet election **and** makes `fleet-claim` refuse the REAL successor — two independent gates, one character, both silent. A shape-INVALID typo reads as a declared vacancy and a third seat claims while you believe you handed over. One variable removes the whole class.
2. **STAMP `.retiring` WITH `$T`, THEN READ IT BACK.** `echo "$T" > .claude/state/review-hub-active-<your-sid8>.retiring` and verify through the function the fleet actually uses, not by `cat`: `_retiring_successor` must return `$T`. ⛔ **`touch` IS WRONG HERE:** an EMPTY `.retiring` declares a VACANCY and sends every booting peer into an election. With the sid in it, `hub-discover` prints `🔁 NO ELECTION — SUCCESSION IN FLIGHT` and routes to the target.
3. **BROADCAST THE ANNOUNCEMENT** — `--to all --signal hub-handover`, and **the signal token is not decoration**: `mail-listen` HOLDS `signal: info` without waking the recipient, and `info` is the majority convention for broadcasts (185 of 295 measured). An `info`-tagged handover would leave the awaiting seat asleep on the one message it is waiting for. Carry: the target's sid and name, that it takes every NEW request **effective now**, that this seat keeps its retained work (step 3), and that this seat's inbox stays READ until it says otherwise. This broadcast is what moves the fleet.
4. **THE TARGET THEN CLAIMS, READS THE MESSAGE, AND ONLY THEN RESUMES PHASE 1.** `fleet-claim review-hub` needs no override flag once `.retiring` is stamped — **and that is not the hazard.** ⛔ **THREE OUTCOMES SHARE rc=3: READ THE MESSAGE, NEVER THE EXIT CODE.** **LOST names a winner — ack them, STAMP NOTHING, and STOP: you are not the hub, and the marker below is what would make you the second one.** REFUSED is a NEAR-match — read `fleet-claim --list` before deferring. COULD NOT VERIFY means the write landed and the read-back was empty — `--check` before STAMPING, not merely before announcing. *(This imperative has now been dropped by TWO successive compressions of this file and restored twice on review findings. It is the first thing to go and the last thing you can afford to lose.)*
   **Then, and only then:** stamp your own base hub marker, **re-arm `mail-listen` WITH `--rebroadcast-hours 48`** (a bare listener leaves the marker ageing past the 72h floor until every peer's `hub-discover` drops you to STALE-BROADCAST), and **arm the staleness poller as a SECOND Monitor, also `timeout_ms: 1800000` and re-armed on each expiry** — `while true; do bash scripts/hub-stale-request-poll.sh 2>&1; sleep 600; done`, the `2>&1` load-bearing. **This is where §A.2's deferral is resumed. A hub arriving by handover that skips it holds a queue with no alarm on it.**

### §C — STEP 3, THE WORK PARTITION. This is the step that decides whether anything gets dropped.

✅ **SETTLED: QUEUED TRANSFERS, STARTED STAYS.** This reading of step 3 is settled. It is no longer an interpretation and does not need re-litigating; the table below IS the rule.

⭐ **AND THE DIRECTIVE'S OWN STEP 4 SETTLES IT INDEPENDENTLY — the strongest evidence here, previously missed by both readers that argued about step 3.** Step 4 says that after the unfinished work is complete, the retiring hub announces that it is done and will not respond to new requests. That sentence is **vacuous unless the retiring hub keeps unfinished work to finish**: if everything started had transferred, there would be nothing left for it to complete and nothing to announce. So the rule is not a correction of the directive at all — it is the reading its next step requires. ⚠️ Worth stating because the argument below was reached for first and is weaker: it reasons from what an implementer CAN do, which invites the reply that the implementation should change instead; this one reasons from what the directive SAYS. **Anyone re-opening this should be shown step 4 before the executability argument.**

*Why it needed settling, kept because it is the argument that survives if anyone re-opens it:* step 3 says that unfinished but started work transfers, and **the literal reading is UNEXECUTABLE at row 2 of the table below** — a running panel cannot transfer, because sub-agents belong to the session that dispatched them, so "started ⇒ transfers" orders you either to hand over something you physically cannot hand over or to kill it and destroy the spend, which is separately forbidden. The directive is restated above, so the rule stays checkable against its source. *(This paragraph read "WE READ IT AS … CONFIRM OR CORRECT IT" and framed the partition as a reading rather than a rule until it was settled.)*

⚠️ **THE DISCRIMINATOR, stated because step 3 names two categories that sound alike and an implementer has to draw one line:** *has this item consumed context that lives only in THIS session?*

| state | where it goes | why |
|---|---|---|
| received, acked, **no panel dispatched and no verdict sent** | **TRANSFERS** — forward it to the new hub naming the ORIGINAL SENDER, not yourself | nothing is lost by a fresh seat picking it up; there is no context to carry |
| **panel dispatched / lenses running** | **STAYS** | sub-agents belong to this session and cannot be handed over; killing them destroys the spend (and is separately forbidden) |
| **verdict sent, fold-verify owed** — an UNCLOSED LOOP | **STAYS** | the findings, the file:line verifications and the brief premises live in this transcript; a fresh seat would re-derive them or take them on trust |
| a HOLD this seat issued that has not been cleared | **STAYS**, and its `todo.txt` row is what survives if the session does not | a hold is the strongest thing this seat sends; the mail plane expires and the row does not |

⛔ **STATE THE PARTITION OUT LOUD, PER ITEM, IN THE STEP-2 BROADCAST — derived by command, never recalled.** Run all four instruments (`review-request-closure-scan.mjs`, `hub-unfinished-loops.py`, `hub-open-promises.py`, `hub-stale-request-poll.sh`) and list every row with its side of the line. **A partition nobody published is a partition both hubs will guess at differently**, and the failure is silent on both sides: the new hub assumes you kept it, you assume they took it.
⚠️ **All four instruments are blind to the hub's own dominant open loop — a verdict YOU issued whose findings never came back.** That one is invisible to every scan as run by default (§ ALSO ARM THE QUEUE-CLOSURE CHECK: pointed at the requester, the disposition scan counts your own ledger commits as its fold) and it is the commonest thing in the STAYS column, so read the ledger rows, not the scan output.

### §D — STEP 4, THE DONE ANNOUNCEMENT. Distinct from step 2 and easy to skip.

⛔ **PRECONDITION, AND IT IS THE GATE THAT STOPS THE WORST REACHABLE STATE: confirm `review-hub-active-<target>` EXISTS before this broadcast.** Without it, an awaiting seat that dies after §A leaves you with a base marker present, `.retiring` naming a dead sid, `hub-discover` reporting **0 live hubs with the election SUPPRESSED**, `fleet-claim` refusing every other seat, and you having publicly refused new work while forwarding to a corpse — **with no step violated anywhere.** One existence check also makes §B.1's typo case and the dead-target case LOUD instead of silent. If it is absent: do NOT send this broadcast, say so, and either re-run `--handover` against a live target or declare a VACANCY.
When every STAYS item has closed AND that precondition passes, **broadcast again** (`--to all`): this seat is DONE, it will **not** answer new requests, and **anything that arrives from here is FORWARDED to the new hub naming the sender**.
⛔ **THIS IS A SECOND, SEPARATE BROADCAST AND THE PROTOCOL IS INCOMPLETE WITHOUT IT.** Step 2 told the fleet where NEW work goes; step 4 tells them this seat has stopped working, which is a different fact and the one peers need before they stop expecting a reply. A step-2 broadcast with no step-4 leaves every peer holding a retained item unable to tell "still working" from "gone quiet".
**Forward, never re-verdict.** A request that reaches you after step 4 goes to the new hub as the REQUESTER's, not as yours — re-verdicting it re-opens the split the handover just closed.

### §E — STEP 5, READY FOR WRAP. The retiring hub does NOT wrap on its own judgment.

1. **UPDATE THE WORKING PLAN** (`plans/session-<sid8>-<date>.md`) — the partition as it actually resolved, what closed, what transferred, and the closability verdict. This is the artifact that outlives the session.
2. **NOTIFY THE OWNER that it is ready for `/wrap`** — and say what the wrap will still carry (open loops it will find, anything it must commit); the wrap IS the close, never a cost of closing.
3. ⛔ **HOLD. Standing down from the ROLE is not ending the SESSION**, and conflating those has already cost a wrong commit on `main` (see the vocabulary table in Phase 4). The successor has no authority over this gate and neither does your own read of being finished. **Only the owner's go releases it.**

### ⏸ `/review-hub --pause` — hold new reviews until the owner lifts it

> The pause holds new reviews, panels and subagents until the current ones are complete. A review the hub does itself is a new review. The first pause and how it lifts: the source project's `references/hub-incidents.md` (not in this copy) § the pause.

**Stops:** seating any new reviewer, panel or subagent of any kind (fold-verify seats, a breaker of the hub's own work, a due `/wrap --checkpoint`'s slice agents), and the hub reviewing anything not running at entry, a request ACKed but not yet seated included. **Never `TaskStop` a running seat** — the pause is on new work, not an abort.
**Continues (how the running reviews complete):** running seats finish; a seat a limit or a login drop cut is resumed by its agent id once the cause clears; returned patches are combined, gated and mutated, and their verdicts sent; *(hub's reading)* a fold-verify that is a byte-compare needing no seat. A fold whose residue needs a seat is held.
**Each held request:** a ledger row whose Verdict cell OPENS `QUEUED — HELD (owner pause)` (the parser does not know `HELD`: `HELD … fold-verify` reads as a dispositive FOLD-VERIFY and closes the request), and one ACK, `--signal review-ack`, subject `ACK <sha>: HELD, pos <n>/<N> — the hub is paused by the owner`, no verdict word in it. At the lift, one line each naming its panel (Phase 3's panel statement). The staleness poller keeps saying *start it* on held rows; the row is the answer.

1. **Enter:** list the running seats from `ListAgents` and the dispatch log (sha + lens each), write `.claude/state/review-hub-paused-<sid8>` (`<epoch> inflight=<N> until=owner`), add a dated `⏸ PAUSE` block to the working plan (the owner's words, the running seats, the held queue), and confirm in one line to the owner. The listener stays armed; peers learn of the pause from their ACK, so no broadcast.
2. **After a compaction or resume,** `ls` the marker before seating anything; it outlives the context. `/post-compact` Step 5 reads it. `pgrep -P $PPID -f '[h]ub-usage-watch'` empty ⇒ re-arm the usage watch step 9 names, if any.
3. **Ends only on the owner's word** — `/review-hub --resume`, or the owner's own words lifting it (it holds until the owner says otherwise; why: the source project's `references/hub-incidents.md` (not in this copy) § the pause). When the last running seat is back and its verdict sent, tell the owner in one line that the running reviews are done and which requests are held, and KEEP holding. On the owner's word: remove the marker, tell the owner in one line which held requests start now, and seat them in arrival order.
4. **Not `/pause`** (it holds a builder session's folds and commits and banks its running builders' hand-backs unverified — here, the running reviews' verdicts still go out) **and not `/standby`** (it parks the seat and stops the listener). An owner "pause" here that names NEW reviews or subagents is this one.
5. **Handover and teardown:** a held request is a queued item, so it TRANSFERS (§C table), and a successor would seat it at once; the forward says it is held by the owner's pause, and the new hub stamps its own marker until the owner's word. Phase 4 removes `review-hub-paused-<sid8>` with the other two markers.

**`--pause --when usage>=N` — the pause the limit causes, lifted at its reset or on a switch to an account below N.** It is the owner's pause armed ahead of time, so steps 1-5 bind it except at its end (step 3) and at a handover (step 5): the limit is this session's, so the forward says so and the successor arms step 6 with the same N rather than stamping a hold until the owner's word; its own watch decides.

6. **Arm** `python3 -I scripts/hub-usage-watch.py --sid <sid8> --pause-at N 2>&1` as a Monitor, `timeout_ms: 1800000`, re-armed on each expiry like the staleness poller (`2>&1` for the poller's reason: a Monitor captures stdout only, and a bad argument prints to stderr), and write one line in the working plan, `usage watch armed: --pause-at N`, which is what a recovery re-arms it from (step 9). The script is read-only; the readings it trusts are its docstring's (`agent-dispatch-session-limit-guard.py`'s rule, with the reset epoch required). On a `usage watch: no trusted reading (<reason>)` line do nothing: the watch keeps running, and after a reset that line is what wakes the seat to refresh the figure. An exit with no decision line (`usage watch: internal error (…)`, a traceback) is re-armed once and reported to the owner if it recurs. `--once` gives the same decision for a check by hand (exit 0 fires, 1 holds, 3 a fault).
7. **On `USAGE-PAUSE pct=<p> resets_at=<ISO>`:** if `review-hub-paused-<sid8>` already reads `until=owner`, the owner's pause outranks this one: change nothing and arm nothing more. Otherwise enter by step 1 with the marker `<epoch> inflight=<n> until=reset:<ISO> cause=usage>=N`, each held ACK's subject ending `— the hub is paused until the ~HH:MMZ reset` in place of `by the owner`, tell the owner in one line that it paused (the % and the reset time), and arm the second watch the same way: `python3 -I scripts/hub-usage-watch.py --sid <sid8> --pause-at N --resume-after <ISO> 2>&1`. It fires on the first trusted reading below N after the reset, or before the reset on one from another account's window (step 8).
8. **On `USAGE-RESUME pct=<p>`** (or `USAGE-RESUME pct=<p> account-switch resets_at=<ISO>`: before the old reset, a reading from another account's window, below N; the switch shows only after this session's next request on the new account, since an idle session keeps the old figures, so it lands at the hub's next wake, not when the owner switches)**:** run `--resume` (step 3's last sentence) ONLY while the marker still reads `cause=usage` (the watch checks the same before printing, and says `not resuming` when it does not: stop that watch then), its one line also saying that the window reset, or that the account switched and when the new window resets, and the new %, and re-arm step 6 for the next window. A pause the owner orders during it (`--pause`, or the owner's words by step 4) rewrites the marker by step 1 to `until=owner`, which no watch lifts: stop the resume watch and keep holding. The owner's `--resume` or words lift either kind at any time and stop the resume watch; step 6 is then re-armed unless the owner says to stop watching the limit, which removes the plan line, and the one line says which. Re-arm it at once only if `--once` prints `holding` below N; otherwise it would read the figure that caused this pause and pause again within one poll, so the plan line reads `usage watch armed: --pause-at N from <ISO>` (that window's reset) and it is re-armed at the first wake after that time.
9. **Across a compaction the marker says which watch is live:** none ⇒ step 6's, if the working plan records the arm (not before its `from` time); `cause=usage` ⇒ the resume watch, rebuilt from the marker alone (`until=reset:<ISO>` is its `--resume-after`, `cause=usage>=N` its `--pause-at`); `until=owner` ⇒ neither. Those two rebuild the whole command, so unlike the poller's nothing is banked; step 2 re-arms it.
10. **`--when` takes only `usage>=N` for now;** a clock time is `/autorun`'s job.

### Receiving a `hub-retire-demand` — what the INCUMBENT does

This is the other half: how the incumbent knows a retire order is genuine before it runs
`--retire` from step 1.

1. **VERIFY THE WARRANT FIRST — this is how you confirm the order came from the owner, and it
   is the whole reason the signal is machine-checkable.** Run
   `m._validate_authorized_by('<the authorized-by value>')`. A `(True, …)` certifies ONLY that a HUMAN SPOKE in that session at that second.
   ⛔ **IT IS CONTENT-BLIND AND CANNOT TELL A RETIRE DEMAND FROM ANY OTHER OWNER TURN — any two
   different owner utterances in one session both return `(True, …)`, so a `True` says only that
   the owner spoke, never what the owner said.** Reading it as *"this is the owner's demand"* would rest
   the whole mechanism on a false sentence.
   **So AUTHENTICATE THE QUOTE too:** `grep -F '<a distinctive clause of the quoted body>'` against
   the named session's jsonl — the validator hands you the record's exact timestamp; the grep is what
   makes it a DEMAND. No hit ⇒ peer request, decline it. A judgment on the order's CONTENT (not
   standing down on a secondhand directive) is stronger than this check, so the check adds to that
   judgment and never replaces it. **A missing or non-verifying warrant is a PEER REQUEST,
   not an owner order — you are entitled to decline it**, and should say so rather than retire
   on a claim you could not check. Nothing weaker certifies: prose, a confident subject line, and
   absence-predicates never do.
2. **STAMP `.retiring` FIRST, WITH THE SUCCESSOR'S SID IN IT** — before anything else —
   `echo <successor-sid8> > .claude/state/review-hub-active-<your-sid8>.retiring`. From that
   instant `hub-discover` renders you `⏸ RETIRING — do NOT delegate`, so a peer delegating
   mid-handoff reads a MARKER rather than a timestamp. It is also the successor's unblock.
   ⛔ **`touch` IS NOT ENOUGH HERE, AND THE EMPTY FORM OPENS THE WINDOW THIS PROTOCOL EXISTS TO
   CLOSE.** A `.retiring` marker is never counted LIVE, so from your stamp until the successor
   stamps its own marker at its `--takeover` step 5 (`references/takeover-superseded.md`) the fleet reads **zero live hubs** — and `hub-discover`'s
   vacancy branch then tells every peer booting in that window to ELECT. That is the same O(N)
   fan-out the vacancy branch exists to prevent, arriving through the handover working rather
   than through a crash; measured at ~4 minutes on one real
   succession. You are the one seat that knows the successor at this instant — the demand named
   it in `--authorized-by` — so write it down. `hub-discover` reads the sid out of the file and
   prints `🔁 NO ELECTION — SUCCESSION IN FLIGHT`, routing delegations to the successor instead
   of starting an election (`_retiring_successor`, `scripts/session-manifest.py`). An EMPTY
   marker still means a DECLARED VACANCY and still elects, which is why the two spellings must
   not be used interchangeably.
3. **DERIVE the open queue by command, never recall** — `node scripts/review-request-closure-scan.mjs`
   plus an enumeration of inbound, read AND unread. A retirement that says "everything is closed"
   from memory is the one claim nobody downstream can re-check.
4. **PRESERVE the dismissal ledger** into a git-tracked `plans/` file and name it in the
   broadcast — it is sid-keyed and git-ignored, so retiring deletes it from the fleet's view
   without deleting the file, and a successor re-flags every dismissal as OPEN.
5. **ANNOUNCE the retirement IN THE SUCCESSOR'S FAVOUR** (`--to all`), naming the successor's
   sid explicitly. This is a successor-CONFIRMED retirement, so it needs no ack to be complete —
   but it must not be softened to "a fresh hub is coming", which designates nobody and triggers
   the every-peer-self-runs fan-out. State your open loops and whether your inbox stays read.
6. ⛔ **THEN HOLD FOR THE OWNER'S GO BEFORE `/wrap`.** The retiring hub announces its retirement in
   the successor's favour to the fleet and then waits for the owner's go before calling `/wrap`.
   Standing down from the ROLE is not ending the SESSION — the two are
   different axes and conflating them has already cost a wrong commit on `main` (see the
   vocabulary table in Phase 4). **The successor has no authority over this gate**; neither does
   your own read of being finished.

A takeover transfers the ROLE, never the outstanding work: finish every open loop regardless.

### `/review-hub --retire` — the ordered sequence

⛔ **THE ORDER IS THE POINT. Phase 4 has always held every step; what it lacked was a
named command that runs them in sequence — and the retiring hub reconstructs that order
from prose at exactly the moment it is winding down.** Codified after a retiring seat that
had READ Phase 4 the same day still (a) broadcast BEFORE
stamping the marker and (b) wrote *"a fresh hub is up in minutes"* — the precise phrasing
the vacancy rule names as designating nobody. Two of the four steps, in the one run.

1. **STAMP `.retiring` FIRST**, before anything else — `touch
   .claude/state/review-hub-active-<sid8>.retiring`. From that instant `hub-discover`
   renders this hub `⏸ RETIRING — do NOT delegate`. It precedes the broadcast so a peer
   delegating mid-handoff reads a MARKER, never a timestamp.
2. **DERIVE the open queue — never recall it.** Every request addressed to this hub with a
   verdict from you, established by command. A retirement broadcast that says "everything
   is closed" from memory is the one claim nobody downstream can re-check.
3. **PRESERVE the dismissal ledger** into a git-tracked `plans/` file and name it in the
   broadcast — it is sid-keyed and git-ignored, so retirement deletes it from the fleet's
   view without deleting the file.
4. **BROADCAST**, and it MUST end in exactly one of two states, never in prose between them:
   - **successor CONFIRMED** — named sid, and only after that peer ACKED. **Write that sid into
     your `.retiring` marker in the same turn** — `echo <successor-sid8> >
     .claude/state/review-hub-active-<sid8>.retiring` — so `hub-discover` prints
     `🔁 NO ELECTION — SUCCESSION IN FLIGHT` instead of an election to every peer that boots
     before the successor stamps its own marker. The broadcast reaches whoever is reading mail;
     the marker reaches whoever is booting, which is the population the election misroutes.
   - **VACANCY DECLARED** — say the word, route to `fleet-claim review-hub`, and **leave the
     `.retiring` marker EMPTY**. Emptiness is the signal that the election is correct: a marker
     naming nobody elects, exactly as it always did.
   ⛔ **"A fresh hub is coming" is neither.** It reads as a handoff and designates nobody,
   and the resulting silence is the trigger for the fleet's most expensive failure: each
   peer reads "no hub", broadcasts, gets no ack because every peer is in that same state,
   and self-runs the SAME review with its own panel. One review, N panels. **A retiring hub
   that cannot get an ack declares the vacancy; it does not soften it.**
5. **STATE THE INBOX**, explicitly, one of two: the listener stays ARMED until the session
   closes, or this inbox is now POLL-ONLY. A `TaskStop` with neither leaves peers mailing a
   seat that will never answer — and their `mail-send` still prints a success ack, because
   delivery and readership are different facts and only the ack is visible to them.
6. **FORWARD, do not answer, once your loops are closed.** A
   retiring hub keeps receiving requests — peers read mail on their own cadence and a
   broadcast does not reach a session mid-wave. Forward each to the successor naming the
   SENDER and the SHAs, and add nothing else: **a forwarded request must reach the new hub
   as the requester's, not as yours.** Re-verdicting it yourself after standing down
   re-opens the split the handover just closed, and answering "I have retired" without
   forwarding strands work that was correctly sent to a hub that was still listed.
7. **TEARDOWN LAST**, and ⛔ **RELEASE THE CLAIM BEFORE THE MARKERS — THE ORDER IS THE
   WHOLE FIX.** In this exact sequence:
   1. `python3 scripts/session-manifest.py fleet-claim review-hub --release`
   2. `TaskStop` the listener — ⚠️ **ONLY IF you declared POLL-ONLY at step 5.** Step 5
      offers "the listener stays ARMED until the session closes" as its first option,
      and a `TaskStop` here makes that announcement false. Declared ARMED ⇒ skip this,
      remove the markers, leave it running. ⛔ **AND SAY THIS OUT LOUD IF YOU TAKE THAT
      BRANCH: 7.3 DELETES THE BASE MARKER, AND THE QUEUE-CLOSURE SCAN IS GATED ON IT**
      (`session-manifest.py`: `if not my or not os.path.exists(... review-hub-active-{my})`
      → `return []`). So an ARMED teardown leaves you RECEIVING requests with the one
      instrument built to catch a dropped one switched off — and it returns an empty list
      at the gate, never reaching the fail-loud branch its own docstring promises. Run
      `node scripts/review-request-closure-scan.mjs` BY HAND before closing, or forward
      per step 6. Keeping the base marker instead is worse: it re-lists you as LIVE.
      *(Measured 2026-09-06: a retiring hub kept
      it armed and received 16 further messages, including a question relayed by
      the successor. A spec-compliant unconditional `TaskStop` would have dropped all
      sixteen, and `mail-send` would still have printed a success ack to every sender —
      the failure step 5 exists to prevent, arriving through step 7 instead.)*
   3. `rm -f` the marker files (base, `.retiring` AND `review-hub-paused-<sid8>`; `rm` of the
      base does not touch the companions).

   ⛔ **WHY THE RELEASE COMES FIRST — AND THE REASON THIS PARAGRAPH GAVE UNTIL 2026-09-07
   WAS FALSE AT SOURCE.** It claimed release-after-`rm` is *unreleasable* because
   `_fleet_claim_holder_stood_down` needs the `.retiring` marker. That helper does need it,
   and **it is never consulted when a holder releases its OWN claim**:
   `session-manifest.py`'s release refusal reads
   `if my and f'session: {my}' not in existing and not args.force and not rel_down:` —
   `rel_down` is the **fourth** conjunct, reached only when the second is true, i.e. only when
   releasing SOMEBODY ELSE'S claim. A retiring hub holds its own. Measured in an
   isolated fixture: **both markers removed first, then `--release` → rc=0, claim gone**, with
   a peer-release control correctly refusing at rc=3 so the arm was not vacuous. The repo's own
   self-test asserts the same thing (`fleet-claim: owner releases its own claim` → 0).

   **The order is still right, for a reason worth more than the false one: it buys a correct
   DISCOVERY WINDOW.** Between step 7.1 and 7.3 a peer runs `hub-discover`, and the two orders
   say opposite things — measured, both windows:

   - **markers gone, claim still held** → *"… VACANCY (0 live hubs) — but review-hub
     is CLAIMED by `<sid>` … DELEGATE THERE; do not self-run"* — **the notice's own remedy
     defeating the notice**, and a peer sent to a seat that has stood down.
   - **claim released first, markers still present** → the hub renders `⏸ RETIRING — do NOT
     delegate`, then a clean **VACANCY → ELECTION** with the `fleet-claim` command.

   So: release-first is correct, the window is the payoff, and the original defect — retirement
   stamped `.retiring` but never released the fleet-claim — was one of **omission**: `--release`
   appeared **zero** times in this spec before the fix. **Adding the release is the fix; the order
   is the refinement.**

   ⚠️ **AND VERIFY THE RELEASE LANDED — `rc=0` DOES NOT MEAN RELEASED.** The release swallows an
   `os.remove` OSError and still prints `released` and returns 0 (measured against a
   read-only state dir: rc=0, success text, claim file still on disk, and `--check` then printing
   `⛔ CLAIMED`). Run `fleet-claim review-hub --check` after 7.3 and require *not claimed*, or a
   sid that is not yours. A `rc=2` identity-unresolvable exit strands it the same way.

   ⭐ **SAFE ON BOTH EXITS BY CONSTRUCTION, so it needs no conditional.** In a SUCCESSION
   the successor has already overwritten the claim, so the release is loudly REFUSED
   (rc=3, *"held by ANOTHER session"*) and nothing happens. It only takes effect on the
   VACANCY path — the one that needs it. Run it unconditionally and read the refusal as
   the success it is.

   Never at wrap-start: a wrapping hub is done-for-now, not deaf.

⚠️ **Steps 4 and 5 are the two that get skipped, and both fail SILENTLY** — a softened
handoff and an unannounced dead inbox each look like a completed retirement from the
retiring seat's side. Neither produces an error, and only a peer discovers the cost.

### Phase 1 — ARM the listener + STAMP the hub marker (first turn)
**MODEL AND EFFORT FIRST: the hub session runs Opus at effort HIGH, and its review agents inherit that.** The harness saves the model and, per model, the effort as the defaults a new session starts with (vendor docs, model-config: an interactive `/effort low`–`xhigh` is saved per model under `modelSettings`; `max` and an `s`-confirmed pick last the session only), so a hub whose first turn finds itself on Fable or at another effort asks the owner to type `/model opus` and THEN `/effort high` in its first-turn readout (in that order: `/effort` saves the level for the model in use, so typed on Fable it rewrites Fable's saved level and leaves Opus's alone), AFTER arming the listener below, and holds no review on the answer — panel agents are pinned `model: "opus"` either way (the lever is the owner's; ground truth is `.message.model` on the session jsonl for the model, never the `# Environment` line, and, for the effort a new session starts at, the level the settings resolve for that model — its `modelSettings` entry in the user settings, unless a project, local or managed settings file sets an `effortLevel` (that applies to every model and outranks the user file), all below `CLAUDE_CODE_EFFORT_LEVEL` or `--effort` — which the hub never opens (a top-level `effortLevel` is the older form and does not count for Opus 5.5, per the same page), then any `/effort` `local_command` record since). A hub already mid-queue on another model or effort states its measured model, and its effort as the `/effort` records show it (or "effort unmeasured" when there are none), once in its next readout, asks once, and keeps dispatching — nothing in flight is stopped, re-seated or killed.

### A lens never waits longer than 4 minutes in one call
**Why:** a lens's prompt cache lives 5 minutes. One Bash call that runs longer than that makes the lens re-buy its whole context on the next turn. Measured 2026-10-07 over this hub's 1,042 lens transcripts: 190 cold re-caches, 39.3M tokens. 96 of those followed the lens's OWN wait of 5 minutes or more, and 93 of the 96 used `timeout: 600000`. Of 117 calls of 5+ minutes, only 16 were the hook smoke suite; the rest were unit runs, mutation runs, open-ended wait loops and browser tests.
**Every lens brief carries these three lines, verbatim:**

> `No single Bash call over 240 s. Anything longer runs with run_in_background: true, writing to a scratch file that ends with its exit code (e.g. "cmd > f 2>&1; echo RC=$? >> f"); check that file in calls that each finish within 240 s.`
> `Never re-run a command that moved to the background, or one you backgrounded yourself — two runs in one folder corrupt each other without an error. Read its file instead.`
> `This overrides the 300000 ms / 600000 ms timeouts in bash-environment.md for this review seat; you never apply a migration to a shared database.`

**A hook lens adds a fourth:** `For a hook change run "bash scripts/smoke-test-hooks.sh --for <changed hook path>" (median about 9 s, up to about 140 s for a hook that selects the Results section; every section that names the file or its stem, plus the core set). Exit 0 certifies those sections only: a section that reaches the file through another hook, a script a hook runs, or a value another section sets is not run, so name the selection in your verdict and run the full suite in the background when the change touches shared state. It is never a pass for pushing; exit 2 = a term matched nothing or the file needs the full suite, exit 3 = the selection broke, so run the full suite in the background then.` (`--for` refuses shared hook libs, `settings.json`, `.githooks/*` and the suite itself under any spelling — a `scripts/` file a hook executes needs the full run too.)

⚠️ **This is a lens rule, not a migration rule.** A lens never applies a migration to a shared database (the throwaway Postgres `scripts/integration-test.sh` builds is its own, and the second line already forbids the re-run `migrations.md` guards against), so `migrations.md`'s keep-`timeout: 600000` advice (which holds an APPLY in the foreground) has nothing to protect here. ⚠️ **Not covered:** a wait the HUB itself does is paid at the main session's 1-hour cache, so it does not cost this. ## Checkpoint cadence — `/wrap --checkpoint` BEFORE accumulation forces a deep-pass
A long-lived hub accumulates review-process lessons + lens `Memory Update` blocks across its WHOLE life; an un-checkpointed hub that runs to 25h+ hits the `/wrap` **1b-DEEP** threshold (>1500 transcript lines) and must reconcile the entire pile at end-of-life — or lose it on a mid-life crash. So the hub SELF-FIRES a **`/wrap --checkpoint`** (session CONTINUES — frame it "Checkpoint complete — session still live", never "closed") when, SINCE THE LAST CHECKPOINT, EITHER **~6–8 delegations served** OR **~1500 transcript lines accumulated** (the SAME bound that fires 1b-DEEP — checkpoint BEFORE you'd need the deep-pass), whichever comes first. **Soft/warn cadence, not a hard gate** — the count is self-tracked; calibrate up (fewer interruptions) / down (more durability) as observed.
- **Why `/wrap --checkpoint`, not a bare `/meta learn`:** the checkpoint's own skip-gates auto-lighten it for a review-ONLY hub — no commits → the 7b/7c/7d tracker sweeps skip; no `src`/`tests` → the 5b/5c/5d unit/lint/i18n gates skip; no migrations → Step 6 skips. What RUNS each checkpoint is exactly the hub's yield: `/meta learn` (incremental lesson persist + lens `Memory Update` sweep — keeping current the orchestrator's duty to persist sub-agent MEMORY blocks), the corrections-registry sweep, `mail-check --peek`, and the Step-11 reconcile. ~1–2 min, not the full heavy wrap.
- **Benefits:** incremental lesson persistence (a crash loses only since-last-checkpoint) · each checkpoint's Step-1b scan window stays UNDER the 1500-line bound so the deep-pass never has to fire · a tractable end-of-life wrap · lens `Memory Update` blocks swept in BATCHES, not one 25h pile.
- **Evidence:** a ~25h hub ran ~15 reviews un-checkpointed → 24,604 transcript lines, 1b-DEEP fired, and every review-process lesson piled up to end-of-life; the cadence was adopted to prevent recurrence.

## Disciplines (the lessons that paid off in the founding session)
- **verify-before-relay** — every finding at file:line; a "this is broken" claim crosses to a peer only after you confirm it (caught a stale already-fixed finding + a false brief-premise + a self-buggy clean-check).
- **builder≠breaker** — fresh lenses; exclude wave authors.
- **severity-to-threat-model** — calibrate to the real blast radius; don't inflate a local owner-run tool to P0 (a doc/script review's "bug" class is false-claim / contradiction / mis-cite, not a code defect).
- **reconcile cross-lens severity** — the orchestrator's job is to resolve disagreeing lenses, not relay the max.
- **append the log simply** — don't carve hunks or chase phantom-dirty on an append-only shared log.
- **the peer/hub lens advantage** — a delegate reviewer sees cross-session working-tree state (`whose-edit`, live `git diff`) that an in-session panel structurally cannot (a delegate review once caught a partner's transient mid-review mutation).
- **cross-lens AGREEMENT is not ground truth (2026-07-20)** — two FRESH lenses can share an enumeration blind spot, so N agreeing lenses ≠ N independent confirmations. Resolve a COMPLETENESS/ABSENCE claim ("no test guards X" / "deleting Y ships all green") at ground truth — the tier the code actually gates (unit + integration + e2e globs), never at cross-lens agreement. Evidence: in one review, my front-load AND one lens both ruled the Stage-2e wiring "deletable-green" (both enumerated only the UNIT tier); the 3rd lens + a file:line check found the integration coord-overlay test guards it. The DISAGREEING lens was the signal; the agreeing pair was the trap.
- **`--code` coherence is BLIND to prompt attention-priming (2026-07-20)** — a review pass over a prompt fence / negative instruction cannot see whether NAMING the forbidden pattern INDUCES it. Clear the STRUCTURAL questions; mark every behavioral-prompt claim EVAL-DEFER and never coherence-clear it into deploy — the empirical "does it induce" is the eval-gate's to answer. Evidence: the v2.17 arc (round-1 coherence-clearance was empirically contradicted by the eval's 3/3 forbidden-prose confab).
- **read the ACTUAL pixels for an image / legal-image call (2026-07-20)** — a text-only review of "a construction diagram" waves through a photoreal-face EU-AI-Act-Art.50 disclosure gap; Read the raster and rule from the pixels, not the alt/comment describing them (factual-claim verification). Evidence: a lesson page once served a photoreal AI face undisclosed under a "stylized illustration" label; only reading the image file caught it.
- **verify a peer's OWN state-claim before it goes load-bearing (2026-07-20)** — a delegator's claim that a red test is external to its diffs, or that the owner ruled for a particular fix, is a self-asserted snapshot, unverified until checked against git / ground truth. Confirm before relaying or acting. Evidence: one peer's external-red claim (verified TRUE via `git show` name-only) + another peer's relayed owner ruling (flagged as relay, not direct owner speech — immaterial to the code-correct CLEAR, but named).

## ⛔ RUN IT BEFORE YOU READ IT — I trace whether the code is RIGHT and never check whether it RUNS (2026-08-10, self-diagnosed; homed 2026-08-12 per a routing note)

**Verbatim, because the naming is the useful part: *"THE GAP IS METHODOLOGICAL AND I CAN NAME IT EXACTLY: I trace whether the code is RIGHT and never check whether it RUNS."*** A `--code` review reads for logic — the branch is correct, the predicate discriminates, the guard is live — and never asks the prior question: does this file execute at all? Two `ReferenceError`s on unbound identifiers survived BOTH my verdict AND a fresh-context breaker, because neither of us ran anything; they died only when an in-process `no-undef` arm landed.

**Rule: on any `--code` whose scope includes `.mjs` / `.sh` / any interpreted script, RUN it — or at minimum lint it for unbound identifiers — BEFORE reading it for correctness.** Reading-for-logic is what a reviewer is good at and it is downstream of a question a two-second lint answers. An unbound identifier is invisible to every careful read and fatal at first execution.

## ⛔ A REMEDY IS A HYPOTHESIS — mark it as one IN the verdict, at the hub's writing surface

`behavioral-anti-patterns.md` #9 codifies the split; what belongs HERE is the verdict CONVENTION that follows from it. **A finding reads a system that exists; a remedy predicts a system that does not.** Finding a defect inspects what is there — that is where the review's authority comes from. Proposing a fix predicts the behaviour of code nobody has written, from LESS system knowledge than the author has.

The verdict format grants both the same authority, which is the trap. **So say which is which:** findings assert, remedies are labelled UNTESTED HYPOTHESIS. Measured cost of not doing it — two proposed fixes shipped as peers of their findings, both worse than what the author had, one a harm INVERSION; both planks conceded at `file:line` once challenged. A conceded plank is a healthy outcome, not a conflict — but only if the verdict flagged it as a prediction in the first place.

## ⛔ A DELEGATOR'S MUTATION EVIDENCE CANNOT SEE A SHARED FALSE PREMISE — the strongest verification in this repo is powerless against a wrong belief (2026-08-12, a peer's finding, and it is theirs)

The hub routinely accepts a fold on mutation evidence: arm counts moving by exactly the arms added, single-arm attribution, inverse restores content-keyed both halves. **All of that is intact and was completely powerless here**, in their words: *"I pinned 'a pure-digit token is NOT a sha' with a mutation-pair, and it PASSED. It passed because the arm and the predicate under it were built from the same wrong belief. An assertion and a guard that share a mistaken premise agree with each other forever — the mutation is evaluated by the same belief that produced the error, so it cannot dissent."*

**The discipline measures whether an assertion RUNS and whether it DISCRIMINATES. It never asks whether it is TRUE.** Measured instance: a sha-shape predicate requiring a hex letter, pinned by a passing mutation pair, false-negating on 1.60% of all commits (80/5000 sampled; theory `(10/16)^9` = 1.46%) — including the very commit cited as its motivating example.

**What breaks the tie is an instrument OUTSIDE the belief**, and it is usually cheap: here, resolving candidate tokens through `git cat-file -t` instead of a charset test. **Check, when a fold arrives citing mutation evidence: what would this arm assert if the author's premise were wrong? If the answer is "the same thing", the mutation proves liveness and nothing about correctness — go find a ground-truth oracle.** Fixture REALISM is the aggravating factor, not a defence: a realistic sha has letters, so a letter-requiring bug is invisible to a realistic corpus. **The discriminating fixture is the ugly one.**

## ⛔ SHIPPING AN UNRECONCILED TENSION — a lens report that contradicts ITSELF, relayed with both halves intact and the conflict unflagged (2026-08-06, occurrence 2 in one session)

A hub's job is to resolve a report before it becomes a verdict. The failure mode is not dropping half of it (that is synthesis-dropout) and not characterising it wrongly (that is a separate failure — in both measured cases the hub's HEADLINE was CORRECT). It is **passing along two sentences from ONE report that cannot both be read naively, without naming that they need reconciling** — and letting the headline carry the weight while the raw halves ship underneath it.

**Both measured occurrences, ~3.5h apart, different reviews and different peers — independent threads, so this is occurrence 2 under the co-thread rule, not one incident counted twice:**
- A lens reported a mechanism note AND, separately, that the landmark the mechanism depends on **no longer exists**. The hub relayed the first without reconciling it against the second. *The refutation was inside the report it was synthesizing from.*
- A partition lens wrote *"Exactly 1 is a genuine present-state defect"* and, four paragraphs later, *"Net effect: none … the extended-field sweep adds ZERO genuine instances."* Both shipped. The delegator did the obvious thing — added them — and committed an inflated numerator to a file header.

**Why it is worse than relaying the wrong half:** a wrong half is one claim a reader can check. An unreconciled pair **looks complete**, so the downstream reader resolves it by the obvious operation and inherits an error neither party stated.

**The check, at compose time:** when two claims in one report bear on the same quantity, either reconcile them in the relay or SAY they are unreconciled. If you resolved the tension silently to write the headline, that resolution is the thing the recipient most needs and the thing you are least likely to include.

**Companion, from the same exchange — THE PEER'S HALF, named by them:** adding counts from two instruments without establishing the counted SETS ARE DISJOINT. The remedy that settled it is worth copying: a **pre-registered two-branch discriminator** — one query, both outcomes stated in advance with their consequences — handed to whichever party can actually run it.

**And verify your own CONFESSION.** The hub's first self-blame here named the wrong class ("I forwarded the reading that fit my summary"); grepping its own sent verdict showed it had forwarded BOTH and gotten the headline right. **The confessed class is what gets codified**, so an unverified over-confession mints the wrong lesson — Anti-pattern #1's accepting side applies to your own admissions, not only to a peer's correction.

## ⛔ A BRIEF'S PREMISES ABOUT THE **AUTHOR** ARE PANEL INPUTS TOO — and only the premises about the CODE ever get verified

When you compose a re-run or verdict-attack brief, you characterise not just the diff but the
person who wrote it — *"they conceded without checking"*, *"they folded on one reviewer's say-so"*,
*"this was rushed"*. **Those sentences enter the panel with exactly the same status as a claim
about the code, and nothing in the pipeline grounds them.** A breaker sent at *"they folded on
one reviewer's say-so"* attacks a strawman, and whatever it concludes **launders that premise back
out as a finding** — now wearing the panel's authority.

Measured 2026-07-30: a re-run brief told the architect breaker that three findings
had been *"ALL CONCEDED WITHOUT A CHECK."* False — three of the four legs had been verified at
source (a comparison record, an independent runtime-registry corroboration) and
only one was accepted on reasoning. The reviewee intercepted before the panel converged.

**Rule:** before sending, separate the brief's claims about the DIFF from its claims about the
AUTHOR'S PROCESS, and either cite the second kind at `file:line` / a quoted mail, or delete it. The
breaker needs the diff and the question — it does not need your read of how carefully the author
worked, and supplying that read is how a wrong one becomes evidence. Kin: the strawman-check
for a brief that mis-frames the *user's* proposal, and the rule against a gauntlet laundering an
untraced premise; neither covers a peer REVIEWEE's verification process, which is the axis nobody grounds.

## ⛔ THE HUB REVIEWS EVERYONE AND NOBODY REVIEWS THE HUB — route one of your OWN verdicts per checkpoint (2026-08-06)

⛔ **AND THAT ROUTED SELF-REVIEW RUNS HOST-COMMITS-FIRST, EXACTLY LIKE ANY OTHER PANEL.** The full ordering is `expert-review/SKILL.md` § Process 4b; it binds here because this path is the one where skipping it is invisible — **you are both the host and the author of the thing under review, so your position is already written and the temptation is to send it along as the brief.** Do not: commit your verdict-about-your-own-verdict under a timestamped `## Host position` block in your SESSION PLAN FIRST (no brief points the breaker at that file for reading; the brief names it by path as do-not-open and excluded from every search — `expert-review/SKILL.md` § Process 4b (a)-(b); this said "the checkpoint log" until 2026-09-26, a name nothing here defines and one a reader can resolve to a shared state checkpoint file), dispatch the breaker with the artifact and the question ONLY, and when you report, name the strongest argument against yourself that came back and say plainly whether it moved you. **An unchanged position reported silently is exactly the shape this whole section exists to prevent** — the hub agreeing with the hub, with a review-shaped receipt attached.

Every other seat in the fleet has a breaker: it ships a diff, the hub attacks it. **The hub ships
verdicts and nothing attacks those.** That is not a gap in coverage, it is the fleet's single
largest unreviewed surface, and it sits on the seat whose entire job is **asserting that other
people are wrong** — which the forensic pass measured as the highest-risk assertion shape there is.

**An existing rule already binds this and was never applied here.** A hub verdict is self-referential (it
evaluates work under the hub's own frame), evaluative (that is what a verdict is), and
codification-bound (peers fold it into commits). All three conditions hold, so the rule's own
conclusion applies: it needs a **fresh context with a refute mandate**. Lens count does not
substitute — N lenses composed by the same orchestrator, over the same brief, share the frame.

**What a retired hub's own root-cause record shows** (104 classified errors):
- **5 of 16 outbound broadcasts were retractions, and every one was an act of correcting a peer.**
  None was self-caught.
- **One slice's five errors all had a correctly-executed instrument in hand** — right output, wrong
  characterisation on top. Instrument density does not protect a verdict; another slice's
  window ran `git show` ×156 and still shipped two.
- A verdict shipped with two lenses APPROVED that a third lens later broke, on a mismatch
  neither of the first two had caught.

**Procedure — ride the checkpoint you already fire (§Checkpoint cadence), do not add a new one.**
At each `/wrap --checkpoint`, pick ONE verdict served since the last checkpoint — prefer one that
CONTRADICTED a peer, since that is the measured risk concentration — and route it to a
fresh-context agent with a refute mandate: *"here is the diff and here is the verdict I sent;
find where the verdict is wrong."* Give it the artifact and the verdict, **not** your reasoning
about the peer's process (§ the brief-premises rule above). Fold what survives; mail the peer a
correction if the breaker overturns a plank you sent them. One agent, one verdict, per checkpoint.

**Do NOT** substitute a self-re-read, a second lens from the same panel, or the delegator's
agreement — the delegator accepted the verdict, which makes them the least independent reader
available.

  commits sat unreviewed, surfacing only after three pings in one session.
- "Say the word and I'll take the rest" is a defer. The word was said at delegation.
- ⛔ **AND THE COMMITS-NOT-MAIL RULE ABOVE HAS ITS OWN BLIND SPOT — IT CANNOT SEE A REQUEST YOU NEVER OPENED (measured 2026-08-06, TWO hubs in one handoff, same direction).** That rule exists to stop a real failure (reading "0 unanswered mails" as an empty queue) and in fixing it points AWAY from the mail store — but a delegation that was never read has no declared range to subtract from, so a commits-only derivation is structurally blind to it. **A queue derivation must ENUMERATE THE STORE'S INBOUND *and* reconcile the commit range. Neither alone is sufficient.**
  **Both seats failed it and both named it better than the rule did.** The retiring hub certified *"UNREVIEWED QUEUE: EMPTY. Explicitly, and derived… from the mail store this turn, not from recall"* — and its own account of what it actually ran: *"I grepped for the SHAs of the waves I remembered serving, and for deploy-clear tokens. I never enumerated the store's INBOUND. So the derivation confirmed what I already believed and could not surface what I had never seen."* Its one-liner is the rule: **a queue derivation must LIST INBOUND, not VERIFY OUTBOUND — mine did the second and called it the first.** A peer sharpened the general form: **"derived, not recalled" bounds the SOURCE and says nothing about the SET — both halves need naming: derived from WHAT, enumerating WHICH population.**
  **Cost, measured:** a 4-commit wave carrying a serious finding stranded on the retiring hub (never opened, omitted from a handoff that named two other peers), then stranded again on the successor, which had the self-contained resend in its own store and reported a clear queue four times. A direct question about pending reviews is what surfaced it; one read of the mail store answered it.
  **⚠️ AND BOUNDING YOUR RECALL HONESTLY IS WHAT MAKES THE SENTENCE FEEL SAFE.** The retiring hub disclosed three compactions and correctly refused to trust its memory. That disclosure is good practice and it did not help: the substitute instrument was shaped by the same blind spot. Naming a source as untrustworthy does not validate whatever you reach for instead.
  ⛔ **AND THE INBOUND ENUMERATION IS ITSELF WINDOW-BOUNDED — THE STORE PRUNES, SO IT IS NOT AN ARCHIVE (verified at source 2026-08-06, `scripts/session-manifest.py:104` `MAIL_READ_TTL_HOURS = 24` · `:107` `MAIL_UNREAD_TTL_HOURS = 72`).** A peer bounded this sweep within minutes of it going out, and the evidence is decisive: mail from that seat to the retired hub currently in the store = **0**, while verdicts it holds FROM that hub = **5**. Both cannot be true of a complete store — the requests existed and were pruned.
  **The direction is the cruel part: the failure mode you are hunting has the SHORTER TTL.** A stranded-and-never-read request survives 72h and then becomes ABSENT — indistinguishable from never-sent. A request that was READ and never answered is gone at **24h**. So a store sweep reaches ~24h for the read-not-answered shape, not the ~4h of whatever incident prompted it, and a clean enumeration past that window means nothing at all.
  **So the BROADCAST is the primary instrument and the enumeration is the secondary one** — only the SENDER still knows what they asked for, and their transcript outlives the store. Ask; enumerate only to seed the ask. Stating a clean enumeration as though it bounded the queue is the same defect one level up: an instrument that is incomplete not by a missed file but by a DELETED one.

  **Disposition is the SENDER'S to give, never yours to infer:** unread-on-disk is NOT unhandled (one unread item here had a full 5-lens verdict sent). When the store cannot answer, broadcast a claim-or-disclaim and let each seat classify its own outbound — that sweep returned 8-of-9 handled plus the one real loss, in two replies.
- **Re-derive the range at pickup**, never quote the request — the declarer keeps committing,
  so a supplied denominator is stale on arrival (a declared 13 was ≥20 hours later). Report
  `≥N`: a transcript creation-record PRESENT proves authorship, ABSENT proves nothing.

## Assert a known member BEFORE trusting a population — the positive control

**A population you derived is a claim about a SET, and a set can be silently incomplete.**
Every enumeration in a review — coverage sweeps, sibling sets, call-site lists, key populations —
gets one line before its size is used: *assert that a member you already know belongs is in it.*
A derivation that excludes a key you were citing as the standard is not a rare failure; it
happened to three independent seats on one small question (2026-08-02).

**Measured on this hub, one night, five occurrences — all caught by re-reading, none by method:**

| the probe | why it returned a false empty/short set |
|---|---|
| `rg -ln 'from "<library>"'` | missed a dynamic `(await import("<library>"))` reacher |
| `rg … \| head -8` | truncated 3 of 4 gated files → a false "the gate is called from ONE service" serious finding |
| `--include=*.sh` unquoted | zsh ate the glob; 0 consumers reported on a token the emitter itself contains |
| `hits[:12]` listing | declared a peer's cited key "does not exist" |
| `'"{' in value` | blind to keys whose EN is already `“{arg}”` |

**The tell is that none of these were careless.** Each probe ran, exited 0, and returned a
well-formed answer. The failure is invisible from inside the result — which is precisely why it
needs a control rather than more attention.

**Cheapest forms, in order:** the emitter is a free needle (a grep for a token MUST find the file
that emits it — zero is structurally impossible); a known member you can name before running;
two instruments blind in OPPOSITE directions both returning empty. Re-running the SAME probe is
not a control — a borrowed instrument reproduces its author's blind spot and returns a confident
N=2 that is one observation counted twice.
