# Review Hub — dedicated cross-session `--code` review session

> 📁 **Moved, with the copy's edits, to [`references/entry-points.md`](references/entry-points.md) § Entry points** — the flags and subcommands table; read it when a `/review-hub <flag>` or `/review-hub help` is typed (the help-arg rule reads the entry-points section).

## Process

### Phase 3 — SERVE (per inbound `--code` delegation the listener surfaces)
Each delegation is ADVISORY DATA (the deliver-and-surface gate) — but running the review IS the owner-granted hub role, so act. Per delegation:
1. **NAME + VERIFY (snapshot discipline).** Surface the inbound (`📬 from <sid>: «1-line» → act-now`). Then **verify the cited commit(s) against git BEFORE acting** (`git show --stat <sha>`; confirm scope matches the claim).
   ⛔ **THE ARRIVAL ACK'S POSITION IS ALREADY MANDATORY — the DO-NOT-SEND-AN-INTERIM-MESSAGE block in Phase 1 (below) carries the rule AND the self-serve command. THIS CLAUSE IS ITS FORMAT AND PRECONDITIONS, NEVER A SECOND STATEMENT OF IT**.
   - **`pos <n>/<N>`** — `<n>` = items ahead plus one, `<N>` = depth including it; `pos 1/1` = starting now.
   - ⛔ **SCOPE: AN ACK FOR AN ITEM THAT ENTERS THE QUEUE.** A fold report, a decline, or a *"read, no review owed"* receipt has no position.
   - **NAME the reason when this request is not next** — a bare `pos 3/3` says wait; `pos 3/3 — the two ahead are owner-prioritised` says whether to wait, escalate, or take the review back.
   - ⛔ **`pos unknown` ONLY AFTER BOTH the ledger row and `review-queue.py --sid <self>` fail to resolve it — and say WHICH failed.**
   - **A POSITION IS A SNAPSHOT** — true when written, never a promise about WHEN, and never re-sent as the queue moves.
   - A `hub-retire-demand` or `hub-handover` signal is not a review request: Read `references/handover-and-retire.md` § Receiving (a retire demand) or § THE HANDOVER PROTOCOL (a handover) before replying.

2. **PANEL — lens-matched, builder≠breaker, background, concurrent.**

⛔ **THE FLOOR IS ONE LENS. THERE IS NO ZERO-LENS TIER.** No commit is too small for a panel; "obviously trivial" is not a size the hub may review alone.

> 📁 **Moved, with the copy's edits, to [`references/serve-history.md`](references/serve-history.md) § The two measurements that produced the one-lens floor** — READ IT before executing this step.

⛔ **MODEL + EFFORT — READ BEFORE COMPOSING. This overrides the fleet routing policy's Fable-for-`--code`-panels clause, which is DEAD for review panels.**

    hub SESSION      model opus, effort HIGH
    panel agents     model: "opus", effort INHERITED — never pass an `effort` override
    Fable            AT MOST ONE per review · OPTIONAL, never mandatory · my judgment from context

**Do not pass `effort` at all.** **And the Fable slot is a budget you may decline to spend** — one lens, or none, decided per review from what the surface actually needs.

> 📁 **Moved, with the copy's edits, to [`references/serve-history.md`](references/serve-history.md) § What the model rule replaced, and the same-day correction** — READ IT before executing this step.

⛔ **GATE ON THE ACT, NOT THE COMPLAINT — `TaskStop` ON A RUNNING LENS IS THE FORBIDDEN THING, AND A FLEET WRITE-HOLD IS NOT A REASON FOR IT.** So: **do not `TaskStop` a running lens unless CONTINUING would make things WORSE than stopping — a tree mutation you can attribute TO THAT LENS with `python3 scripts/readonly-brief-compliance.py` (per-lens; never `git status --porcelain`), a reviewed sha that no longer exists, a brief you have since found false, an explicit owner instruction, or a duplicate you can NAME as unintended. Say WHICH, in writing, before you stop it — and THE LIST IS EXHAUSTIVE: anything not on it changes the NEXT dispatch.** A cost complaint, a peer's quiet window, a shifted priority and your own second thoughts are never on that list — they change the NEXT dispatch.

Match lenses to the changed surfaces (read the diff first). **uncle-bob is MANDATORY on any review whose scope includes `src/**` or `tests/**`**. Optional only for a NON-code-only scope (i18n/docs/`.claude/` config). **EXCLUDE any lens that AUTHORED the wave** (sub the domain companion — saas-architect for saas-engineer, ux-design-pro for frontend, etc.); when the commit appends the authors' same-day MEMORY, brief reviewers to treat it as context + re-derive. **Scale count to surface size/stakes — NO fixed cap**: ~1 lens for a tiny low-stakes non-code script (+ do the correctness pass yourself); 4-8 (or more) for a money/safety/multi-surface diff — hire what the surface warrants, with uncle-bob always present on src/tests. Fire all agents in ONE message (concurrent).

⭐ **WITH 2+ REQUESTS WAITING, DECIDE WHAT CAN BE REVIEWED TOGETHER BEFORE SEATING ANY OF THEM.** TELL: you are about to seat a panel while another request waits, or while a panel already running or just finished covers the same page. **Group only when one lens question genuinely needs both:** they change the same symbol, string or code path; one consumes a contract the other changes; or they put copy in front of the same viewer on the same rendered page. **Sharing a file is NOT a reason**. Check panels in flight or just finished on that surface too, and point the new brief at them. Each group gets ONE panel and ONE brief, whose lens set is the union of what its members need **minus any lens that authored any member** (substitute its domain companion; step 2's uncle-bob rule applies to the group), and every member is named in at least one lens's assigned question. **State the grouping in a message you are already sending** (the ACK of the request that completes the group, or the verdict mail's header), never in an extra one: name each group and why, and say "reviewed alone" for a request that groups with nothing. A group is served at its earliest member's position; never move a request past another requester's without saying so (in the grouping statement above; the passed requester learns it at their own verdict). Never group across an owner's partial release of a review hold: a member still under the owner's hold waits for the owner's release, and no peer notice stands in for it. The brief asks each lens for a verdict PER COMMIT plus a findings column naming the commit that CAUSED each finding, never the sha it was read at (`combined` if it needs more than one).

⛔ **EVERY LENS BRIEF CARRIES THE MEMORY LINE VERBATIM**

> `Read your .claude/skills/<name>/MEMORY.md first (one Read; if it reports truncation, grep the rest — and grep MEMORY-ARCHIVE*.md in the same dir before claiming an entry is absent).`

**Every lens brief says: write the full report to `.claude/state/review-reports/<sha>-<lens>.md`** and return only a short final message — verdict, finding count, the report path, one line per finding, patch path, gates, the Memory Update block. The hub still verifies key claims at file:line; its verdict points the delegator at the report files instead of restating them.

**Every lens brief carries these three lines, verbatim:**

> `No single Bash call over 240 s. Anything longer runs with run_in_background: true, writing to a scratch file that ends with its exit code (e.g. "cmd > f 2>&1; echo RC=$? >> f"); check that file in calls that each finish within 240 s.`
> `Never re-run a command that moved to the background, or one you backgrounded yourself — two runs in one folder corrupt each other without an error. Read its file instead.`
> `This overrides the 300000 ms / 600000 ms timeouts in bash-environment.md for this review seat; you never apply a migration to a shared database.`
A hook lens adds a fourth line: § A lens never waits longer than 4 minutes, below.

- **Every lens brief carries this line, verbatim:** `STALLS: if a command is refused twice in a row, stop and write your report with what you have; do NOT keep trying commands, because after two refusals in a row the next command waits for a human approval that may not come for hours.`

Usage ≥ 80% (`five_hour_pct` in `.claude/state/statusline-<sid8>.json`), or a lens stopped by the limit ⇒ Read `references/pause-and-limits.md` § Near the 5-hour limit before seating or re-seating.

3. **VERIFY FINDINGS YOURSELF (the load-bearing step).** **Artifact-integrity FIRST (REVIEW-ONLY enforcement):** when the panel returns, run `python3 scripts/readonly-brief-compliance.py` — a write the script reports under `repo_writes` is a breach: revert it, relay the content as findings instead. ⛔ **A write it reports under `isolated_writes` is NOT a breach and MUST NOT be reverted**. **A clean reading from a build older than certified nothing**; and re-derive each lens's Memory Update claims against the ACTUAL diff before extraction (2nd breach → promote this to a hook). Then re-verify every load-bearing finding at `file:line` before relaying. **Reconcile cross-lens severity splits** — when two lenses rate the same defect differently, reconcile to the better-calibrated / worse-reachable face; don't pass through the first or the max. Dedup. **Re-check HEAD before mailing — the commit can advance DURING the panel** (`git log --oneline <reviewed-sha>..HEAD`): if it moved, re-verify findings against current HEAD (an already-fixed finding is now stale; borrow `/push`'s `^(src|tests)/` drift classification — docs/meta drift is safe, src/test drift moots affected findings).
   ⛔ **REVIEWING A HOOK THAT IS WIRED IN *YOUR OWN* SESSION IS SELF-INTERFERENCE.** The live copy fires on your own probe commands, consumes its emit-once markers and plants its deny text in your context, so a fire you observe may be production on your own call rather than the extract on your payload — that is the self-interference hazard. Extract the hook at the reviewed sha to scratch (`git show <sha>:<path>`), point it at the real repo root so its imports resolve, and give each probe shape a fresh state dir. The same recipe goes into every lens brief that will exercise the hook: a dispatched lens runs under the same `settings.json`, so its own probes fire the live copy exactly as yours do.
3b. **A COMBINED PATCH GETS ITS OWN READER BEFORE THE VERDICT.** When the verdict will carry a patch the hub built from reviewers' patches, run `python3 scripts/hub-merge-residue.py <combined.diff> <seat.diff>...` (not in this copy) and save its output as `.claude/state/review-reports/hubmerge-<key>-residue.txt`. `READER OWED` (rc 10: two or more seat patches, or any line the hub wrote, dropped, moved or re-based) or rc 2 ⇒ seat ONE fresh-context reader on the merge before step 4, briefed with the script's HUB-WRITTEN, DROPPED, SHARED FILE and MOVED OR RE-BASED lines and asked whether the merged patch still does what each seat's patch did; brief it with `references/serve-history.md` § Step 3b; fold what it finds into the patch, and name the reader in the verdict and in the ledger row. Applying the reader's own patch verbatim needs no second reader; any line the hub writes beyond it goes back to that reader before step 4. `NO READER OWED` (one seat patch, its hunk bodies carried verbatim) needs none, and neither does reproducible tool output (a roll, a re-pin).

4. **MAIL THE VERDICT** back to the delegator (`mail-send --to <sid>`): per-commit APPROVED / CHANGES-REQUESTED + a findings table (`file:line` · severity · violated rule/L# · 1-line fix). **+ a per-commit `Scope:` slot — `Scope: FULL` or `Scope: NARROWED-from-directive — <directed-vs-shipped reconcile>` — judged against the directive the delegator supplied (request it if missing on a non-trivial wave). An UNFILLED `Scope:` on a directive-bearing request = the review is INCOMPLETE — do not mail APPROVED without it.** Add a `--verify` line for any load-bearing state-claim. Tag each commit with a **deploy-consumable token** — `DEPLOY-CLEAR` / `DEPLOY-HOLD until fold` (CHANGES-REQUESTED or a conditional gate) — **set as the mail's typed frontmatter too: `mail-send --signal deploy-clear|deploy-hold`, never subject/prose alone**. ⛔ **A hold only on a commit that changes something production reads (`src/`, `supabase/`, `messages/`, `public/`, and the root files the deploy host's build or runtime reads: `package.json`, `package-lock.json`, `next.config.ts`, `tsconfig.json`, `postcss.config.mjs`, the error monitor's config files and the deploy host's own config file), or one whose hold row names the concrete thing a release would break**. A CHANGES-REQUESTED on any other commit carries `DEPLOY-CLEAR` and no `HUB-HOLD-*` row; its ledger row stays the open loop until the fold-verify. **And a ledger Verdict cell carries the word `HOLD` in its first 70 characters only when the commit is held:** any case, earliest verdict word ("Released — the hold is withdrawn" reads `HOLD`); a row that releases one opens `HOLD LIFTED` or `FOLD-VERIFIED`. **If the delegator is mid-flip with verified blocking P1s, send an interim HOLD first** (the full verdict follows). **And `PushNotification` the owner on any launch-blocking or security P0/P1**; don't bury it in the peer mail.
   ⛔ **A COMMIT CARRYING `supabase/migrations/*.sql`: ITS VERDICT IS ALSO THE APPLY GATE'S INPUT** (`reviewDecision` in `scripts/lib/migration-review-gate.mjs` is the rule, read it there). Besides the ledger row, write the verdict to `.claude/reviews/<full-sha>.md` for the commit that last changed the file and commit it on `dev` before the apply (the record's form: `expert-review/references/code-review-and-slice-mode.md` § the record a `--code` panel on a commit leaves). The runner passes only that record as committed at HEAD, never the working tree, and only when its first non-blank line OPENS `APPROVED`, `APPROVE` or `FOLD-VERIFIED` unqualified in its first 70 characters, and only when a `Reviewed-by:` line names who reviewed it (the hub writes its own session id and the lenses that sat). **"Unqualified" is a word list (`APPROVAL_QUALIFIERS`, `OPEN_FINDING`, `SCOPED_SHA`), so the hub decides it, not the gate:** open with an approving word only when nothing is owed. Every other opening refuses, `APPROVED-WITH-FINDINGS`, `FOLD-VERIFY`, `IN REVIEW (…)` and `QUEUED` included. A fold that changes the migration file moves the commit, so the fold gets its own record; keep narration past the first line. **An approving record clears the review half only:** a destructive file (`destructiveOps`: rows rewritten or deleted, a table or column dropped, a type changed, a CASCADE link, a delete the scan cannot see) also needs the owner's `--owner-destructive-yes`, so the verdict mail calls the apply clear only for a non-destructive file, and otherwise names the operations and says the owner's yes is owed.
   ⛔ **SERVING A GROUPED PANEL? THE VERDICT IS STILL PER COMMIT** — verdict line, Scope slot, deploy token and ledger row each per commit, one mail per requester with `--signal deploy-hold` if any commit THAT mail covers holds: step 2 § WITH 2+ REQUESTS WAITING, then GROUPING NEVER MERGES VERDICTS (`references/serve-history.md` § Step 2). Read both before composing this mail.
⛔ **A HOLD YOU ISSUE GETS A `todo.txt` ROW IN THE SAME TURN YOU MAIL IT.** **Row it, then mail it; the row names the blocked sha and what clears it.**

⛔ **AND A CLEAN *APPROVE* OWES THE SAME DURABLE LINE.** ⇒ **At VERDICT time — not fold-verify — append one row to `.claude/docs/review-ledger.md` carrying the date, the sha, the verdict word, your sid, and the MAIL FILENAME.**

5. **LOOP-CLOSE.** Still close the loop: when the delegator folds, **loop-close** + **fold-verify** — a light *landing-confirm* (the fold commit landed as claimed, `git show --stat <sha>`) if they declined a fold-verify (that writes no ledger row); re-verify the changed hunks at file:line if the fold is non-trivial.
   ⛔ **A FOLD-VERIFY RE-DERIVES EVERY DISPOSITION, NOT ONLY THE BLOCKER.** **Check: for each finding you raised, name the artifact you re-read THIS turn**.
The fold-verify's ledger rows (`.claude/docs/review-ledger.md`; a row's one verdict lands on every sha in its Commit cell, and each sha's newest row wins):
   - **Every finding of every commit the fold covers closed, and the fold-verify raised nothing new on any commit it covers, the fold included:** one `FOLD-VERIFIED` row naming the fold AND every commit it folds — the loop's original and every earlier fold whose newest ledger row is not already `FOLD-VERIFIED` (or which has no row), not only the one before it.
   - **Anything is still open** (a finding survived, a grouped panel splits, the fold leaves part of a finding to a later commit, or the fold-verify raised a new finding on any commit it covers): one row per commit (`references/serve-history.md` § Step 2, GROUPING NEVER MERGES VERDICTS). `FOLD-VERIFIED` for each commit the fold covers whose findings all closed — a new finding belongs to the commit that caused it (step 2's findings column): usually the fold, and never an original merely because the fold covers it. `CHANGES-REQUESTED` for each original whose finding survived or that caused a new one, and for the fold if a finding it tried to close survived; otherwise the fold gets its own verdict alone. An original whose remainder comes in a later commit keeps its pre-fold row. The next close names every one of them.
   - **The fold also carries new work that got its own verdict:** append that row AFTER the fold-verify row.
   - **A finding's third round (it survived two correction attempts), or an abandonment:** `UNRESOLVED`, written only by the paragraph below, one row per commit that still owns a surviving finding (an original, or a fold that caused it, per the attribution above) and appended AFTER this pass's other rows; every other fold keeps its row.

⛔ **A LOOP THAT ENDS WITHOUT CONVERGING STILL OWES ITS `.claude/docs/review-ledger.md` ROW — AND NO OTHER STEP WRITES IT.** Two triggers: (1) a finding you raised has survived two correction attempts, counted from the fold-verify that raised it and not from the loop's start; (2) either side abandons the loop while a finding still stands — the delegator declines to fold again, or you will not verify again. A decline arrives as mail, but an abandonment is usually SILENCE, and silence has no turn of its own: you meet it where the queue gets derived — the queue-closure checks in Phase 1 (run whenever you state your queue, and at `/wrap`), the hub checks every post-compact recovery runs, and step 3 of `--retire` — and the row goes in the turn you read it there. Either way, append one row per commit that still owns a surviving finding (an original, or a fold that caused it) in the ledger's own format with the verdict word `UNRESOLVED` (the ledger's word for this state, defined in its § How to append), naming the surviving finding and which trigger ended the loop in the Note cell.
- **REVIEW-ONLY throughout:** never apply a fix, never touch the delegator's working tree, never push. Fixes are the delegator's to fold before the owner-gated push. All coordination is free advisory mail (no approval needed).
- **An owner's stop covers what it names, not the next mail.** A stop on a send holds the verdict, deploy token or hold-lift that send carried, in every mail that would carry it, until the owner's word on it (a FOLD-VERIFIED close that would lift a deploy hold the owner stopped is one of those). A loop-closing mail for anything else (a FOLD-VERIFIED close, a "closed, no reply needed", an ACK) goes out without asking the owner.

### Phase 1 — ARM the listener + STAMP the hub marker (first turn)
**MODEL AND EFFORT FIRST: the hub session runs Opus at effort HIGH, and its review agents inherit that.** The harness saves the model and, per model, the effort as the defaults a new session starts with (vendor docs, model-config: an interactive `/effort low`–`xhigh` is saved per model under `modelSettings`; `max` and an `s`-confirmed pick last the session only), so a hub whose first turn finds itself on Fable or at another effort asks the owner to type `/model opus` and THEN `/effort high` in its first-turn readout (in that order: `/effort` saves the level for the model in use, so typed on Fable it rewrites Fable's saved level and leaves Opus's alone), AFTER arming the listener below, and holds no review on the answer — panel agents are pinned `model: "opus"` either way (the lever is the owner's; ground truth is `.message.model` on the session jsonl for the model, never the `# Environment` line, and, for the effort a new session starts at, the level the settings resolve for that model — its `modelSettings` entry in the user settings, unless a project, local or managed settings file sets an `effortLevel` (that applies to every model and outranks the user file), all below `CLAUDE_CODE_EFFORT_LEVEL` or `--effort` — which the hub never opens (a top-level `effortLevel` is the older form and does not count for Opus 5.5, per the same page), then any `/effort` `local_command` record since). A hub already mid-queue on another model or effort states its measured model, and its effort as the `/effort` records show it (or "effort unmeasured" when there are none), once in its next readout, asks once, and keeps dispatching — nothing in flight is stopped, re-seated or killed.
Call the **Monitor tool with `timeout_ms: 1800000`** (the maximum: the tool has NO `persistent` parameter and ends every watch at 30 minutes, so re-arm on each expiry notice — this read `persistent: true` until 2026-09-26) running:
```
python3 scripts/session-manifest.py mail-listen --poll 30 --rebroadcast-hours 48
```
(The SessionStart hook may DIRECT a bare `mail-listen --poll 30` — for a hub, arm it **with `--rebroadcast-hours 48`** so the push cadence is on; if a bare one is already running, re-arm with the flag. A `/command` first turn still owes the arm.) Each inbound mail surfaces as an event; the session keeps working and is re-invoked on arrival.

**ARM THE SECOND MONITOR IN THE SAME TURN — the staleness poller. It is a SEPARATE Monitor, not a check you run — arm it with `timeout_ms: 1800000` too, because the tool's DEFAULT is 5 minutes and this loop sleeps 600 s, so an arm without it polls ONCE and dies; re-arm on each expiry like the listener:**
```
while true; do bash scripts/hub-stale-request-poll.sh 2>&1; sleep 600; done
```
⛔ **THE ARMING INSTRUCTION LIVED ONLY IN THE SCRIPT'S OWN HEADER UNTIL 2026-09-07, WHICH MEANS IT REACHED A HUB ONLY BY ACCIDENT.** `hub-stale-request-poll.sh:3` says *"Armed as a persistent Monitor by the review hub"* — but this Phase named only `mail-listen`, and the poller appeared once in the whole spec, inside the four-instrument fence in the closure-check block below, where it reads as a thing you RUN rather than a thing you ARM. **Measured on this seat:** hub armed 10.4h, `mail-listen` running, poller never armed; three requests sat with nothing sent (83m, 80m, 56m) and no alarm existed to say so. Arming it fired all three on the first tick. **The two monitors answer different questions and neither substitutes: `mail-listen` tells you something ARRIVED, the poller tells you something you already hold has gone UNANSWERED.** An unrouted instrument is an unbuilt one — the same sentence this spec already applies to `review-request-closure-scan.mjs` two blocks down, which is the instrument this poller wraps.
- ⚠️ **`2>&1` is load-bearing:** the poller's own header records that a Monitor captures stdout only, so a misconfiguration (`HUB_STALE_MIN` non-integer) prints to stderr and the alarm dies SILENT — indistinguishable from a quiet queue.
- ⚠️ **It measures OPEN, not IDLE.** A request with lenses running reads identically to one nobody started; the fire text says so. Check which before acting.
- ⚠️ It inherits the closure scan's blind spots wholesale (subject-phrasing `ASKS` gate, broadcasts excluded), so its silence is a FLOOR, never an all-clear.
- ⭐ **`25` / `600` ARE TUNED VALUES, NOT FIRST GUESSES — measured over one earlier session's whole tenure of running the poller, and passed on when it closed.** 21 of its 24 invocations used `HUB_STALE_MIN=25`; 20, 30 and 45 were each tried once before returning to 25 — **20 is noisy against a hub that acks in ~3 minutes, 45 is past the point where a peer has already pinged you.** `sleep 600` then yields at most one alarm per request, landing while the request is still actionable. **`25` is also the script's own default (`THRESHOLD_MIN="${HUB_STALE_MIN:-25}"`), so the loop above needs no env at all** — do not re-derive these by experiment.
- ⚠️ **That tenure ran `2>/dev/null`, which is the one form to NOT copy** — it is precisely the redirect that guarantees the silent death this block's `2>&1` exists to prevent, and that session said so itself when passing the numbers on. That tenure never hit the failure because its threshold happened to be valid every time; **a tenure without a failure is not evidence the failure mode is absent.** ⚠️ The companion claim that exporting the FULL uuid is load-bearing is NARROWER than stated: measured on this seat, `CLAUDE_CODE_SESSION_ID` is already the 36-char uuid by inheritance, so the export is belt-and-braces here. Check your own env before adding it. **Negative control, run before trusting any quiet tick — `HUB_STALE_MIN=99999` must print NOTHING at rc=0** (measured: stdout 0 B, stderr 0 B), which is also what proves `2>&1` adds no per-tick noise.

**ARM THE USAGE WATCH IN THE SAME TURN, BY DEFAULT:** `python3 -I scripts/hub-usage-watch.py --sid <sid8> --pause-at N 2>&1` as a third Monitor, `timeout_ms: 1800000`, re-armed on each expiry, with N from the working plan's `usage watch armed: --pause-at N` line when it has one and otherwise 80 — the value the owner has armed every time so far, so a measured default and not a ruling on the number — unless the owner's words in the same turn say otherwise (another N, or no watch) or the working plan carries the owner's `usage watch: off (<the owner's words>, <ISO>)` line (§ ⏸ step 8), and, when you arm it, write the `usage watch armed: --pause-at N` plan line (§ ⏸ step 6 below). A review the owner orders bypasses the hold the watch causes, as § Near the 5-hour limit already says; the watch holds new reviews, never a running seat, and after a compaction or a resume, which watch to re-arm, if any, is § ⏸ step 9's call (no plan line there means none).

**Then STAMP the durable hub marker (the PULL half):**
```
date -u +%FT%TZ > .claude/state/review-hub-active-<this-session-sid8>
```
This marker is how a freshly-booted peer DISCOVERS this hub at its own SessionStart (`session-manifest.py hub-discover`, wired into the SessionStart hook + `/orient`), **independent of the staleable broadcast** — a hub live >72h has lost its original `--to all` announcement to the unread-mail TTL, so a peer booting on day 5 finds nothing without this. The marker's mtime = last-broadcast time (re-stamp it on every (re-)broadcast, Phase 2/3); `--rebroadcast-hours 48` makes the listener surface a `⏰ RE-BROADCAST DUE` nudge once the marker passes 48h (< the 72h TTL) — the PUSH half. Push keeps the broadcast fresh; pull is the zero-staleness backstop.

**ALSO ARM THE QUEUE-CLOSURE CHECK — a hub's characteristic failure is a request it RECEIVED and never answered, and no other net sees it.** `review-verdict-disposition-scan.mjs` answers the opposite direction ("a verdict came to me and I never folded its findings"); nothing answered this one. Run at any point you are about to state your own queue, and at `/wrap`:

```bash
node scripts/review-request-closure-scan.mjs   # 1. unanswered request SHAs   (does an outbound name this sha)
python3 scripts/hub-unfinished-loops.py        # 2. peers awaiting a reply    (who holds the last word)
python3 scripts/hub-open-promises.py           # 3. MY OWN open promises      (did I say I would and not do it)
./scripts/hub-stale-request-poll.sh            # 4. staleness poll over (1)
```

⛔ **AND ALL FOUR SHARE ONE BLIND SPOT, WHICH IS THE HUB'S OWN DOMINANT OPEN LOOP: A VERDICT *I* ISSUED

On a `usage watch: no trusted reading (<reason>)` line do nothing: the watch keeps running, and after a reset that line is what wakes the seat to refresh the figure. An exit with no decision line (`usage watch: internal error (…)`, a traceback) is re-armed once and reported to the owner if it recurs. `--once` gives the same decision for a check by hand (exit 0 fires, 1 holds, 3 a fault). The same watch reads the weekly line too (`--weekly-pause-at W`, default 97), so the command and the plan line are unchanged; the weekly line needs no reset epoch and decides on a reading whose five-hour fields are empty.
7. **On `USAGE-PAUSE pct=<p> resets_at=<ISO>`:** if `review-hub-paused-<sid8>` already reads `until=owner`, the owner's pause outranks this one: change nothing and arm nothing more. Otherwise enter by step 1 with the marker `<epoch> inflight=<n> until=reset:<ISO> cause=usage>=N`, each held ACK's subject ending `— the hub is paused until the ~HH:MMZ reset` in place of `by the owner`, tell the owner in one line that it paused (the % and the reset time), and arm the second watch the same way: `python3 -I scripts/hub-usage-watch.py --sid <sid8> --pause-at N --resume-after <ISO> 2>&1`. It fires on the first trusted reading below N after the reset, or before the reset on one from another account's window (step 8).
7b. **On `USAGE-PAUSE cause=weekly pct=<w> resets_at=<ISO|unknown>`:** as step 7, with the marker `<epoch> inflight=<n> until=weekly-below:W cause=usage>=N weekly>=W`, each held ACK's subject ending `— the hub is paused until the weekly limit resets` (`~<ddd HH:MMZ>` when `resets_at` is an ISO), the one line to the owner naming the weekly % and the reset (or that the feed gives none), and the resume watch `python3 -I scripts/hub-usage-watch.py --sid <sid8> --pause-at N --weekly-pause-at W --resume-weekly 2>&1`. It fires on the first trusted reading with the weekly figure under W: the weekly reset, or a switch to an account under W (one account's weekly figure never falls; the script's docstring). While the status file is stale (the session idle, or the machine asleep) it prints nothing until that file's own weekly reset has passed, then its `no trusted reading` line wakes the seat to refresh the figure, as in step 6; a stale file that gives no weekly reset stays silent, and the Monitor's expiry re-arm (step 6) is then the wake. A resume watch of either kind prints the OTHER line's `USAGE-PAUSE` in place of its resume when that line is at or over its threshold: handle it by step 7 or 7b from inside the pause (rewrite the marker, stop the old resume watch, arm the new one); held requests stay held and their ACKs are not re-sent.
8. **On `USAGE-RESUME pct=<p>`** (or `USAGE-RESUME pct=<p> account-switch resets_at=<ISO>`: before the old reset, a reading from another account's window, below N; the switch shows only after this session's next request on the new account, since an idle session keeps the old figures, so it lands at the hub's next wake, not when the owner switches)**:** run `--resume` (step 3's "On the owner's word" sentence; the deploy-hold reading after it runs only on the owner's word) ONLY while the marker still reads `cause=usage` (the watch checks the same before printing, and says `not resuming` when it does not: stop that watch then), its one line also saying that the window reset, or that the account switched and when the new window resets, and the new %, and re-arm step 6 for the next window. A pause the owner orders during it (`--pause`, or the owner's words by step 4) rewrites the marker by step 1 to `until=owner`, which no watch lifts: stop the resume watch and keep holding. The owner's `--resume` or words lift either kind at any time and stop the resume watch; step 6 is then re-armed unless the owner says to stop watching the limit, which rewrites the plan line to `usage watch: off (<the owner's words>, <ISO>)` (Phase 1 and step 3 honour it), and the one line says which. Re-arm it at once only if `--once` prints `holding` below N; otherwise it would read the figure that caused this pause and pause again within one poll, so the plan line reads `usage watch armed: --pause-at N from <ISO>` (that window's reset) and it is re-armed at the first wake after that time. **On `USAGE-RESUME cause=weekly pct=<w>`:** as above, its one line saying the weekly figure fell under W (the weekly reset or another account) and the new %. Re-arm step 6 at once: this line prints only while the five-hour line is under N or has no trusted reading, so the pause watch cannot read the figure that caused this pause.
9. **Across a compaction the marker says which watch is live:** none ⇒ step 6's, if the working plan records the arm (not before its `from` time; a `usage watch: off (…)` line records none); `cause=usage` ⇒ the resume watch, rebuilt from the marker alone (`until=reset:<ISO>` is its `--resume-after`, `cause=usage>=N` its `--pause-at`; `until=weekly-below:W cause=usage>=N weekly>=W` ⇒ the weekly resume watch, `--pause-at N --weekly-pause-at W --resume-weekly`); `until=owner` ⇒ neither. Those two rebuild the whole command, so unlike the poller's nothing is banked; step 2 re-arms it.
10. **`--when` takes only `usage>=N` for now;** a clock time is `/autorun`'s job.
11. **`--pause --disarm`:** the pause as written (steps 1-5), then `/pre-compact --disarm` run through the Skill tool in the same turn — the same pairing as `/pause --compact --disarm` in `pause/SKILL.md` — which takes down the listener, the staleness poller and any usage watch and banks the seat's state in the working plan; the recovery re-arms them (`/post-compact` step 5; step 2 here for a restart).

### Three token-saving practices
Adopted on the hub's own proposal. Until 2026-10-05 they ran from session memory alone; no line of this spec carried them.
1. **The report-path line every lens brief carries is in Phase 3 step 2** (moved there 2026-10-26 so a compaction's carry keeps it).
2. **On a fold-verify with more than one seat, give each seat a DISJOINT set of questions** (2026-10-02: two seats on one fold reached 3 of 7 findings independently — duplicated work).
3. **When a fold report says the hub's patch was applied unchanged, byte-compare instead of seating a reviewer:** apply the patch at the parent in a scratch worktree, then `cmp` each file against the fold commit.
⛔ **None of these cuts a fresh seat, mutation testing or the second fold-verify seat** — those have caught real defects, including a regression the hub itself prescribed.

### A lens never waits longer than 4 minutes in one call
**Why:** a lens's prompt cache lives 5 minutes. One Bash call that runs longer than that makes the lens re-buy its whole context on the next turn. Measured 2026-10-07 over this hub's 1,042 lens transcripts: 190 cold re-caches, 39.3M tokens. 96 of those followed the lens's OWN wait of 5 minutes or more, and 93 of the 96 used `timeout: 600000`. Of 117 calls of 5+ minutes, only 16 were the hook smoke suite; the rest were unit runs, mutation runs, open-ended wait loops and browser tests.
**The three lines every lens brief carries verbatim are in Phase 3 step 2** (moved there 2026-10-26 so a compaction's carry keeps them).

**A hook lens adds a fourth:** `For a hook change run "bash scripts/smoke-test-hooks.sh --for <changed hook path>" (median about 9 s, up to about 140 s for a hook that selects the Results section; every section that names the file or its stem, plus the core set). Exit 0 certifies those sections only: a section that reaches the file through another hook, a script a hook runs, or a value another section sets is not run, so name the selection in your verdict and run the full suite in the background when the change touches shared state. It is never a pass for pushing; exit 2 = a term matched nothing or the file needs the full suite, exit 3 = the selection broke, so run the full suite in the background then.` (`--for` refuses shared hook libs, `settings.json`, `.githooks/*` and the suite itself under any spelling — a `scripts/` file a hook executes needs the full run too.)

⚠️ **This is a lens rule, not a migration rule.** A lens never applies a migration to a shared database (the throwaway Postgres `scripts/integration-test.sh` builds is its own, and the second line already forbids the re-run `migrations.md` guards against), so `migrations.md`'s keep-`timeout: 600000` advice (which holds an APPLY in the foreground) has nothing to protect here. ⚠️ **Not covered:** a wait the HUB itself does is paid at the main session's 1-hour cache, so it does not cost this. And a lens that hits the usage LIMIT re-caches no matter how it waits; that is rule 1 of `references/pause-and-limits.md` § Near the 5-hour limit. The always-loaded `bash-environment.md` § Pass `timeout: 300000` sits exactly on the 5-minute cache life and is due its own change after the 2026-10-07 experiment freeze; until then this paragraph is the override. ⚠️ **Since 2026-10-18 `subagent-cache-window-inject.sh` gives every sub-agent, lenses included, a 180 s bound at start; where both arrive, lenses follow this brief's 240 s** (measured 2026-10-19: the 5 lenses carrying both that went past 180 s all stayed at 200-220 s). Both sit within ~14% of the cheapest bound per waited second (~220 s, over 55,560 sub-agent response times), so neither moves for cost; one number is the cleaner state, and the 240 s line is the owner's to move.

### A lens still issuing commands after 2 refusals in a row is waiting on the owner — tell the owner at once
After 2 refusals in a row, auto mode stops deciding for that lens and puts a permission prompt in the owner's terminal, on the hub's session, so the lens's next command waits there, measured at 5-7 hours on 2026-10-20. Two parts:
- **Every lens brief carries the STALLS line, verbatim; it is in Phase 3 step 2** (moved there 2026-10-26 so a compaction's carry keeps it). A lens that obeys it hands back and is not waiting (2026-10-20T03:03Z: "this reviewer hit 2 refusals in a row, stopped, and handed its findings back").
- **A lens that kept going is waiting on the owner: tell the owner in your next reply** which lens, what it was refused, that a permission prompt for it is waiting in the owner's terminal, and that nothing comes back from it until the owner approves or denies that prompt. Look for one every time you state the queue (the `ListAgents` read that row already makes); never a blocking question.

Founding case 2026-10-20: a hub promised exactly this in its reply, and the promise reached no file until it was found later.

## Checkpoint cadence — `/wrap --checkpoint` BEFORE accumulation forces a deep-pass
A long-lived hub accumulates review-process lessons + lens `Memory Update` blocks across its WHOLE life; an un-checkpointed hub that runs to 25h+ hits the `/wrap` **1b-DEEP** threshold (>1500 transcript lines) and must reconcile the entire pile at end-of-life — or lose it on a mid-life crash. So the hub SELF-FIRES a **`/wrap --checkpoint`** (session CONTINUES — frame it "Checkpoint complete — session still live", never "closed") when, SINCE THE LAST CHECKPOINT, EITHER **~6–8 delegations served** OR **~1500 transcript lines accumulated** (the SAME bound that fires 1b-DEEP — checkpoint BEFORE you'd need the deep-pass), whichever comes first. **Soft/warn cadence, not a hard gate** — the count is self-tracked; calibrate up (fewer interruptions) / down (more durability) as observed.
- **Why `/wrap --checkpoint`, not a bare `/meta learn`:** the checkpoint's own skip-gates auto-lighten it for a review-ONLY hub — no commits → the 7b/7c/7d tracker sweeps skip; no `src`/`tests` → the 5b/5c/5d unit/lint/i18n gates skip; no migrations → Step 6 skips. What RUNS each checkpoint is exactly the hub's yield: `/meta learn` (incremental lesson persist + lens `Memory Update` sweep — keeping current the orchestrator's duty to persist sub-agent MEMORY blocks), the corrections-registry sweep, `mail-check --peek`, and the Step-11 reconcile. ~1–2 min, not the full heavy wrap.
- **Benefits:** incremental lesson persistence (a crash loses only since-last-checkpoint) · each checkpoint's Step-1b scan window stays UNDER the 1500-line bound so the deep-pass never has to fire · a tractable end-of-life wrap · lens `Memory Update` blocks swept in BATCHES, not one 25h pile.
- **Evidence:** a ~25h hub ran ~15 reviews un-checkpointed → 24,604 transcript lines, 1b-DEEP fired, and every review-process lesson piled up to end-of-life; the cadence was adopted to prevent recurrence.

### The digest — one per checkpoint, and at `/wrap`
At every `/wrap --checkpoint` and at `/wrap`, before the readout, the hub writes a DIGEST: one line per verdict served since the last digest — the sha, the requester's session NAME (`session-manifest.py who`), the items by severity (`P1 n · P2 n · P3 n`), how many the hub held at `file:line` itself, the deploy token (`DEPLOY-CLEAR|DEPLOY-HOLD`), and the disposition so far (folded; rejected, by name; open).
- Append the lines under a dated `## <date> <hub sid8>` heading to `.claude/docs/review-digest.md` (tracked; its header fixes the line shape), and print the same lines in the checkpoint readout under `Digest:`.
- It is the owner's source for what the hub found and what held, so side-agent notes stop being the owner's: a claim the owner hears elsewhere that no digest line carries is unverified until one does. A verdict with no items still gets its line (`APPROVED · 0 items`).
- No script writes it; the hub writes it by hand from its ledger rows for the window, and the ledger rows are what the digest reconciles against (a verdict with a ledger row and no digest line, or the reverse, is a finding at the checkpoint).
- Basis: in the measured window, 735 side-agent notes pasted into 34 sessions, 138 "validate this" replies, and 3 of 8 sampled note errors traced to the hub's own earlier mail.

## Disciplines (the lessons that paid off in the founding session)
- **verify-before-relay** — every finding at file:line; a "this is broken" claim crosses to a peer only after you confirm it (caught a stale already-fixed finding + a false brief-premise + a self-buggy clean-check).
- **builder≠breaker** — fresh lenses; exclude wave authors.
- **severity-to-threat-model** — calibrate to the real blast radius; don't inflate a local owner-run tool to P0 (a doc/script review's "bug" class is false-claim / contradiction / mis-cite, not a code defect).
- **reconcile cross-lens severity** — the orchestrator's job is to resolve disagreeing lenses, not relay the max.
- **append the log simply** — don't carve hunks or chase phantom-dirty on an append-only shared log.
- **the peer/hub lens advantage** — a delegate reviewer sees cross-session working-tree state (`whose-edit`, live `git diff`) that an in-session panel structurally cannot (a delegate review once caught a partner's transient mid-review mutation).
- **cross-lens AGREEMENT is not ground truth (2026-07-20)** — two FRESH lenses can share an enumeration blind spot, so N agreeing lenses ≠ N independent confirmations. Resolve a COMPLETENESS/ABSENCE claim ("no test guards X" / "deleting Y ships all green") at ground truth — the tier the code actually gates (unit + integration + e2e globs), never at cross-lens agreement. Evidence: in one review, my front-load AND one lens both ruled the Stage-2e wiring "deletable-green" (both enumerated only the UNIT tier); the 3rd lens + a file:line check found the integration coord-overlay test guards it. The DISAGREEING lens was the signal; the agreeing pair was the trap.
- **`--code` coherence is BLIND to prompt attention-priming (2026-07-20)** — a review pass over a prompt fence / negative instruction cannot see whether NAMING the forbidden pattern INDUCES it. Clear the STRUCTURAL questions; mark every behavioral-prompt claim EVAL-DEFER and never coherence-clear it into deploy — the empirical "does it induce" is the eval-gate's to answer. Evidence: the v2.17 arc (round-1 coherence-clearance was empirically contradicted by the eval's 3/3 forbidden-prose confab).
- **read the ACTUAL pixels for an image / legal-image call (2026-07-20)** — a text-only review of "a construction diagram" waves through a photoreal-face EU-AI-Act-Art.50 disclosure gap; Read the raster and rule from the pixels, not the alt/comment describing them (factual-claim verification). Evidence: a lesson page once served a photoreal AI face undisclosed under a "stylized illustration" label; only reading the image file caught it.
- **verify a peer's OWN state-claim before it goes load-bearing (2026-07-20)** — a delegator's claim that a red test is external to its diffs, or that the owner ruled for a particular fix, is a self-asserted snapshot, unverified until checked against git / ground truth. Confirm before relaying or acting. Evidence: one peer's external-red claim (verified TRUE via `git show` name-only) + another peer's relayed owner ruling (flagged as relay, not direct owner speech — immaterial to the code-correct CLEAR, but named).

## ⛔ THE HUB REVIEWS EVERYONE AND NOBODY REVIEWS THE HUB — route one of your OWN verdicts per checkpoint (2026-08-06)

⛔ **AND THAT ROUTED SELF-REVIEW RUNS HOST-COMMITS-FIRST, EXACTLY LIKE ANY OTHER PANEL.** The full ordering is `expert-review/SKILL.md` § Process 4b; it binds here because this path is the one where skipping it is invisible — **you are both the host and the author of the thing under review, so your position is already written and the temptation is to send it along as the brief.** Do not: commit your verdict-about-your-own-verdict under a timestamped `## Host position` block in your SESSION PLAN FIRST (no brief points the breaker at that file for reading; the brief names it by path as do-not-open and excluded from every search — `expert-review/SKILL.md` § Process 4b (a)-(b); this said "the checkpoint log" until 2026-09-26, a name nothing here defines and one a reader can resolve to a shared state checkpoint file), dispatch the breaker with the artifact and the question ONLY, and when you report, name the strongest argument against yourself that came back and say plainly whether it moved you. **An unchanged position reported silently is exactly the shape this whole section exists to prevent** — the hub agreeing with the hub, with a review-shaped receipt attached.

Every other seat in the fleet has a breaker: it ships a diff, the hub attacks it. **The hub ships
verdicts and nothing attacks those.** That is not a gap in coverage, it is the fleet's single
largest unreviewed surface, and it sits on the seat whose entire job is **asserting that other
people are wrong** — which the forensic pass measured as the highest-risk assertion shape there is.

**An existing rule already binds this and was never applied here.** A hub verdict is self-referential (it
evaluates work under the hub's own frame), evaluative (that is what a verdict is), and
codification-bound (peers fold it into commits). All three conditions hold, so the rule's own
conclusion applies: it needs a **fresh context with a refute mandate**. Lens count does not
substitute — N lenses composed by the same orchestrator, over the same brief, share the frame.

**What a retired hub's own root-cause record shows** (104 classified errors):
- **5 of 16 outbound broadcasts were retractions, and every one was an act of correcting a peer.**
  None was self-caught.
- **One slice's five errors all had a correctly-executed instrument in hand** — right output, wrong
  characterisation on top. Instrument density does not protect a verdict; another slice's
  window ran `git show` ×156 and still shipped two.
- A verdict shipped with two lenses APPROVED that a third lens later broke, on a mismatch
  neither of the first two had caught.

**Procedure — ride the checkpoint you already fire (§Checkpoint cadence), or your 25th dispositive ledger row since the last self-review row, whichever comes first.**
At either trigger (measured 2026-09-15..10-26: 3 checkpoints against 1,833 dispositive rows, and 0 self-reviews in 4,885 dispatches), pick ONE verdict served since the last self-review — prefer one that
CONTRADICTED a peer, since that is the measured risk concentration — and route it to a
fresh-context agent with a refute mandate: *"here is the diff and here is the verdict I sent;
find where the verdict is wrong."* Give it the artifact and the verdict, **not** your reasoning
about the peer's process (`references/disciplines.md` § A BRIEF'S PREMISES ABOUT THE AUTHOR). Fold what survives; mail the peer a
correction if the breaker overturns a plank you sent them. One agent, one verdict, per trigger — and ONE ledger row for it: `| <date> | self-review | KEEP — self-review of <sha> by <agent type>, report <file>; overturned: none / <items> | <hub sid8> | — | self-review of <sha> |` (`KEEP` is in the ledger enum; the row is the only receipt that this section ran). ⛔ **Never the audited sha in the Commit cell:** the ledger is newest-row-wins (`parseLedgerShas`) and `KEEP` settles nothing, so such a row would un-settle the verdict it audits for `/promote` and the closure scan.

**Do NOT** substitute a self-re-read, a second lens from the same panel, or the delegator's
agreement — the delegator accepted the verdict, which makes them the least independent reader
available.
