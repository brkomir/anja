## Trigger — the strip one-liner and its measurements

   **Trigger — auto-detect (fire when this session compacted — a record, per /wrap Step 1b's Detection, auto or `/compact` — AND either bound is crossed):**
   ```bash
   TX="$HOME/.claude/projects/<project-key>/${CLAUDE_CODE_SESSION_ID}.jsonl"
   # STRIP FIRST, then measure — see the byte-unit rule below. TXT is the scan target for EVERYTHING downstream.
   # (filename deliberately avoids the `wrap-dp-<wordchar>` shape — that string in THIS spec would
   #  false-positive wrap-reconcile.mjs's deepPassRan transcript-grep, same trap as the digit rule below)
   TXT=/tmp/wrap-stripped-${CLAUDE_CODE_SESSION_ID}.jsonl   # SESSION-SCOPED — see below
   # ⛔ BLANK THE IMAGE PAYLOAD, NEVER DELETE THE LINE. A `grep -v` on the base64 marker stood here until 2026-09-15
   # and deleted every owner message sent WITH A SCREENSHOT, its text and rulings included (measured on one
   # session: 9 typed owner records in the raw transcript, 8 in the stripped copy; the lost one carried two rulings),
   # and it shifted every later line number off the raw transcript. The payload sits under TWO keys per record,
   # `source.data` and `toolUseResult.file.base64`, so the pattern names both: a `data`-only form kept 397,933,828 B
   # across 250 transcripts and one line of 3,102,592 B, more than a whole agent slice.
   # Keep the replacement a NON-raw string; a raw one writes literal backslashes into the JSON. Same pattern:
   # the strip in scripts/lib/transcript-strip.mjs (blankBase64Payloads blanks the base64, stripTranscriptLine stubs the request
   # copies, strippedTranscriptBytes counts) and transcript_bytes in scripts/wrap-preflight.py, which does both; after any edit
   # here, run the three strips on one transcript and compare their byte counts, which must agree.
   # ⛔ AND BLANK THE HARNESS'S REQUEST COPIES TO A ONE-LINE STUB, NEVER DELETE THEM.
   # Since harness 2.1.300 (first seen 2026-10-14T21:36Z) the harness writes `api-request`, `api-request-blob` and `api-request-shape` records, a copy of each request
   # sent to the model; measured 52-65% of every transcript's bytes from their first appearance (five
   # sessions measured), so a slice agent spent half its reading on duplicate conversation. A stub keeps every line
   # number, for the reason above; every such record starts `{"type":"api-request`, so the test is a prefix, never a substring.
   python3 -c 'import re,sys
R=re.compile(r"^\{\"type\":\"(api-request[a-z-]*)\"")
for l in open(sys.argv[1],encoding="utf-8",errors="replace"):
    m=R.match(l)
    sys.stdout.write("{\"type\":\"%s\",\"stripped\":\"request copy\"}\n" % m.group(1) if m else re.sub(r"\"(data|base64)\":\"[^\"]{200,}\"","\"\\1\":\"<stripped>\"",l) if "\"type\":\"base64\"" in l else l)' "$TX" > "$TXT"
   BYTES=$(wc -c < "$TXT" | tr -d ' ')
   COMMITS=$(git log --oneline <session-start-sha>..HEAD | wc -l)   # session span; peer over-count is safe (it only raises the fire-rate)
   # FIRE the parallel deep-pass if Step 1b counted a compaction record AND (BYTES > 3000000 OR COMMITS > 20)
   ```
   Below both bounds (or no compaction record) → the inline 1b scan is sufficient; skip.

## Slice from CP; the scoped plan line

And **`$TXT` is the stripped copy, so `$CP` indexes IT, never the raw `$TX`** — the strip keeps every line, so the two share line numbers but not bytes: since the request-copy stub a range cut to ~1.7 MB of `$TXT` holds 2.5-5.9 MB of `$TX` (measured on one session), so cut and read every slice from `$TXT`. Measured 2026-09-02: whole transcript 83.5 MB → **42 slices**; since the last wrap at line 32,692 of 38,179 → 11.9 MB → **6**.

## Scratch artifacts — `$TXT` session-scoping, the run suffix, slice-vs-slice collisions, the frozen copy

   ⛔ **`$TXT` MUST BE SESSION-SCOPED — it was a FIXED SHARED PATH until 2026-08-06, and two concurrent wraps silently overwrite each other's scan corpus (measured).** The bug is soundless in the worst possible way: `grep -v ... > "$TXT"` truncates and rewrites, so the SECOND wrap to reach this line replaces the first's corpus **while the first's slice agents are still reading it** — every downstream `sed -n 'A,Bp'` then addresses a *different file* than the one whose byte-count set the slice boundaries. Nothing errors. The agents return well-formed reports about line ranges that no longer hold the content they were sliced from, and the coverage ledger records those ranges as scanned. **The tell is a slice-total that cannot fit the file**: this seat's 53 slices totalled 36,897 lines against a `wrap-stripped.jsonl` holding 2,195, and at the moment of writing this the shared path held **6,966,747 bytes** belonging to neither of the two wraps that had most recently used it. On a fleet that routinely runs 2–4 concurrent sessions this is not a rare race; it is the default outcome of two wraps overlapping. **Cross-check the slice-line-total against `wc -l < "$TXT"` before trusting any coverage claim** — the numbers agreeing is cheap, and it is the only signal this failure emits. *(The filename still avoids the `wrap-dp-<wordchar>` shape for the reason in the comment above; the `${CLAUDE_CODE_SESSION_ID}` suffix preserves that.)*

   ⛔ **AND A THIRD AXIS NEITHER PARAGRAPH REACHES: RUN-vs-RUN INSIDE *ONE* SESSION. SESSION-SCOPING IS BY CONSTRUCTION BLIND TO IT (measured 2026-08-26).** A session that wraps twice — a `/wrap checkpoint` and then a real `/wrap`, the routine 2-5× re-wrap pattern this spec documents elsewhere — hits the SAME session-scoped path twice. Measured: an 11:43 run cut **15 slices over lines 8302-18591**; a 21:10 run cut **17 slices over 10429-21390** into the identical `/tmp/wrap-slices-<sid>/`, overwriting all 15 at identical filenames. The first run's returns had already been consumed, so nothing was lost here — but **the owner-facing `wrap-dp-plan:` line from 11:43 now describes an artifact that does not exist**, and any later restatement of it is false. **Suffix the run, not just the session** (`…-<sid>-$(date +%s)/`), and treat a `wrap-dp-plan:` figure as valid only for the run that cut it. Same class as `bash-environment.md` § A CERTIFYING INSTRUMENT'S SCRATCH STATE — there the second writer is a peer, here it is *you, later*.

   ⛔ **AND SESSION-SCOPING CANNOT REACH THE AXIS ONE LEVEL DOWN — THE N SLICE AGENTS OF *ONE* WRAP SHARE THAT SESSION'S SCRATCHPAD BY DEFINITION, AND EACH REACHES FOR THE SAME OBVIOUS FILENAME. MEASURED N=5 INDEPENDENT AGENTS IN ONE DISPATCH, 2026-08-18.** The paragraph above fixes wrap-vs-wrap; this is slice-vs-slice inside a single wrap, and **the codified remedy is structurally incapable of reaching it** — a session-scoped directory is exactly the namespace the siblings share. Five agents in one fan-out independently wrote `slice.jsonl` / `assist.txt` into the one scratchpad; five reported the same signature. **The failure is not an error — it is a plausible wrong analysis.** The collided file is a real transcript of a real session, parses cleanly as JSONL, and yields a well-formed owner-speech extraction: one agent wrote *"I nearly reported another agent's owner utterances as mine"*, another analysed the wrong window for four tool calls, and a third measured its own file at 1,550 lines and then 2,152 lines minutes later **with no write of its own in between**. Every one of them caught it only by noticing that the record indices ran past their assigned range. **THE BRIEF IS WHAT ARMS THIS: telling an agent to "slice to a temp file in your scratchpad" without naming the file is the whole defect.** So the dispatching brief MUST mandate a slice-unique name — `slice-<first>-<last>-<slot>.jsonl` — and instruct the agent to **content-key the first record's timestamp against its assigned range before working**, which is the one check that fires whether or not the name collided. ⚠️ Generalizes past this procedure: **any fan-out whose members are told to write a working file into a shared directory, without being told what to call it, has this bug** — and it fails toward a confident wrong answer, not toward an error.

   ⛔ **AND THE SAME ARTIFACT HAS A SECOND FAILURE MODE, WHICH IS NOT THE OVERWRITE: `$TXT` IS A FROZEN COPY OF YOUR OWN TRANSCRIPT, PLAUSIBLY NAMED, SITTING ONE GREP AWAY FROM ANY SESSION-STATE CLAIM (2026-08-07).** The block above makes the copy *private*; it does nothing about the copy being *stale*. From the moment `grep -v` writes it, the file stops tracking the session — so every later question answered off it ("how many agents did I dispatch?", "did the owner ever say X?", "what did I commit?") is answered as of the slice moment, and the answer is well-formed, confidently derived, and **short by however long the wrap has been running**. Measured: a seat reported a dispatch count that was really a window count, off a derivative exactly like this one. **Rule: `$TXT` is for SLICING ONLY. Any claim about the session's own state re-reads `$TX` (the live jsonl), never the stripped copy** — and if the claim is load-bearing, say which of the two you read. General form worth keeping: **when a procedure hands you a convenient derivative of the very thing you need to measure, the derivative is the hazard** — its convenience is what gets it used for the second question it was never built to answer.
   ⚠️ **This paragraph exists because the fix for it landed in a MEMORY SHARD and nowhere else.** `git show --numstat` on the shard commit → one file, a meta memory archive shard, +2/−0. The lesson was correctly captured and the *procedure that manufactures the trap* was never told — so every seat kept running the unwarned version while the ledger recorded the warning. ## The unit is bytes

   **⛔ THE UNIT IS BYTES, NOT LINES (2026-07-27, after an OS-level OOM crash killed a live `/wrap`).** The prior trigger and slicing both keyed on LINE COUNT; the memory cost is BYTES, and on an image-lane transcript the two diverge ~10×. Measured on the crashing session: **228.0 MB / 19,331 lines — but 370 base64 lines (1.9% of LINES) carried 177.9 MB (78.0% of BYTES)**, so a "1,146-line slice" was 14 MB average / 26 MB worst, ×14 concurrent agents each running `grep -oE` with a wide character class over it. Same defect family as *right arithmetic, wrong comparand* — the arithmetic was fine, the unit was wrong. **The base64 strip is the single highest-leverage fix (228 MB → 50 MB here) and it loses NOTHING: the deep-pass scans owner speech and arcs, never image bytes.**


## The corpus fence and the brief block

   ⛔ **AND THE SLICE CAP BOUNDS THE *INPUT YOU NAME*, NOT THE *CORPUS A SUBAGENT CAN REACH* — FENCE THE CORPUS EXPLICITLY IN EVERY BRIEF (measured 2026-07-31, two sessions, same night).** Slicing bounds what you HAND the agent. It does nothing about where the agent GOES. A deep-pass brief invariably also says *"dedup each candidate against the ledger"* — and a dedup or owner-turn hunt points naturally at `~/.claude/projects/`, which is **4.9 GB across 119 transcripts, OUTSIDE the repo, where `--ignore-files` protects nothing** (the repo's whole gitignore-respecting corpus is 4,226 files / 131.8 MB — the store is ~37× that). One subagent widened exactly this way and its `ugrep` reached **57.66 GB** (VSZ 461.89 GB) on a lazy `"role":"user","content":"[^"\\]{5,}.{0,1200}?"` — catastrophic-backtracking shaped. Its own session had **zero agents in flight** when its memory guard then denied two dispatches at 33.7 → 40.8 GB: **a returned subagent's allocation outlived it and blocked its parent.** It was spotted in Activity Monitor, mislabelled `2.1.220` because the app name is inherited.

   **Put this in the brief verbatim, every wave:** *"Search ONLY your slice file and the named repo paths. NEVER search `~/.claude/projects/`, `$HOME/.claude`, or any path outside the repo — the transcript store is multi-GB and a regex over it can allocate tens of GB. If a dedup needs transcript evidence, say so and stop; do not widen. FORWARD-ANCHOR every pattern: put a LITERAL first and use a variable-width quantifier on ONE side only — never `.{0,N}(a|b|c).{0,N}`, which is ~4000x its input and reached 19.78 GB on a 5 MB corpus. And never let a dot, a character class or `\s`/`\w`/`\d` carrying a `*`, `+` or `{m,n}` sit anywhere up to about 20 characters before an `(a|b)` group, even with a literal between them: a hook denies it and the whole call is lost; run one `grep -F` per term. NAME EVERY SCRATCHPAD FILE YOU WRITE WITH YOUR SLICE ID (`asst-<slice-id>.py`, never `asst.py`) — your siblings share this directory and each reaches for the same obvious name; a collided helper RUNS CLEAN and returns a plausible WRONG reading of somebody else's window. If your slice's first record carries no `timestamp`, content-key on your LINE COUNT plus the first record that DOES carry one, instead of aborting a healthy slice."* ⛔ **THE 2026-08-26 RETRACTION OF THE `messageId` FALLBACK WAS ITSELF MEASURED WHERE THE CLAUSE CANNOT FIRE (folded 2026-08-27): its 0-of-7 evidence came from `assistant`/`attachment` first records, which ALL carry `timestamp` — the fallback never fires there — while `file-history-snapshot`, the one type the original parenthetical named, carries `messageId` 26/26. The ninth vacuous control in this repo's ledger.** What the data actually says: a no-timestamp `file-history-snapshot` record CAN content-key on `messageId` (26/26); the LINE-COUNT fallback above earns its place on `type:"mode"` records, which carry NEITHER field and were the case that actually fired. ⛔ **THE HELPER-FILE HALF WAS CODIFIED ABOVE AND NOT IN THIS BLOCK UNTIL 2026-08-26, SO IT RECURRED ON THE VERY WAVE THAT FOUND IT (N≥6):** the spec's `$TXT` clause fixes wrap-vs-wrap and the slice-file naming fixes the CORPUS, and neither reaches an agent's own scratch scripts. A slice agent measured its own `asst.py` and `owner2.py` overwritten by a sibling's, caught it only because the collided file's timestamps fell outside its assigned window, and re-derived every affected read. **A clause that lives in the spec but not in the brief is a clause the wave does not have.** **The anti-stall caps bound the OUTPUT (`head`, match limits); nothing bounds the CORPUS but this sentence — and the corpus fence alone is NECESSARY, NOT SUFFICIENT, which is why the pattern clause rides in the same brief (measured 2026-07-31: the fence HELD over two named repo files and a two-sided-quantifier pattern still blew up).** Two independent sessions running this same procedure hit it the same night, and both then tuned their concurrency ceilings against readings the widened grep had confounded — so the corpus fence and the machine-wide-sampler fix are one defect wearing two faces: **the runaway is not concurrency, and lowering the agent count treats the symptom.**

## MODEL ROUTING

   - **MODEL ROUTING: every slice agent dispatches with an EXPLICIT `model: "opus"` — the DEFAULT, on every seat, and NEVER by inheriting the orchestrator's model — EXCEPT under `/wrap --sonnet`, where every slice agent dispatches with an EXPLICIT `model: "sonnet"` instead (the flag lets the owner choose Sonnet 5.5 over the Opus default). Either way the dispatch report STATES the SERVED model of EVERY slice, read from this session's transcript (`~/.claude/projects/<project-key>/${CLAUDE_CODE_SESSION_ID}.jsonl`): each Agent launch's tool_result carries `toolUseResult.resolvedModel`, and the slice is the one whose `toolUseResult.description` names it. Never read an agent's output_file for this (its launch result forbids it), and name any slice that reads a different model — the alias is a request, not a guarantee: `sonnet` served `claude-sonnet-5` at 22:52Z and `claude-sonnet-5-5` at 23:31Z on 2026-09-28 inside ONE session, so a wave can be mixed and one agent's reading cannot show it. ⛔ **UNDER `--sonnet`, STATE THE `wrap-dp-plan:` LINE FIRST, THEN DISPATCH ONE SLICE AND READ ITS `resolvedModel` (with any `[1m]` suffix removed) BEFORE DISPATCHING THE REST — AND AFTER EVERY LATER LAUNCH TOO: the first launch whose model is not `claude-sonnet-5-5` ends dispatching** (the every-launch half is the same "stop before the rest" applied past slice 1, because the alias can flip inside one wave — the 5.0-to-5.5 flip measured above took 39 minutes, well inside a rolling 20-slice wave). Naming the mismatch in the report is not enough: on harness 2.1.282 a whole 11-slice wave served `claude-sonnet-5` (1,139,721 tokens), was reported correctly, and the wrap was then redone on 5.5. The launch result carries the served model at dispatch, so the probe costs one sequential launch; once it passes the rest dispatches in parallel as usual. **At the stop:** let every slice already launched finish (never kill an in-flight agent) and keep its report, labelled with the model it served; declare the slices not dispatched as `line region <first>-<last> unscanned` with real digits; put ONE question to the owner — re-run that region on Opus, on whatever Sonnet the harness now serves, or leave it unscanned — and CONTINUE every other wrap step without waiting. The deep pass is the only step the stop halts: if he never answers, the region stays declared unscanned, and `scripts/wrap-reconcile.mjs` reads a stated plan plus a declared region as a halt, not a skip (`dpSkipVerdict`). A plan line restated after his answer re-dispatches from slice 00, so the ledger floor moves with it. The id is literal on purpose: the flag names Sonnet 5.5, so a successor Sonnet also stops the wave until the owner rules on it and this line is edited. a slice whose declaration carries no range the gate can read (a list under the header, "5420 through 8953") is overlaid by no top-up, since there is nothing to check its `range:` line against, so it is refused unless it affirms none itself (a partial top-up would otherwise have skipped the rest of those regions in every later wrap); the gate copies the slice reports into a scratch view (`dp-gate-<run>`, outside the `dp-returns-*` glob the re-wrap read walks) and lets such a top-up REPLACE its slice's report there — the loop walks the slice reports, never the top-up dir, so a top-up named for a slice that has no report is never read, and an absent or empty top-up dir is no unmatched glob under zsh, the Bash tool's shell — so the slice's declared regions count as covered exactly when a returned top-up affirms none for them (a top-up still `status: dispatched` or one without the affirmation leaves the slice's own report in force, and one that itself declares a region replaces it and is refused by the range test, so the pass is refused either way). A top-up's findings are the only read of its regions, so Step 2 folds each `dp-topups-<run>/` report beside the slice reports, and the every-dir re-read above reads every `dp-topups-*` dir too. On 2026-10-11 (run 1791738537) a complete pass of 26 slices plus one top-up was refused on exactly these two shapes — two slices wrote the affirmation with a depth caveat on the same line, and the top-up's file was outside what the gate read — so no covered-range record was written and the next wrap would have walked the marker again. ⛔ **The affirmation is POSITIVE and the range test is DASH-BLIND on purpose — both earlier forms failed:** a bare-word test refused 7 of 7 complete slices, because the header itself says "Unscanned" (2026-10-11), and the digit-hyphen regex `line region [0-9]+-[0-9]+ unscanned` that replaced it WROTE the record on 8 of 10 declared-region variants in a throwaway control, including the en-dash form the slice protocol below used to carry, `lines`, commas, `line regions` and a bare list under the header (2026-10-11). A missing or reworded affirmation refuses, a prose mention of a digit range beside "unscanned" refuses, and any doubt writes nothing, which only moves the next CP earlier. The next wrap's CP derivation lets it override the marker walk's CP (that read sits below the walk's last `CP=` line, above the SANITY gate). ⛔ Write it ONLY for a pass whose every planned slice returned: a halted or partial pass (a declared `unscanned` region that no returned top-up re-covered, a `--sonnet` stop) leaves the previous file in place, because the file asserts coverage and the next CP skips everything below it.

## Verify every finding; the "no durable home" false positive

   - **Orchestrator VERIFIES every load-bearing finding ITSELF before persisting** — a deep-pass agent's finding is a CANDIDATE, not truth. Evidence 2026-07-01: an agent flagged a cost doc as stale when it already carried the correction — the false positive was caught on verification. Persist confirmed gaps (missed L#/decision/defer), log confirmed memefy candidates, codify confirmed lessons.
