Mechanism in Lecture 4; the authoritative set is `grep -l -F 'paths: [' .claude/rules/*.md`, and `CLAUDE.md`'s router (its table plus the PARKED paragraph beneath it) is where a seat learns it in context.
- **6 slash commands** (`.claude/commands/*.md`) — top-level command definitions (the `expert-audit` alias stub was deleted 2026-10-26).
- **8 templates** (`.claude/templates/`) — reusable output skeletons.
- **384 project-memory files** (`.claude/project-memory/`) — persistent decisions, feedback, and references that survive across sessions.
- **~2200 numbered lessons** in `meta/MEMORY.md` (with renumber gaps).
- **1 catalogued external system** in this copy, of ten in the source project, as expert-level reference points (`external-*` skills), plus a comparison-only tier in `meta/COMPARISON.md` for systems that sit below the expert-admission bar. The one shipped, `external-fagemx-edda`, comes with its agent as a worked example; the other nine catalog skills, their agents and the comparison file are kept in the source project and not shipped.

That is enough complexity that the implicit map a single operator carries in their head is no longer reliable. Someone returning after two weeks of context loss, or onboarding to the project, needs an external map. This document is that map.

It also serves a second purpose: a baseline for future comparisons. When we revisit the system in three months and ask "what changed and was it good?", or when we adopt a pattern from an external system and want to know how it fits, we need a stable description of the present to compare against.

A third purpose, less obvious: writing this forced us to articulate the *theory* behind decisions that were made one-at-a-time over months. Several improvement vectors surfaced only while writing, and have since been queued or shipped.

### Independent review is the other half of the system

⛔ **Every non-trivial change is built by one session and read by another that did not write it** — a fresh context, briefed to find what is wrong rather than to confirm that the work is fine. This is not process decoration. It is the layer that makes everything above it trustworthy, and it is as load-bearing as the building layer.

**Why it has to exist.** A model's error rate rises with the size of its context and the number of moving parts in flight, and the context that produced a mistake is the worst-placed reader of it: the same reasoning that made the claim finds it plausible on re-read. Correctness therefore cannot rest on the builder checking its own work, however careful that builder is. The reviewer's independence from the builder is the mechanism, not the ceremony.

**What enforces it, each unpacked in its own lecture:**

- **The review hub** (`/review-hub`, Lecture 7) — a standing session that runs a builder≠breaker panel over each delegated commit for the whole fleet, so a working session has a standing destination for a diff **whenever the seat is held**. It is not always held: the normal succession (`--await` in the incoming session, then `--handover` in the incumbent — five steps, since 2026-09-12) stamps `.retiring` with the successor's sid before any broadcast so no election window opens, but the fallback `--retire` sequence (seven steps) can end in a declared VACANCY, and the fleet runs through those by election rather than by every peer quietly running its own panel.
- **`/expert-review --code`** (Lecture 7) — the review mode itself: a panel sized to what the diff actually touches, over the real changes rather than a description of them.
- **The completion check's own fix review** (`/audit-check` **conditional** Check 13, the Fix-Wave Review Gate, Lecture 7) — above the `--code` threshold, or where the wave touches codified policy, the wave of fixes an audit produces is itself reviewed before the audit may report COMPLETE. Below that threshold the check is N/A.
- **Two wired hooks** (Lecture 5) — `delegate-code-review-warn.sh` fires at an Agent dispatch that looks like a code review while a peer is live, arguing *delegate rather than run it inline*; `commit-review-warn.sh` fires after a `git commit` touching `src/`, arguing *get the review before you report done*. ⚠️ **Both WARN and neither blocks**, each has a named escape, and between them they leave two holes worth naming: a solo session with no live peer trips neither, and a commit touching no `src/` file — a rules, docs or memory change, which is most of the meta-system's own traffic — trips neither either.
- **A model rule** — the breaker is never given a weaker model than the builder, except in a hub review, where the rule gives way: the Opus hub reviews Fable-built work for cost, while a working session's own panels and breakers keep the rule.
- **A closure rule** — a loop is closed only when the verdict arrived, it approved, zero follow-ups remain (non-blocking ones count), and, where the fold rewrites prose no test reads, a non-author has read that fold. There is no exception for a fold that touches only prose or records: any outstanding read holds the close while the seat that owes it is live, whatever the fold touches — the wrap still runs and the close waits after it; only a seat that has CLOSED or EXITED (its lifecycle state, never its silence) releases it, and the close then names the read that will not arrive.

**And the limits, which are part of the principle.** A clean review is evidence, not proof. Reviewer and builder are usually drawn from the same model family and share blind spots, so two clean reads are not two independent checks, and a flaw encoded in the frame survives every lens inside that frame. The enforcement is also thinner than the list above reads: the two hooks warn rather than block, and **the plain `--code` mode's author-exclusion rule is prose, not a hook** — builder≠breaker is codified as a hard constraint at the audit chain's Step 2b, the deep probe and the completeness auditor, and the `--code` mode itself states who reviews: never the author; the hub, else fresh sub-agents given only the commits. Nothing mechanical stops an author running `--code` inline, which is what the review hub is for. What a review buys is a different context reading the artifact — the cheapest correction this system has, and the only one that reliably catches what the builder cannot see from inside its own reasoning.

## Lecture 1 — Foundations: What is Claude Code?

> **TL;DR.** Claude Code is three things stacked: a model in a loop, a tool harness, and a configuration surface (`.claude/`). Everything in this document is configuration layered on that base loop, designed around a single principle: **always-loaded vs. on-demand**.

Claude Code is Anthropic's official command-line interface for Claude. Conceptually it is three things stacked:

1. **A language model in a loop.** A Claude model receives a conversation context and a list of available tools. It can either reply to the user, or call a tool. Tool results return as new messages. The loop continues until the model stops calling tools and produces a final reply, or until the user interrupts.
2. **A tool harness.** Claude Code provides the model with tools to read and write files, run shell commands, search the codebase, spawn sub-agents, schedule wake-ups, persist memory, and interact with external services (git, GitHub, Vercel, MCP servers, etc.). These are the *actions* the model can take.
3. **A configuration surface.** Inside any directory tree, a `.claude/` folder configures how the model behaves: which rules apply, which hooks fire on which events, which skills the model can invoke, which agents it can spawn, what gets loaded into context at session start.

If you understand only this much, you understand the rest by composition. Everything that follows — skills, rules, hooks, agents, slash commands, memory, the meta layer — is *configuration* layered on top of the base loop, designed to shape the model's behavior on a specific project.

### Conventions you'll encounter

Terms used throughout this document, defined here so you don't have to chase them down later:

- **`F<N>` and `Flow #<N>`** — internal trackers. `F<N>` = feature audits. `Flow #<N>` = critical-path UX flows audited end-to-end.
- **`P0` / `P1` / `P2` / `P3`** — severity classes from `/expert-review` synthesis (P0 = launch-blocker, P3 = post-launch nice-to-have). A `--code` review of a diff asks its reviewers for P0 to P2 only.
- **`L<N>`** — numbered lessons in `.claude/skills/meta/MEMORY.md`. When you see `L<N> (verify-codification grep)`, the number identifies the lesson and the parenthetical is a topic tag (the renumber-drift mitigation rationale is in `state.md` — its "Renumber drift" fragility entry and the topic-tag convention in its Part 2).
- **`D+I+S`** — Durability + Impact + Scope (each 0–3) for promoting lessons to MEMORY/RULES. Total ≥6 promotes; 4–5 watch; ≤3 ignore. Introduced in Lecture 8.
- **`Capture → Curate → Enforce`** — the central architectural lens. Capture = passive signal collection; Curate = active triage (`/meta learn`, `/meta memory-audit`); Enforce = mechanical activation (rules, hooks, skill-lint). Introduced in Lecture 9.

### The conversational loop in practice

A single turn looks like this:

1. User sends a message (or invokes a slash command).
2. The harness assembles context: system prompt, prior conversation, available tools, any always-loaded files (CLAUDE.md, project memory MEMORY.md, certain rule files).
3. The model produces a response, which may include zero or more tool calls. Tool calls are issued as structured JSON.
4. The harness executes the tool calls in order (or in parallel if the model dispatched them in a single block). Some tool calls require user permission depending on permission mode.
5. Tool results are appended to the conversation and the loop returns to step 3.
6. When the model produces only text (no tool calls), that text is shown to the user and the turn ends.

There are a few subtleties worth noting now, because they shape later design choices:

- **The conversation is persistent within a session, but ephemeral across sessions.** When you close Claude Code and re-open, the next session is fresh. Memory files, git state, and the filesystem are the *only* things that survive.
- **Context length is finite but elastic.** Modern Claude models (Opus-class; measured ≥~516k tokens live on claude-opus-5, 2026-08-01) have very large context windows, but eventually conversations grow long enough to trigger compaction — the harness summarizes prior turns to free space. Compaction is mostly transparent, but it loses fine-grained detail.
- **Tool calls have cost.** Each tool call is a round trip; each loaded file is tokens. Designing for low-friction interaction means *not* loading 119 skill specifications into every conversation.

That last point is the seed of the whole architecture. The system we describe in the following lectures is, fundamentally, an answer to the question: *how do you give a model access to deep, project-specific expertise without paying the token cost of loading all of it every turn?*

### What's "always loaded" vs. "loaded on demand"

In our system, the following are *always* in the model's context at session start:

- `CLAUDE.md` at the project root (which `@AGENTS.md` extends).
- `.claude/project-memory/MEMORY.md` (the project memory index — the harness truncates it at a cliff measured in CHARACTERS, bounded not pinned — no banner at 24,964 chars, a banner at 25,300 — and announces the truncation; the vendor page's nominal 200-line / 25 KB figure was refuted on both unit and number on 2026-08-13 and this bullet carried it until 2026-10-11; the repo's gate is `CAP_BYTES` + `CAP_LINES` in `check-memory-budget.sh`, read both there).
- ⛔ NOT the user's profile or the feedback memories: `user_profile.md` and its sibling entry files are recalled on demand through the index above, never resident (this bullet asserted the opposite until 2026-10-09; the memory-type table in Lecture 3 had it right).
- Files in `.claude/rules/` — ⛔ **NOT "all 19, unconditionally" any more. Path-scoping shipped 2026-08-18 and this line asserted the opposite until 2026-08-24.** Measured 2026-09-27: **3 of 19 are resident** (`bash-environment` · `migrations` · `security`); **16 carry real `paths:` frontmatter** and join on a matching read — derive the set with `grep -l -F 'paths: [' .claude/rules/*.md`, never restate it (this line said 9 resident / 10 scoped from 2026-08-24 until today while Lecture 4 already read 3 / 16). **ZERO carry a `globs:` line in any form** (`grep -l '^globs:' .claude/rules/*.md` → 0), so the "eleven inert hints" clause is doubly dead. Lecture 4 has the mechanism; `CLAUDE.md`'s router (a table of the fourteen live scoped files plus the PARKED paragraph naming the other two) is the ONLY place a scoped file's existence can be learned in context — the harness strips frontmatter before injection, so a scoped rule cannot announce its own scoping.
- The orchestrator plane — `.claude/orchestrator/conventions.md` + `session-doctrine.md`, delivered to the MAIN session by `orchestrator-inject.sh` at every SessionStart (startup, resume, clear and compact; 25 registered parts in `settings.json`) — or, for a session launched through `scripts/claude-main.sh` (2026-10-07), placed in the SYSTEM PROMPT via `--append-system-prompt-file`, so it is cache-shareable and survives a `/compact`, with the hook skipped by `SKIP_ORCHESTRATOR_INJECT=1`. A dispatched sub-agent never receives it at launch (Lecture 4), though its own compaction re-fires SessionStart inside it and delivers the parts (the hook's header). Per-command deliveries (`.claude/traps/shell-traps.md` via `shell-trap-inject.sh`, the commit doctrine on the first commit-shaped Bash call) are on-demand, not resident.

Everything else — skill specs, expert MEMORY.md files, agent definitions, templates — is loaded *only when invoked*. A slash command like `/expert-review` loads the orchestration skill. An agent spawn loads that agent's definition. A skill invocation loads its SKILL.md and (depending on size) its MEMORY.md.

This always/on-demand split is the first architectural choice you should internalize. Every subsequent design decision is shaped by it.

## Lecture 2 — The Skill Abstraction

> **TL;DR.** A skill is a named, invocable bundle of expertise — at minimum a `SKILL.md`. Two kinds: **command skills** (recipes, stateless) and **domain experts** (stateful, with MEMORY). A third pattern emerged 2026-05-17: **auto-fired meta-procedures** that fire on triggers, not user invocation.

A **skill** is a named, invocable bundle of expertise. Skills live in `.claude/skills/<skill-name>/`. The minimum skill is one file: `SKILL.md`. Most non-trivial skills add 1–3 more files.

### The canonical skill file layout

```
.claude/skills/<skill-name>/
  SKILL.md              # Spec: who/what/when/how. Loaded when skill is invoked.
  MEMORY.md             # Two-tier ROUTER (digest + shard manifest), read at consult-start per SKILL.md § Memory.
  MEMORY-ARCHIVE*.md    # Dated body shards (40 skills at 2026-10-27) — grep the DIR, never MEMORY.md alone.
  config.md             # (premortem only) Per-project trigger classes + expert routing.
  CHANGELOG.md          # Version history of spec edits.
  RULES.md              # (Optional) Active-recall lookup table for fast trigger-matching.
  references/           # (Optional) Files referenced from SKILL.md for progressive disclosure.
  COMPARISON.md         # (Only on meta/) Cross-system capability matrix; kept in the source project, not shipped.
```

The mandatory file is `SKILL.md`. Everything else is added when the skill grows beyond what a single spec can hold.

### Invocation modes

Skills can enter the conversation context in three ways:

1. **Slash invocation.** The user types `/orient` (or any other skill name with a matching SKILL.md). The harness loads that skill's files and the model executes its procedure.
2. **Agent-bundled invocation.** When `/expert-review` composes a panel, it spawns sub-agents that load specific skills internally. The orchestrator never directly loads those skills.
3. **Direct programmatic invocation.** Via the `Skill` tool (available to the model), the orchestrator can fire a sub-skill without user intent. Example: `/wrap` auto-invokes `/deep-pass` (Step 1b-DEEP, huge or multiday sessions), `/hanging-work`, `/meta learn`, `/session-memory`, `/decisions`, `/me learn-session`, `/meta architecture-audit` (Step 7d, when its trigger fires), `/meta corrections --scan --current` (Step 7f — its canonical form; the spec runs the scan script directly), (after a compaction) `/post-compact` and (Step 2, since 2026-10-25, when the headroom read before a `/meta` call is under 100,000) `/pre-compact` as sub-skills, with `/push` as its optional last step — eleven, not the three this line used to name (it read six until 2026-10-11, then eight without 7d and 1b-DEEP, then nine without 1b-DEEP, then ten without `/pre-compact`), which matters because the sub-skill discipline (when a spec says invoke X, fire X) is enforced against the whole set.

The distinction between (1) and (3) is subtle but important. A slash invocation by the user is durable — the user knows they ran it. A programmatic sub-skill invocation by the orchestrator must follow strict rules: it must be in the parent skill's spec, and it cannot be silently swallowed (the orchestrator conventions force (`.claude/orchestrator/conventions.md` § Slash-command sub-skills, main-session-only since it left `AGENTS.md` on 2026-09-03): when a slash command's SKILL.md spec says invoke X, fire it via the `Skill` tool — never inline-summarize it).

**The `Skill` tool itself** is one of the orchestrator-facing tools Claude Code provides (alongside Read, Edit, Write, Bash, Agent, etc.). When the orchestrator decides to fire a sub-skill, it makes a structured tool call with `skill: "<skill-name>"` and optional `args: "<argument-string>"`. The harness resolves the skill name to its SKILL.md path, loads the spec into the conversation context, and the model executes the procedure described there. From the orchestrator's perspective, invoking a sub-skill is the same shape as invoking any other tool — but the *consequence* is a sub-procedure that may make further tool calls of its own. This is how `/wrap` can compose its eleven sub-skills (the set named above) in a single turn while preserving each sub-skill's internal discipline.

### Frontmatter declarations that shape behavior

Skill frontmatter is not just metadata — it changes how the orchestrator treats the skill. The most load-bearing fields:

- `name`, `description` — used for routing and discovery.
- `skepticism: low|medium|high` — biases the orchestrator's panel composition. Adopted from `wan-huiyan/agent-review-panel`. High-skepticism experts (security-expert, qa-expert) are heavier hitters in critical audits; low-skepticism experts (ux-copywriter, seo-content-strategist) are appropriate for greenfield exploration.
- `model:` — the declared model tier, adopted from `wshobson/agents` and shipped in our v2.8.3. The field lives in `.claude/agents/*.md`, not in skill specs (corrected 2026-05-18). One value is in use: **every agent definition in the copy declares `model: inherit`** (skill-lint `AGENT_MODEL_PIN` refuses any other value), so a dispatch that names no model runs on the session's. Before that, the source project's definitions declared `opus` (most of them) or `sonnet`; the 34th file under `.claude/agents/` is `_agent-primer.md`, which is a preamble, not an agent. The decision is the dispatch-time routing policy — see Lecture 6.
- `checks:` — the tests and scripts an expert owns (9 of the copy's 87 skills carry it); the review hub and `/meta` bind an expert to its check list through it.
- `applies_when.paths` — path globs that route a file-scoped review to the expert (9 skills). 33 of the copy's 87 skills carry `skepticism` (6 high / 21 medium / 6 low): the 33 expert skills, one each; the 54 workflow-command skills carry none.

### Why "skills" instead of "agents"?

Claude Code provides both primitives: skills and agents. The conceptual distinction we settled on:

- **Skill = expertise + state + spec.** A skill *is* a persistent capability with its own memory.
- **Agent = an isolated sub-process running with a specific skill loaded.** Agents are *invocations* of skills (or compositions of skills) in a fresh context.

Most of our domain experts have both a skill (`.claude/skills/security-expert/`) and a matching agent (`.claude/agents/security-expert.md`). The skill holds the lasting knowledge; the agent is the subprocess that loads that knowledge to do work. Command skills (like `/orient`) intentionally have *no* matching agent — they are orchestrator-only procedures, not parallelizable work.

## Lecture 3 — Memory: Persistence Across Sessions

> **TL;DR.** Memory exists at four tiers (project / skill / meta / the session working plan, which persists across compactions rather than sessions) and in four types (user / feedback / project / reference). The hardest problem is hygiene — capture pressure, retrieval pressure, and staleness pressure fight each other. The system addresses each with `/meta learn` + `/meta distill` + size hooks + spot-checks.

Sessions are ephemeral. Memory is how we make accumulated decisions and learnings persist.

### The four memory tiers

The system has memory at four tiers, each with different scope and lifecycle:

**Tier 1 — Project memory.** ⛔ **The direction is the opposite of what this said: the real directory is `.claude/project-memory/` inside the repo (git-tracked), and `~/.claude/projects/<project-key>/memory` is a SYMLINK pointing at it.** That matters — the files are the repo's, and the harness path is the pointer, which is why `./scripts/setup-project-memory.sh` recreates the link after a fresh clone rather than recreating the files. This is the auto-memory system Claude Code provides natively. It contains user/feedback/project/reference entries scoped to this project. The harness loads `MEMORY.md` (the index) into every session automatically; individual entry files are loaded on demand when their description matches the conversation.

**Tier 2 — Skill memory.** Each skill has its own `MEMORY.md` (`.claude/skills/<skill>/MEMORY.md`). Loaded only when the skill is invoked. Holds skill-specific decisions, evidence, and revisit triggers.

**Tier 3 — Meta memory.** `meta/MEMORY.md` — a router since 2026-08-06 over the dated `MEMORY-ARCHIVE-*.md` shards that hold the bodies — is the system's narrative source-of-truth: ~2200 distinct lessons (with renumber gaps), the Panel Playbook, evolution timeline, structural gaps. Loaded when `/meta` is invoked. Companion file `meta/RULES.md` is the trigger→action lookup — since 2026-09-04 a router over section-keyed `RULES-SHARD-NN-<A>-<Z>.md` shards, so grep the directory, never the file — read on `/meta` alongside MEMORY. A **fifth meta surface** shipped 2026-05-25 sits alongside but at different granularity: `.claude/meta-corrections-registry.md` is the **capture layer** for owner-pushback-correction events — high-volume, append-only, owner-triaged. Registry feeds /meta MEMORY (the **curation layer** — formal L# codification with D+I+S scoring). See Lecture 8 `/meta corrections` entry-point description for the full feeder→codifier relationship.

**Tier 4 — the session working plan** (`plans/session-<sid8>-<date>.md`). Added to this lecture 2026-09-14; it had been absent from the doc entirely while being load-bearing in three separate commands, which is the sort of gap a reader only finds by falling into it. The other three tiers persist across sessions and are *about* the system; this one persists across **compactions** and is about the work in flight. It is the re-read path after a context loss — the one artifact a recovering seat can trust when its own context is gone — and `/post-compact` is required to bring it current at every compaction, on the reasoning that a compaction is exactly when the plan stops being redundant with your context and becomes the only copy. `/working-plan`, `/summary`, `/pre-compact`, `/pause`, `/standby`, `/limit-recovery`, `/circuit-break`, `/sanity-check`, `/reach-plan` and a retiring `/review-hub` also write it, each its own dated block or line (this clause read "nothing else may" until 2026-10-14), and it is the file `/wrap` is expected to read its closability verdict *from* rather than composing one from memory (the conventions' closability row says so, and `session-start.sh`'s working-plan announcement repeats it whenever the session's plan file exists — both reach every main session at start, resume and compaction; the `/wrap` spec itself does not name the read). Corrections REPLACE the text they correct, rows are edited in place rather than aged out, and a stale verdict is superseded by a dated block rather than edited — so the file accumulates its own history instead of overwriting it.

### The four memory types

Within project memory, every entry declares a type — in one of two frontmatter shapes that coexist: the harness's nested `metadata:` → `type:` (247 of 362 files at 2026-10-11) and an older flat top-level `type:` (98 files); 17 files declare neither (the two indexes, the twelve shards of the flows tracker, three bodies). Derive with `grep -l -E '^  type:'` and `grep -l -E '^type:'` over `.claude/project-memory/*.md`. (This sentence said "every entry has a `metadata.type` declaration" until 2026-10-11.) The four types:

- **`user`** — facts about who the user is (role, expertise, preferences). The user-profile entry is **loaded on demand like any other entry file, not always-loaded**; it appears in neither `CLAUDE.md` nor `AGENTS.md`, so a rule that needs to fire unprompted cannot live there.
- **`feedback`** — guidance the user has given about *how to work* (corrections + validations).
- **`project`** — facts about ongoing work, decisions, project state.
- **`reference`** — pointers to where information lives in external systems. Example: which hosted service's dashboard holds a given setting.

The type matters because it shapes both *when to write* (different signals trigger different types) and *when to retrieve* (the orchestrator's mental model of "where did we decide that?" follows the type taxonomy).

### Memory file structure

Every memory file follows the same shape:

```markdown
---
name: free-text title (older files; newer ones use a kebab slug)
description: One-line summary used for relevance matching
metadata:
  type: user | feedback | project | reference
---

{body — for feedback/project entries, structured as:
- Rule / fact
- **Why:** the motivation
- **How to apply:** when this fires}
```

The frontmatter `description` is load-bearing: it is the line the orchestrator sees when scanning memory for relevance. A vague description ("notes about X") will be skipped. A specific one ("Integration tests auto-manage Docker — use npm run test:integration") will be loaded when its keywords match the current task.

### The MEMORY.md index

The index file (`MEMORY.md`) is *always* loaded into context. The harness hard-caps it at **min(200 lines, ~24.4 KB of characters)** (bounded 24,964-25,300, never pinned; the gate is `CAP_BYTES` bytes) and truncates the tail past *either* bound — and it ANNOUNCES that with a banner; what it never names is WHICH rows it dropped, so the enforcement you lose is unattributable. ⛔ This sentence read "min(200 lines, 25 KB)" and "SILENTLY truncates" until 2026-09-01. Both halves were already refuted — the unit and number on 2026-08-13 (the cap is 24.4 KiB of *characters*; `CAP_BYTES=24985` enforces bytes against it deliberately, since bytes ≥ chars), the silence on 2026-08-25 — and the retired form contradicted this document's own correction two paragraphs below. The binding constraint is usually **bytes, not lines** (the 2026-06-01 breach was 176 lines but 26 KB, which dropped the vendor `reference_*` tail every session until caught; codified). Entries follow a one-line format: `- [Title](file.md) — one-line hook`. The index is organized topically (not chronologically) so the orchestrator can scan it like a table of contents.

**Hot/cold split (2026-06-01).** After the byte breach above, the index was split into a hot and a cold file:

### Why symlinks?

A non-obvious design choice: project memory files live in `.claude/project-memory/` inside the repo, and `~/.claude/projects/<key>/memory` — the location Claude Code's harness reads automatically — is a symlink pointing at that directory. Getting the direction right matters when you are restoring one: the repo holds the files, the home path holds the link. This dual location lets us:

1. Let the harness load them automatically (it expects the user-home path).
2. Track them in git (so they survive across machines, can be reviewed via PRs, and accumulate history).
3. Have a single source of truth (symlinks resolve to one file on disk).

A `scripts/setup-project-memory.sh` script recreates the symlink on a fresh clone. This was learned the hard way after multiple incidents of losing memory when switching machines.

### Memory hygiene: the unhappy path

The hardest problem in this system is *not letting memory grow into noise*. Three pressures fight each other:

1. **Capture pressure.** Every session produces new decisions; if we don't write them down, we lose them.
2. **Retrieval pressure.** Every persisted entry costs tokens to scan; if we write too many, retrieval becomes lossy.
3. **Staleness pressure.** Decisions decay (code moves, plans change). An old memory that *looks* authoritative but is stale is worse than no memory.

The system addresses each with explicit mechanisms:

- `/meta learn` (Lecture 8) extracts new lessons at session-end with a quantitative promotion rubric (Durability + Impact + Scope, 0–3 each; promote ≥6, watch 4–5, drop ≤3).
- `/meta review --hygiene` (legacy name `/meta memory-audit`) and `/meta distill` prune absorbed/stale entries (the latter explicitly *deletes* sources after promoting their content into prescriptive patterns).
- `check-memory-size.sh` hook fires at write-time. ⛔ **The 4,000-LINE URGENT tier this bullet described was RETIRED on 2026-08-01 as structurally blind** (the hook says so in its own header) — and the escalation history it recited (1500→2000→3000→4000) was a chase up the wrong axis. Scale check: the rules directory alone measured 684,535 B on 2026-09-14 (it was ~379 KB on 2026-08-02) — the byte gate governs far more text than the Band-U row governor does. And the ceiling moves: it was raised three times in four days (330 → 400 → 440 KB, 2026-07-29 → 08-02; ⚠️ it has since gone 473 → 825 KB across seven further raises, and `BLOCK_BYTES` has not been the corpus plane's live ceiling since 2026-08-13 — a ratchet on `observedMin + marginBytes` is; neither is the BINDING ceiling, which is the unscoped plane's. Read the basis block in `check-band-budget.mjs`, never this figure), each with a documented basis in the script's own ratchet log. **A limit that moves three times in four days is not a control; write-path discipline is.**

That reading is what produced the **narrative-demotion doctrine** (a 2026-08-01 panel), which governs the *topical* rule bodies where the byte weight actually sits — distinct from the row-level promote/demote rules above. The demotion unit is the **NARRATIVE, never the rule**: the incident story, the measured numbers, the "distinct from L#" lineage. What stays is a ≤2-line directive plus a pointer to the L# body that now holds the narrative — and a rule whose directive cannot survive that compression is not demotable, it is under-written. Three conditions bound it:

- **(a) Demote iff enforcement-redundant** — a *named, shipped* sentinel / hook / test REDs on violation, and the pointer names it. An unnamed "CI probably catches this" is not the criterion. This direction is fail-safe by construction: the worst case of a wrong demotion is wasted work that CI then catches, not a shipped defect.
- **(b) Unless the blast radius precedes any backstop** — a prod push, real money spent, peer WIP destroyed, a secret leaked, durable memory corrupted. A test that REDs after the money is gone is not a backstop, so those rules stay hot however well-tested they are.
- **(c) Applicability keys on task content at dispatch — never on file-glob or agent-type.** Kinship of implementation is not kinship of obligation; this is the same axis error the `globs:` hints below embody.

It is explicitly **never a bulk byte-ranked pass** — demote at next-touch, one rule at a time, by the seat already reading it. One governor gap is worth carrying: a "cap-neutral fold" satisfies the Band-U *row* governor while growing the *byte* gate silently, so folding a lesson into an existing row is not automatically byte-free. The row governor itself is WARN, never block.

Two further governors sit under those band caps: **each action cell ≤ 50 words *per lesson it carries*** (a row merging N lessons gets ~50 words each — not a standalone token budget; the old ≤2000-token target was inherited, unachievable at our scale, and dropped 2026-06-01), and a **cap-breach escape valve** permitting the Band-U row cap to be exceeded only as a documented last resort — when no demotable row exists AND the lesson can't live one tier down — justified in the commit message + a CHANGELOG line. The retired flat-60 model had its own raise history (40→42→43→48→60, the 48/48 promotion-deadlock, and the 3-expert consult that ended in the 2026-07-12 2-band split), archived out of the live router. Goal = firing effectiveness (the right rule fires at composition time), not token reduction; the band is scanned before composing any non-trivial output. Demotion rule: rows that haven't fired in ~10 consecutive sessions demote back to `meta/RULES.md` deep catalog, OR are absorbed into a hook / skill-lint detector / always-loaded `.claude/rules/*.md` constraint (trigger-PRESENCE instrumentation exists — `scripts/rules-trigger-firerate.mjs` prints the TRUE-DEAD genuine-trigger set and runs as `/meta self-audit` Check 11, so every self-audit and `/meta maintain` pass reads it — though while all three of its sources are parked (since 2026-09-07) it prints "ALL 3 SOURCES ARE PARKED" and reports the TRUE-DEAD set as VOID; demotion stays a human judgment grounded on the measured deadness, never auto-enforced. Its 27 zero-fire triggers were the evidenced starting point for the 2026-09-07 park. Rule-ACTION firing on prose remains un-instrumented — `state.md` § Velocity health).

### Path scoping — the design intent that DID get a mechanism (2026-08-18)

Path scoping **shipped on 2026-08-18** and has widened three times since. Measured 2026-09-14: **16 of the 19 rule files carry real `paths:` YAML frontmatter** and load on a matching read (re-derive with `grep -l -F 'paths: [' .claude/rules/*.md`); only `bash-environment.md`, `migrations.md` and `security.md` are always-loaded. **ZERO carry a `globs:` frontmatter key** (`grep -l '^globs:' .claude/rules/*.md` → 0); two retain a dead `<!-- globs: -->` *comment* (`actions.md`, `migrations.md`; `tests-unit.md` records having replaced its own). The live shape, from `tests-integration.md`:

```yaml

---
# Integration Test Rules
⛔ **PATH-SCOPED — NOT always-loaded (2026-08-18).**
```

The scoped sixteen fall into three groups: the domain files that load when their code is touched (`actions` · `api-routes` · `components` · `copy` · `i18n` · `nextjs` · `processing` · `prompts` · `supabase` · `tests-e2e` · `tests-integration` · `tests-unit` · `typescript` — `tests-unit` as the 2026-08-17 pilot, nine more on 2026-08-18, `copy` · `i18n` · `typescript` on 2026-08-25); `session-cadence`, which loads on the meta-system surfaces (2026-08-26, narrowed 2026-09-03); and the two exhortation files parked on 2026-09-07 by scoping them to the rules archive. **`CLAUDE.md`'s router (table + PARKED paragraph) is the ONLY in-context place a scoped file's existence can be learned; the authoritative SET is the `grep` above** — the harness strips frontmatter before injection, so a scoped rule cannot announce its own scoping, and a compaction does not re-inject one.

**What the mechanism is worth, and the three traps in measuring it.** The three resident files measured 193,340 B of the directory's 684,535 B on 2026-09-14, so a session that touches none of the scoped surfaces is spared roughly 72% of the rules bytes; the pilot file alone (`tests-unit.md`, 66,186 B when scoped) was absent from every `session_start` load event for a session that never touched `tests/**`. But: counting `path_glob_match` FIRES values it **backwards** (a fire is an occasion where scoping FAILED to save you); counting ABSENCES overstates the saving ~2.3×; and residency **decays** — measured 4 of 7 compactions re-injected a scoped file and 3 did not. Net = (full-corpus events × size) − (all deliveries × size).

**The sub-agent plane, stated precisely.** An **unmatched** scoped rule is excluded from a dispatched sub-agent's payload, and a sub-agent that *reads* a matching file receives the rule mid-run — both measured in throwaway-repo rigs with positive and negative controls and corroborated at runtime by the `InstructionsLoaded` hook. The remaining first-touch gap is creation: a glob cannot fire on a file that is being written fresh. `write-scope-inject.sh` NARROWS it and does not close it — its pointer rides `additionalContext` with no deny, so the Write has already landed when the seat first reads *"READ the file(s) above BEFORE writing this one"*, and a file created through Bash fires neither the glob nor the hook. **And agent type DOES gate the resident half:** `Explore` and `Plan` receive none of `CLAUDE.md` or the three unscoped rules (vendor-documented; `conventions.md` § What a built-in read-only seat actually holds), while a matching read still delivers a scoped rule inside them. The byte figures above are **orchestrator-only as measured** — a statement about which population was counted, not about what sub-agents receive.

**Two consequences for the rest of this document.** First, Lecture 1's always-loaded / on-demand split no longer runs cleanly between `.claude/rules/` and everything else; the line now cuts *through* the rules directory. Second, the comparison with the INVARIANTS.md of `vinicius91carvalho/.claude` (a flat, project-wide contract of executable checks) has now inverted **twice**: this document first set our glob-scoped rules against their flat contract, the 2026-08-02 correction said both are flat global contracts, and that correction is itself superseded, since our rules are now path-scoped against their flat contract. It is NOT *"cannot silently fail"*: creation gets a post-write pointer, a Bash-created file gets nothing, and a compaction drops a scoped rule until the next matching read (the decay figure above). ⚠️ And, keying applicability on file-glob is still the wrong axis for an *obligation*: implementation kinship is not obligation kinship, which is why `CLAUDE.md`'s table is keyed on INTENT ("about to write a unit test") rather than on the path a glob would match.

### The orchestrator plane — doctrine only the main session receives (2026-09-03)

Scoping answers *when* a rule loads; a second split answers *who* receives it. Some doctrine binds acts only the main session can perform — dispatching agents, mailing peers, committing, delegating a review, choosing the reply's mode marker — and a sub-agent holding it pays for rules it can never apply. ### `bash-environment.md` — measured facts, not conventions

Most rule files encode a *convention* — what we have decided to do. `bash-environment.md` encodes measured *facts about this machine*, and every entry is a failure whose signature is a command that appears to succeed while doing nothing, or a number that is fiction. Three of the four examples that follow left this file for `.claude/traps/shell-traps.md` on 2026-09-21 and now arrive per matching Bash call; only the word-split rule is still resident. There is no `timeout` binary here, so `timeout 60 <cmd>` returns rc=127 and the command never runs at all — and a pipe hides it, because a pipeline's status is the last stage's. zsh does not word-split, so an unquoted `$FILES` reaches `git add` as one bogus pathspec and nothing stages. The userland is BSD rather than GNU, so a long flag you know from Linux is rejected on *stderr* with no stdout, and the `2>/dev/null` you added for tidiness converts that into a clean-looking zero. Backticks inside a double-quoted `git commit -m` are command-substituted, so the message that lands is not the message you wrote.

Why it is a rule and not a memory entry is worth naming, because it is the decision tree below applied under a constraint. The project auto-memory index is hard-capped (`CAP_BYTES` in `check-memory-budget.sh`; the harness truncates the tail and announces it, but never names which rows it dropped — Lecture 3) and had no room when these rows needed a home; an unscoped `.claude/rules/` file is uncapped and — the decisive property — re-sent on every sub-agent dispatch. Sub-agents are precisely who keeps hitting these traps: three deep-pass agents burned `timeout` on 2026-07-31 and recorded rc=127 as data. That is relief-ladder step 4 (route to a topical rule file) from the cap-collision procedure in `active-recall.md` (parked with that file since 2026-09-07), and it strictly widened reach rather than trading it. It is also why this file stayed loaded through the park: it records facts about the environment, which the park's policy separates from exhortation.

### What goes in a rule vs. a skill vs. a memory?

The decision tree:

- **If it's a hard constraint that applies to many files and has no judgment component → rule.** Example: "Every server action must call `getAuthUserId()`."
- **If it's a recurring lesson learned from incidents (judgment + context) → memory.** Example: "Don't `git stash` when parallel sessions are active."
- **If it's a workflow procedure or domain knowledge → skill.** Example: how to compose an expert panel.

Rules are the most *enforceable* of the three (they can be reinforced by hooks, and `paths:` frontmatter delivers a scoped one at the moment its surface is touched). Memories are the most *contextual* (they encode why, when, what was tried before). Skills are the most *invokable* (they are explicit capabilities the orchestrator can fire).

### Rules grow from memories

Several rule files started as feedback memories. Pattern: a memory entry recurs across 5+ sessions, gets converted into a rule, and the original memory becomes a pointer. Example: `components.md` includes "Interactive `<button>` / `<a>` elements that declare a `hover:` style MUST also declare a `focus-visible:` style" — that began as a feedback memory after the second recurrence, was elevated to a rule after the fifth, and is now backed by a pre-push hook that HARD-blocks staged additions (promoted warn-mode → hard gate on 2026-05-27).

This *memory → rule → hook* promotion ladder is one of the system's most important patterns. Each rung increases enforcement strength:

1. **Memory:** advisory; relies on orchestrator recall.
2. **Rule:** auto-loaded; orchestrator sees it on every relevant edit.
3. **Hook:** mechanical; fires regardless of orchestrator's attention.

We will revisit this in Lecture 9.

## Lecture 5 — Hooks: Deterministic Enforcement

> **TL;DR.** Hooks are shell (and, since 2026-10-07, Python — six wired, two helpers) scripts wired to 9 of the 33 lifecycle events Claude Code documents (`SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PreCompact`, `Stop`, `SessionEnd`, `SubagentStart`, `InstructionsLoaded` — `settings.json` wires no `Notification` or `PostCompact` hook; the retired `PostCompact` restore's compact-recovery moved to `SessionStart`:compact). They fire regardless of the orchestrator's attention. Two disciplines hold the layer together: **warn-mode before block-mode** (warn-before-block discipline) and **smoke-test before ship** (hook smoke-test locally).

Hooks are shell or Python scripts that Claude Code runs in response to lifecycle events. Configured in `.claude/settings.json`, they fire deterministically — the model cannot "forget" them, ignore them, or talk its way around them. Hooks are the closest thing the system has to *real* enforcement.

### The hook events we wire (nine of thirty-three)

Claude Code documents 33 hook events (vendor hooks page, read 2026-09-14) and `settings.json` wires nine of them. Keep the two populations apart: an earlier version of this header transplanted the wired count onto the documented list and read "eight" for both. The nine we wire:

- **`SessionStart`** — when a new session begins (or a compacted one resumes).
- **`UserPromptSubmit`** — when the user sends a new message.
- **`PreToolUse`** — before any tool call. Can match by tool name (Bash, Edit, Write, MultiEdit, Read, Skill, Agent, SendMessage, Workflow, Monitor), or carry an empty matcher and fire on every tool.
- **`PostToolUse`** — after a tool call completes. Same matching plus `CronCreate` and `Grep` (`decisions-archive-zero-hit.py` is registered on `Bash|Grep`), empty matcher included (`auto-precompact-trigger.py` rides it).
- **`PreCompact`** — before context compaction.
- **`Stop`** — when the turn ends (model produced final text).
- **`SessionEnd`** — when the session truly exits (`reason` ∈ logout/prompt_input_exit — the field is `reason`, not `source`; the vendor reason set is `clear` · `resume` · `logout` · `prompt_input_exit` · `other` (`code.claude.com/docs/en/hooks` § SessionEnd), so `/clear` is DOCUMENTED to fire it with `reason: clear` and a normal exit with `reason: other` (the documented catch-all, which names normal exit), while `prompt_input_exit` is documented as stdin closing in non-interactive mode; #17885 (`/exit`) and #6428 (`/clear`) are bug reports closed as STALE, not confirmed fixes or confirmed behaviour, and this build is UNMEASURED because `session-lifecycle.py finished` discards any reason outside logout/prompt_input_exit without logging it — either way a session closed by `/exit` or `/clear` leaves no marker and reads ACTIVE — the jsonl-staleness backstop has since been removed). The only terminal signal — wired 2026-06-03 (session-lifecycle).
- **`SubagentStart`** — when a sub-agent is spawned; `log-subagent-dispatch.sh` records every dispatch by agent type (2026-09-04), and `subagent-cache-window-inject.sh` injects the five-minute cache-window advisory (2026-10-19).
- **`InstructionsLoaded`** — when a `CLAUDE.md` or `.claude/rules/*.md` file is loaded into context, at session start or lazily mid-session; `log-instructions-loaded.sh` writes the log Lecture 4's path-scoping measurements read from.

Two documented events are deliberately unwired: `PostCompact` (its output never reaches the model — compact recovery lives in `SessionStart`'s compact branch) and `Notification`.

Hook scripts receive structured JSON on stdin describing the event and exit with a status code. Exit 0 is success — and it is the code to use when the hook prints JSON for structured control, which is how most of ours deny: a PreToolUse hook blocks a call by emitting `permissionDecision: "deny"` with a reason. Exit 2 is a blocking error on the events that can block; any other non-zero exit does not block on its own. What reaches the model is the other half of the contract: `additionalContext` and a deny reason do, bare stderr does not (measured; `state.md` failure mode 11), and a hook's stdout must be exactly one JSON document or the harness discards all of it (`bash-environment.md`). **How a warn-only hook is launched.** Every warn-only bash hook on `UserPromptSubmit`, `PreToolUse` and `Stop` (26 scripts, 31 registrations) is wired as `bash .claude/hooks/lib/run-advisory.sh <hook>` followed by `|| { r=$?; [ $r -eq 2 ] && r=1; exit $r; }`, so its exit 2 (in practice a syntax error) reaches the harness as 1, a visible non-blocking error, and is logged to `.claude/logs/run-advisory-fires.jsonl`. A failing hook keeps a `.claude/state/run-advisory-failing-<hook>` marker that `session-start.sh` lists at every start until the hook runs clean; a syntax-error marker clears only once the file parses. Stdout passes through untouched, so an `additionalContext` document still lands. A hook that blocks on purpose is never wrapped, because a broken guard should still refuse: the deny guards, `check-memory-budget.sh`, `commit-doctrine-inject.sh`, `warn-large-tracker-read.sh` and `keep-warm-tool-deny.sh`; five of the six Python hooks and `keep-warm-tool-deny.sh` end in `|| exit 1` instead (the PostToolUse `decisions-archive-zero-hit.py` ends in `|| exit 0`). A test pins the wiring and the `BLOCKING` list.

### The hook-enforcement-over-instruction philosophy

The single most important pattern in our hook design, already practised here when `vinicius91carvalho/.claude` was studied, which gave it its sharpest statement: an instruction written into an always-loaded file is advice the model may or may not act on, while a hook is code the harness itself executes around each action, whatever the model is attending to.

Empirically, rules-only enforcement reaches roughly 85–90% adherence at best. The orchestrator is well-intentioned but its attention is finite, and rules drift to the bottom of context as sessions grow. Hooks are different: they fire regardless of the orchestrator's state. A hook that warns on `git add -A` will warn on the 50th turn of a 100-turn session, no different from the first.

This is why several lessons followed the progression: a recurring incident → a feedback memory → a rule → eventually a hook. Each rung up the ladder narrows the failure mode.

### Discipline: warn-mode before block-mode (warn-before-block discipline)

Our codified rule for shipping hooks: warn-mode first, then promote to block-mode once the false-positive rate is confirmed. The reasoning is that block-mode is hard to roll back mid-session (the user has to investigate and exempt), while warn-mode produces a friction signal we can measure cheaply — and a broken blocking hook can lock a session out of Write/Edit entirely, with no recovery path, so the flip is deliberately small (`exit 0` → `exit 2`, or a deny document) rather than a rewrite — though it is never one line: a warn-only hook runs through `.claude/hooks/lib/run-advisory.sh`, which turns its exit 2 into a non-blocking 1, so a promotion also unwraps it in `settings.json` and adds it to the pinned `BLOCKING` list.

**The warn-before-block discipline's own floor is ≥1 session, not five** — and its revisit clause runs the other way, forcing a decision at >3 sessions: promote, or accept warn-only permanently and drop the "promotion-pending" marker. Individual gates then set *stricter* bars for their own reasons, and those are per-gate facts rather than a fleet-wide number: `migration-column-acl-check.py`, for one, needs 5 observed pushes plus a further condition of its own. Quote the gate's bar from the gate; a single remembered figure for all of them has been wrong in both directions.

The exception: narrow-specificity regex hooks where false positives are structurally impossible can ship direct-to-block. `block-dangerous.sh`'s **catastrophic class** is the one that exercises it — `rm -rf /` and its kin have no legitimate use, so there is no warn-signal worth waiting for. (That same hook's SECOND class — the zsh word-split `$VAR` trap added 2026-06-29 — did NOT use the exception: it graduated warn→block the normal warn-before-block discipline way after its warn-mode proved insufficient.)

**The promotion gate for a STRING-MATCHING guard is narrower than that exception makes it look (measured at N=2 in one night).** The claim that buys a warn→block promotion is nearly always *"this shape has no legitimate use, so a false positive costs one rewrite."* That is a claim about what people **do**; a command-string guard enforces a claim about a **string**. The two diverge in exactly one place — the contexts that *mention* the pattern instead of running it: fixtures, verifiers, briefs, docs, commit messages. And a guard **manufactures** those contexts, so its false-positive rate *peaks* in the documentation burst immediately after promotion — the window a short observation samples and a long one misses. So the question to ask of the flagged text is: *does anyone ever have reason to WRITE this without RUNNING it?* Yes ⇒ stay warn (or accept a permanent, unfixable FP cost and say so out loud). No ⇒ block is safe.

Two corollaries fall out of it. **Calibrate per ARM, never per hook** — `grep-blowup-warn.sh` took **3/3 of the 2026-08-01 false positives** on the absolute-root arm (a path shape people write constantly), so the correct fix was a mode split, not a revert. ⛔ **The companion clause here read "and 0 of 3 on the backtracking-shape arm (a regex nobody quotes in prose)" until 2026-08-22, and that is a RETIRED claim** — it was struck at `.claude/rules/session-cadence.md` because the shape arm has since false-fired on real work, and it is the arm in BLOCK mode, so the retired sentence was the standing argument for keeping a fleet-wide blocking gate. **A per-arm FP count is a reading of ONE window, never a standing property of the arm** — re-derive it from `.claude/logs/grep-blowup-fires.jsonl` before any promote/demote argument leans on it, and note the ledger carries no classification fields, so a replay share is a predicate-difference rate and not an FP rate at all. *(This copy survived the 2026-08-19 fold because the fold's completeness grep searched `0/3` and this file spells it `0 of 3` — a single-spelling grep certifying a fold it could not see.)* And **read the FP rate with the same split**: a true positive (a real hazardous invocation, correctly blocked, costs one rewrite — *the guard working*) and a false positive (prose about the pattern, unfixable inside a string matcher — *a defect in the guard*) are indistinguishable from the outside, because both arrive as an interruption during legitimate work. Counting incidents without classifying them over-reports the FP rate and argues for weakening a guard that is behaving correctly. Two mechanical notes for authors: fixtures for a Bash-matching guard live in a **file**, never inline (an inline fixture is indistinguishable from the invocation it models, so the guard blocks its own test), and run `bash -n` before wiring and after every edit — a syntax error in a directly wired `PreToolUse(Bash)` guard with no `|| exit 1` tail exits 2 on every Bash call that reaches the broken line, so a fast-path `exit 0` above it still passes its calls (a warn-only hook runs through `run-advisory.sh`, which turns that 2 into a non-blocking 1). Bash parses one command at a time, so the hook's `SKIP_*` escape runs only if it executes above the broken line and outside any compound command that holds it (a function body or an `if` block is parsed whole: an escape inside `main() { … }` above the error still exits 2) — and it reaches a harness-spawned hook only through `settings.json`'s `env` block.

## Lecture 6 — Agents: Subprocesses and Personas

> **TL;DR.** Agents are subprocesses with isolated context that the orchestrator spawns. `/agent-work` parallelizes 1–5 specialists on independent files, halving wall-clock. `_agent-primer.md` is a **read-first pointer carried by all 56 project agent definitions — not an injection**, so a harness-provided agent type never sees it. Sub-agents emit `Memory Update:` blocks rather than writing MEMORY.md directly (hook-enforced).

Agents are subprocesses the orchestrator can spawn. They have their own context window, their own tool access, and they run independently to completion before returning a result to the orchestrator. Conceptually they are how the system *parallelizes* work and *isolates* concerns.

### The 57 agents in `.claude/agents/`

Agent definitions live as Markdown files. Most agents are 1:1 with a corresponding expert skill — `accessibility-expert.md` (agent) loads `accessibility-expert/SKILL.md` (skill) plus its MEMORY. The agent file declares:

- `name`, `description` — used by the orchestrator for routing.
- `model:` — `inherit` on all 56 agent definitions (skill-lint `AGENT_MODEL_PIN`); before that, 50 declared `opus` and 6 `sonnet`.
- `tools: ...` — which tools the agent can use. There are exactly **two shapes across the 56 agent definitions** (the 57th file, the primer, carries no `tools:` line), and reading them is more instructive than the count: 37 carry `Read, Write, Edit, Glob, Grep, Bash, WebFetch, WebSearch`, and 19 carry the same list minus `Write, Edit` (re-derived 2026-10-09).

⚠️ **`general-purpose`, `Explore`, `Plan`, `statusline-setup` and `claude` are HARNESS-PROVIDED agent types — they are not files in `.claude/agents/` and never have been** (`git log --all -- .claude/agents/general-purpose.md` is empty). This line called them "stand-alone agents" until 2026-08-24, which also broke the section's own arithmetic: every one of the 56 agent definitions has a matching skill directory (re-derived 2026-10-09 after the vinicius agent's removal; this read 56 / 50 / 57 until then), so 56 agents + 1 primer accounts for all 57 files with nothing left over for a "stand-alone" tier.

### The model is chosen at dispatch, not in the agent file

The `model:` frontmatter above is not the decision, and it is now `inherit` everywhere: a dispatch that names no model runs on the session's model. The fleet model-routing policy is applied by the orchestrator as a per-dispatch override. ⛔ **It has been amended at least ten times since this paragraph was written (eight are listed here; the policy also carries a context-cost amendment, under which a cheaper model is not a cost lever, and a `/wrap --sonnet` rule), and the first two amendments invert what it said.** (1) **Session tier:** the orchestrator runs **Fable for JUDGMENT sessions/turns, Opus for procedural ones** — not "always Fable". (2) **Review-panel amendment:** **every review / `--code` / breaker panel agent is `model: "opus"` INHERITING effort, with at most ONE optional Fable lens per review.** The Fable-for-breaker-lenses clause is DEAD for panels and survives only for non-panel verify/judge uses. What it cost: seven Fable lenses in one session, all at inherited max effort, dispatched five and six at a time, which spent the Fable usage allowance far too fast. (3) **The mandatory Fable ladder**, which partly walks amendment 2 back in the other direction: a panel now owes **≥1 Fable seat at 3+ seats, ≥2 at 6+, ≥3 at 9+** — a floor, not a ceiling — and **only the review hub keeps the choice of whether to spend one**. So "at most one optional Fable lens" is retired: on a nine-seat panel three are required. (4) **Long-running builders route to Fable.** Opus remains the tier for reads and short implementation work; a breaker is never routed below the tier of the builder it is reviewing; and genuine uncertainty routes to `inherit` rather than to a guess. (5) **Session defaults:** a working session runs Fable 5.1 at effort high, the review hub Opus at high, and panel seats inherit that effort. (6) **Hub carve-out:** breaker ≥ builder binds working-session panels only; for hub reviews the rule gives way (the asymmetry rule in the routing policy — the hub's panels stay on Opus whatever model built the change). The model is stated explicitly per agent in the dispatch brief. (7) **Raise the switch as a question:** on Fable with only procedural work ahead, the orchestrator proposes `/model opus` in that readout and never switches itself. (8) A `/wrap` ideally runs on Opus at effort high, and when a `/compact` is due each model switch goes AFTER it, never before (a switch rewrites the cache); dispatches name their model.

This is worth flagging because reading the agent files alone gives the wrong picture — they declare `inherit` on all 56 (`grep -h '^model:' .claude/agents/*.md | sort | uniq -c`; 50 opus / 6 sonnet before the switch, 49/6 on 2026-10-09 before the edda agent, 48/6 before that), which says nothing about the split that runs. The policy also simplifies what we adopted from `wshobson/agents`: their five-tier strategy collapses here to two working tiers plus `inherit`, keyed, by a choice made here, on the *shape of the work* (does this dispatch produce material, or judge it?) rather than on the agent's identity.

### How `/agent-work` parallelizes specialists

The flagship pattern: `/agent-work <task>` spawns 1–5 specialist agents in parallel, each loaded with a different skill, each working on a different file or partition. The orchestrator then integrates their outputs (typecheck, merge, test).

A typical `/agent-work` call for a multi-file feature might look like:

- Agent A (frontend-developer) — refactor `src/components/foo.tsx`.
- Agent B (ux-copywriter) — write the feature's new interface strings.
- Agent C (saas-engineer) — add a new server action in `src/actions/`.
- Agent D (security-expert, contrarian) — review the diff for missing auth gates.

All four start at once. Wall-clock is the slowest agent, not the sum. The orchestrator's job is the *brief* (what each agent should do, what skill they should load, what success criteria they own) and the *integration* (after-the-fact glue work).

This pattern diverges from external systems like `shinpr/claude-code-workflows`, which run phase-sequential agents with named handoff contracts. The trade: ours has lower coordination overhead but no clean phase boundary; theirs has structured handoffs between sequential phases.

### Personas as a kind of agent

Personas are specialty agents that role-play a user archetype rather than supplying technical expertise. The copy ships none, and nothing in it seats one: in the source project a standing trigger-index row and `/expert-review`'s § Routing Rules rows put its persona on UX-touching audits, and neither came with the copy. To use a persona, write its skill and agent, then add it to the Routing Rules rows where a user's view matters.

⚠️ **Skepticism lives on the skill, not the agent.** `skepticism:` is a frontmatter field on the expert's **SKILL.md**, not on any agent file — the agents carry zero of them — and the copy's experts split 6 high / 21 medium / 6 low (`grep -h '^skepticism:' .claude/skills/*/SKILL.md | sort | uniq -c`). The high set is security, QA, legal, uncle-bob, the engagement psychologist and haines-churn-prevention.

### Why we don't have a separate Persona primitive

`alirezarezvani/claude-skills` (one of the catalogued external systems) explicitly distinguishes three roles: Skills (procedures), Agents (executions), Personas (cross-domain role-players that load 15+ skills). Our system collapses Personas into the Skill primitive — a persona is a `SKILL.md` carrying a character sheet and a `skepticism:` field, not a separate kind of object.

Consequence: multi-persona reasoning (e.g. "look at this launch decision as founder, engineer, and lawyer simultaneously") is not a primitive. It requires manual orchestrator composition (`/expert-review` summoning all three). This works today but it's the kind of thing that, if the pattern becomes load-bearing, would be worth elevating into a first-class primitive.

### Agent lifecycle and the `block-subagent-memory-write` hook

Subagents cannot directly write to skill MEMORY.md files. The reason is structural: sub-agents have local context but no view of the orchestrator's session-wide synthesis. If they each independently wrote their findings to skill memory, the result would be noisy, duplicated, and out of order. Instead, sub-agents emit `Memory Update:` blocks in their final output. The orchestrator extracts these blocks, deduplicates them, and appends with full context.

The `block-subagent-memory-write.sh` hook enforces this. **It does not return nonzero** — it emits a `hookSpecificOutput` document with `permissionDecision: "deny"` and exits 0, which is the JSON form of the PreToolUse contract: the JSON carries the verdict. (The other form, exit 2, blocks regardless of JSON — `code.claude.com/docs/en/hooks` § Exit code 2 — so the exit code is not verdict-free in general; this hook simply does not use it.) Its reach is wider than the name suggests: the whole memory tier family (`.claude/skills/*/MEMORY*.md`, archive shards included), the meta `CHANGELOG-ARCHIVE-*.md` shards (the `CHANGELOG.md` router itself sits outside the pattern), and the meta live registers `WATCH-TIER.md` / `ADOPTION-QUEUE.md`. It also **fails closed** — a payload it cannot parse that references a protected path is denied rather than waved through. The deny text is TWO texts since 2026-10-10 (a fold from the prior-art review of `cosmix/loom`): the orchestrator's is a redirect, not a refusal — it names the supported path (Bash append to the current dated shard, resolved by MAX END-DATE, never the regenerated router) and the `/tmp/claude-meta-mem-allow` marker for bulk meta operations the orchestrator performs intentionally; a sub-agent — detected by an `agent_id` key in the payload — gets a refuse-only text naming only its Memory Update route, and the marker is REFUSED to it (fire arm `subagent-marker-refused`), never granted.

### `_agent-primer.md` — the read-first agent preamble

`.claude/agents/_agent-primer.md` is a special file: not an agent definition itself, but a shared preamble that **all 56 project agent definitions point at** (56 in the source project at 2026-10-11 — 55 after the vinicius agent's removal on 2026-10-09, then the edda agent landed the same day; this read 57 before the removal), written in by `generate-expert-agents.mjs` (55 of them; `external-guildhall.md` is hand-maintained and carries the pointer by hand). It encodes the rules a sub-agent needs but its parent skill's spec wouldn't naturally include — most importantly, the sub-agent MEMORY blocks instruction that sub-agents must emit `Memory Update:` blocks rather than directly Edit/Write MEMORY.md files.

⛔ **It is READ-FIRST, not injected, and this doc called it an injection at prompt-assembly time for a long while.** No mechanism inserts it into an agent's context: the agent file carries a pointer, and the agent reads it or does not. Two consequences follow, and both are load-bearing. The primer is an instruction layer with a compliance rate, not a delivery guarantee — which is exactly why the hook exists beneath it. And a **harness-provided** agent type (`general-purpose`, `Explore`, `Plan`, `statusline-setup`, `claude`) has no file to carry the pointer, so it never receives the primer at all; a dispatcher relying on primer content for such a seat must paste it into the brief.

Two layers protect the sub-agent MEMORY blocks invariant: the primer (prompt-layer instruction telling the agent "don't try"), and the `block-subagent-memory-write.sh` hook (deterministic deny if the agent tries anyway). The primer is the curate layer; the hook is the enforce layer. The hook fires on every Edit/Write call (its settings.json matcher is `Edit|Write`, so a Bash append is outside it), whichever skill the agent loaded; the primer fires on the 56 that point at it — every definition, if read (this read 54 until 2026-10-09 and 55 until 2026-10-14).

The primer pattern is a generalizable answer to "how do you bias every sub-agent without bloating every agent definition file." If the system grows another always-applies rule, the primer is the right place to add it before duplicating across all 56 agent definition files (re-derived 2026-10-11; this read 54 until 2026-10-09 and 55 until 2026-10-11).

The most recent such addition is the **memory-read procedure** (2026-08-01). Thirty-six skill MEMORYs (at 2026-09-27; 38 at 2026-10-11 — `ls .claude/skills/*/MEMORY-ARCHIVE*.md | awk -F/ '{print $3}' | sort -u | wc -l`; the bare `ls` counts shard FILES, 119 at 2026-10-14) are split two-tier — a hot `MEMORY.md` beside a cold `MEMORY-ARCHIVE.md` (Lecture 3) — which changes what a consulting agent has to do and, more importantly, what its *absence* results mean. The primer therefore prescribes: attempt the whole-file `Read` first; on a truncation banner, `rg` for the consult topic and then page the **tail**, because newest entries are last and most likely to have superseded the head; never answer from page 1 alone; and report what you actually got (`FULL` / `PARTIAL(lines A–B of N)` / `FAILED` / `NOT-READ`) in the structured return, because an honest partial is useful to the orchestrator and a silent one is not. The primer's "Grep the DIR, not just the file" rule carries the clause that matters most for correctness: **grep the skill DIRECTORY, not `MEMORY.md` alone** — a single-file grep proves absence only from the hot file, and a clean zero on an archived lesson is indistinguishable from "never codified." The motivating measurement is in the primer too — **and it has been superseded once, in the direction that makes the problem smaller.** The founding figure was 39% of 4,184 dispatches never attempting the read; a classifier fix on 2026-08-26 re-measured it over 6,953 dispatches at **27.6% never-attempted plus 5.1% that read an alternate path**, so the original number was counting a real failure and an instrument artifact together. What survives unchanged is the shape of the finding: un-read outnumbers un-readable several times over, and 87.3% of the byte-capped class never paged past the truncation. The failure is procedural, not a file-size problem — which is exactly why it belongs in the primer rather than in any one skill's spec.

### Tool access and the principle of least privilege

Different agents get different tools — but the two shapes above are the whole story, and the version of this section that preceded them was aspirational rather than measured. **No project agent is granted `MultiEdit`** (zero of 56 name it), so "code-modifying agents get Edit/Write/MultiEdit" describes a tier that does not exist. **Restricted agents keep `Bash`** — the 19-file shape drops only `Write` and `Edit` (19 restricted definitions at 2026-10-11, re-derived from the `tools:` lines — the edda agent joined the shape 2026-10-09; this read 17, then 18, until then) — so "review agents typically get only Read/Grep" overstates the restriction considerably: a Bash-holding agent can read anything and, with enough determination, write too. The genuinely read-only seats are the harness-provided `Explore` and `Plan`, which are structurally denied Edit/Write/NotebookEdit.

What the split does buy is real but narrower than "cannot mutate state": removing `Write`/`Edit` removes the *accidental* mutation — the tool an agent reaches for by reflex mid-review — rather than closing the capability. That is worth having and worth describing accurately, because a brief written against the stronger claim will route work to a seat it believes is sandboxed and is not.

### The fleet coordination plane

Five further commands exist because the owner routinely runs many sessions against one repo, and coordinating *investigation* across them is a different problem from coordinating a deploy. Transport and protocol were pulled apart deliberately after the 2026-07-27 mail cascade (Lecture 9): the mechanics live in `/channel`, the two topologies in `/fleet-inquiry` and `/fleet-swarm`.

**`/channel` — the transport.** The fleet-channels client (Wave 2) writes to a dedicated mail root `channels/<slug>/`, which is spectator-visible to the owner as plain files. Its FC-01/FC-02 write gates are what make it more than a second mailbox: membership fails **closed**, the lead is barred from taking a position or a rebuttal, and spokes are addressed to the lead so peers cannot cascade to each other. It is thin in the same sense `/mail` is — the transport, never the protocol.

**`/fleet-inquiry` (Mode A) — the convergent topology.** One lead session does all the analysis; peers reply only to scoped, direct-addressed evidence requests, never to broadcasts. The question and its termination condition are pre-registered, the owner gets one report at close, and findings fold **once** through `/meta learn`. It exists because process-referent questions — "how does the fleet do X?" — cascade all-to-all when every seat can broadcast, which is exactly what happened and what the lesson behind this mode codifies.

**`/fleet-swarm` (Mode B) — the divergent counterpart.** N seats each live a *different* user situation against one pinned-SHA build, to discover what no test is asking about, under SBTM session sheets and per-seat charters that must name their automation gap. It is the only fleet mode that spends real money and writes to staging, so it is always charter-capped and owner-invoked — never "while the fleet is idle." ⛔ **Its validation gate FIRED AND PASSED on its 2026-08-06 due date** — 0/16 mis-routed against a <10% bar, 0 impressions filed, 1 self-caught duplicate — and **Mode B GRADUATED 2026-08-06.** This paragraph said "PENDING to 2026-08-06 … this document should keep saying so until the gate fires" until 2026-08-24: the doc carried its own update instruction, the trigger fired, and the flip commit swept four other surfaces while missing this one. It is now a validated procedure, not merely a usable one.

**`/summary` — the mid-session read.** The counterpart to `/orient` (session start) and `/wrap` (session end): where *this* session has landed, net rather than narrative, plus the owner-decision queue and what is still in flight. The discipline that makes it worth having is that every number is **derived live** — never restated from context, and never read off the truncated `gitStatus` header block. That rule was codified after nine restatement errors across five sessions, four of which had mis-read a capped instrument's silence as absence.

**`/whoami` — the full identity surface.** Prints this session's full UUID. `/peers` and the mail plane deliberately show only 8-hex prefixes, so this is the surface for anything keying on the whole id — env-validated via `session-manifest.py whoami`, never a filesystem guess.

### Response-mode prefix scheme (`.claude/orchestrator/conventions.md` § Response-mode prefix — adopted 2026-05-17, rosters deleted 2026-09-01)

Prefix the FIRST line of EVERY reply with a bracketed marker so the owner can tell at a glance what mode the orchestrator is in. The marker is the command's own name — `/wrap` → `[wrap]`, `/meta` → `[meta]` — derived, never looked up; default mode with no command running is `[main]`. **There is no unprefixed state** — the rule was tightened after prefixes silently stopped firing inside a live flow, because the markers had proved useful.

A multi-reply flow keeps its marker on every reply until the flow ends; a one-shot read marks the one reply it produces — read that off the command's own behaviour, never off a membership list. Nested cases (e.g., `/wrap` invoking `/meta learn` as a sub-skill): parent's prefix wins (`[wrap]`).

Adopted in the third adoption batch. Solves the disambiguation problem when multiple skills nest 3-4 levels deep (`/wrap` → `/meta learn` → `/session-memory` → `/me learn-session`) — without prefixes, the owner can't tell which sub-skill is currently speaking.

### Universal `help` arg convention (`.claude/orchestrator/conventions.md` — adopted 2026-05-30, relocated 2026-09-03)

A second SessionStart-delivered orchestrator convention (`conventions.md` § Universal `help` arg; sibling to the prefix scheme above, relocated from `AGENTS.md` on 2026-09-03). ### Inclusion criteria for RULES.md

A new lesson promotes to RULES.md only if it satisfies all three:

1. **Trigger** — a concrete cue (a phrase, a tool call, a file pattern).
2. **Action** — a sub-15-second check.
3. **Generalizable** — fires across many contexts, not just one feature.

Lessons that don't qualify (principles, post-mortems, panel playbook entries, evolution timeline) stay MEMORY-only.

### The Durability + Impact + Scope rubric

Adopted from `alirezarezvani/claude-skills`, shipped in our v2.7.3. Every candidate lesson scored 0–3 on each axis:

- **Durability** — how long the lesson stays relevant (one feature vs. system-wide).
- **Impact** — how much it changes behavior (minor nudge vs. preventing a class of incident).
- **Scope** — how broadly it applies (one workflow vs. all of them).

Total ≥6: promote. 4–5: watch. ≤3: ignore (don't even add to MEMORY).

**Watch-tier register (added 2026-06-01).** "Watch" is no longer a note-and-forget — a 4–5 candidate is recorded in the live register `meta/WATCH-TIER.md` (sharded into `WATCH-TIER-PART-NN.md` since 2026-09-13; archived rows in `WATCH-TIER-ARCHIVE.md`, revived on recurrence) with: tag · first-seen date · `occurrences` count · D+I+S · a **recurrence signature** (the trigger phrase / failure shape that identifies a re-fire in a future session) · prune date. Each `/meta learn` re-reads the register and, if this session re-triggered an item's recurrence signature in a session *distinct* from its prior occurrences, increments `occurrences`. **Auto-promote to a full numbered L# on the 2nd occurrence** (counting starts at 1 = the codification moment; there is no occurrence 0). This closes the gap where a borderline-but-real pattern was scored 4–5, mentioned once, then lost before it recurred enough times to cross the ≥6 bar — the register makes the recurrence countable across sessions instead of relying on memory.

This rubric replaced a gut-feel promotion process from the defer-with-trigger gold-pattern era and dropped the false-positive rate visibly. It is also the rubric applied when `/meta distill` runs against an over-large MEMORY.md.

### `/meta learn` — session-end lesson extraction

The most-frequently-invoked meta subcommand. Triggered by `/wrap` automatically (with a `<15-min exception` rule: if `/meta learn` ran as an explicit Skill-tool call within the last 15 minutes and its output is verifiably present, the auto-invocation may skip with a one-line citation).

Steps (compressed):

1. Scan conversation for signals (user pushback, agents launched, defer-with-trigger added, LARP markers, "we should add X" without action).
2. Diff against existing knowledge — is this lesson already captured somewhere?
3. Propose expert MEMORY updates (for skill-specific insights).
4. Propose skill-spec edits (when the lesson generalizes to the spec layer).
5. Run the deferral sweep — every defer added this session must be in `todo.txt` with a trigger.
6. Surface structural gaps that emerged this session.

Auto-execute for meta MEMORY writes; approval required for skill or expert MEMORY edits.

**L# numbers are ALLOCATED, not derived.** `scripts/lesson-mint.mjs` is the allocation ledger; the number a new lesson receives comes from `mint`, never from reading `maxL` and adding one. The distinction is the whole point: **`maxL` is a READ, not a reservation** — two sessions that derive from the same counter minutes apart both compute the same next number and both write it, and on a fleet where several seats codify in parallel that is the ordinary case rather than the unlucky one. An allocated number is issued once and never reassigned. The ledger also takes a `--slug` argument, which is what makes a **content** duplicate visible: two seats codifying the same lesson under different numbers is a failure the push gate structurally cannot see (it sees two well-formed appends), while two slugs naming the same subject are legible at mint time. If a number must be derived as a fallback, substitute `maxL` in the *same* bash call as the append rather than baking a literal into a heredoc composed a turn earlier — the gap between reading and writing is where the collision lives.

**Codification cycles + self-firing checks (multi-layer enforcement, codified across 2026-05-24 → 2026-05-25).** Lessons codified in a single session don't immediately load into orchestrator's active-recall — the most-just-learned lesson can paradoxically be the most likely to be re-fired in the following ~3 turns because the rule exists on disk but not in working active-recall yet. A lesson codifies this as an orchestrator-side self-firing check (re-grep new L#'s Trigger column against own draft for 30 min OR 3 turns after codification); sniff-test Check 12 enforces. **Worked example from 2026-05-25:** cost-rationalization / scope-justification framings — "cheaper / minimum-viable / smallest-defensible" used as justification when correctness was the real rationale — a pattern codified as a lesson earlier that same day, which then self-fired 3 times in the next ~90 minutes before pushback caught each instance (Step 7f defer-by-vague-trigger / Phase 2 b/c spec-deviation refactor / "surface only" structural-gap framing). The 3rd firing triggered codification (spec-deviation invisibility — companion to the scope-justification lesson, at the structural-disclosure layer rather than the scope-justification layer). All three patterns trace back to one root: orchestrator under composition pressure defaults to easier path AND fails to flag the deviation. The codification quartet (scope-justification in active-recall Hot Tier + diagnostic-extract-mirrors-canonical + self-firing window + spec-deviation flag) is the multi-layer enforcement that emerged from this session: scope-justification at always-loaded scan time, canonical-tool extraction discipline for diagnostic display, self-firing window check for fresh-codification vulnerability, and structural-deviation disclosure at ship-time. Sibling layer: meta-corrections-registry capture surface (described in `/meta corrections` entry-point above) feeds future L# codifications by surfacing pushback events in bulk before they reach memory-decay threshold.

### `/meta self-audit` — auditing the auditor

Critical against the failure mode where the meta skill becomes the thing it critiques. Fourteen checks:

1. Embedded-number drift (claims like "currently 24 lessons" vs. actual count).
2. Ordering inconsistencies (sequential phase/step numbers).

## Lecture 9 — Workflow Patterns: Capture, Curate, Enforce

> **TL;DR.** The central conceptual axis. Every signal or rule lives in one of three layers — **Capture** (passive collection), **Curate** (active triage), **Enforce** (mechanical activation). Most failures are layer misclassifications; the 30-second pause to ask *which layer is broken* is the cheapest discipline in the system.

This lecture introduces the central conceptual axis of the system: every decision, signal, or rule has a *layer* — Capture, Curate, or Enforce — and most failures are layer misclassifications.

### The three layers

- **Capture** — signal collection. Happens *during* work. Includes: conversation transcripts, tool call logs, agent outputs, user pushback, hook fires, audit findings, error patterns. Capture is passive.
- **Curate** — signal triage. Happens *between* work cycles. Includes: `/meta learn` (lesson extraction), `/session-memory` (decision capture), `/meta memory-audit` (hygiene), `/meta distill` (promotion + deletion). Curate is active and judgment-heavy.
- **Enforce** — rule activation. Happens *before output is written*. Includes: hooks (deterministic), rule files (loaded always or on a matching read), the active-recall trigger bands (parked since 2026-09-07 — Lecture 4), skill-spec assertions, skill-lint detectors. Enforce is mechanical.

The principle (codified in `meta/SKILL.md`): when adding a new rule, ask *"is this a capture gap (no data), a curate gap (data exists but isn't sifted), or an enforce gap (rule exists but doesn't fire)?"* The three failure modes require different fixes. Capture-gap → new signal to watch. Curate-gap → new `/meta` step or MEMORY entry. Enforce-gap → new `meta/RULES` row (the `RULES-SHARD-*` shards today), skill-lint detector, or hook.

### A worked artifact: the book→rule map (a Curate-layer calibration record)

Added 2026-06-01. A *book→rule map* is a Curate-layer artifact for canon-backed expert skills (uncle-bob ← R.C. Martin's SOLID/smells + Kent Beck's *Tidy First?* change-economics; engagement-psychologist ← the persuasion canon; saas-launch-marketing ← GTM; saas-economist ← pricing; accessibility-expert ← WCAG; security-expert ← OWASP; performance-expert ← Core Web Vitals; legal-advisor ← GDPR/CCPA/AI-Act). It is a *forward* map: enumerate the external canon, and verdict each item **ENCODED** (a rule/control we have — cite it), **EXCLUDED** (we deliberately don't fire — cite a guard: an anti-scope clause, a critic, an L#, "N/A to our stack", or another owner), or **GAP** (uncovered — held for validation, never auto-encoded). The load-bearing column is **EXCLUDED**: it records *why we don't fire*, so the skill's calibration survives expert turnover — Capture→Curate→Enforce applied to a whole external standard at once. A GAP graduates to a firing rule only through the normal Curate path (validation → `/meta learn`), never by sitting in the map. Lives in `<skill>/references/*-rule-map.md`, consulted during corpus-design / audit passes (not always-loaded). The source project keeps ten; the copy ships one, uncle-bob's (derive the set with `ls .claude/skills/*/references/*rule-map*.md`).

### A worked example: anti-anchoring filter

This trace appeared in our 2026-04-22 session. Tracing it through the three layers:

**Capture.** During synthesis, `saas-architect` (contrarian) included a magnitude estimate — "0.3–0.6pt divergence" — embedded in a proposed project-memory write. The signal was present in the conversation transcript but not flagged.

**Curate.** During `/session-memory`'s proposal-review step, a pushback asked whether persisting it would anchor later AI scoring. The napkin estimate was about to be persisted as a quotable fact for future sessions. `/session-memory` Step 4 at that time lacked an anti-anchoring filter.

**Enforce (the fix, shipped v2.8.3 same session, two layers):**

1. *Curate layer fix:* `/session-memory` Step 4a now applies an anti-anchoring filter BEFORE Step 5 presents the proposal. Measured magnitudes (N≥5 data points) keep; single-example / expert-narrative / napkin estimates are rewritten qualitatively or tagged with evidence-lineage, or dropped.
2. *Enforce layer fix:* `meta/RULES` got a row that fires at composition time for ANY project-memory write carrying a measured-magnitude number (pt, %, delta, rate, threshold), not just a `/session-memory`-initiated one. The lesson's scope list supplies the YES examples ("0.3–0.6pt divergence", "crosses tier boundary", "defer at >30% promotion rate") and the NO examples (user-decided thresholds, counts derivable from git).

**Outcome.** The anti-anchoring filter lesson labels its diagnosis explicitly: capture-gap NO, curate-gap YES, enforce-gap YES. Revisit trigger: ≥3 napkin catches across the next 10 `/session-memory` invocations → the rule is paying for itself, keep (maybe tighten); 10 fires with zero napkin catches → noise, relax.

This is the *shape* of a healthy lesson: a layer diagnosis, a two-layer fix where possible, and a revisit trigger.

### A worked counter-example: wrong-layer fix proposal

The layer model's value comes from preventing fix-at-wrong-layer waste. A concrete near-miss illustrates the failure mode:

When the project memory index breach surfaced (2026-05-21; `state.md` Status updates), the initial impulse was to file it as a *capture* gap — "we're not seeing the cap-breach warning often enough." Following that frame would have proposed adding more visibility (a Stop hook surfacing the breach to stderr on every session-end, or a dashboard widget). All capture-layer fixes.

But the signal is *not* missing. The harness emits the warning on every session start ("Only part of it was loaded"). Every session sees it. The actual gap was that no curate-layer process *acted* on the signal between sessions, and the manual trim is mechanical-but-curate (which 2 lines to drop is judgment, even though the LOC count isn't).

The diagnosis was curate-gap → a prune step in `/meta memory-audit`, and it shipped as Step 3b, the intra-file dedup sweep (memory-cap dedup, 2026-05-21). A capture-layer fix (more warnings) would have added noise without changing outcomes. The enforce layer turned out to matter as well, at a different point than first feared: a block at load time would have stranded sessions until a manual trim, whereas what shipped on 2026-06-01 (`check-memory-budget.sh` ARM 1) denies the *write* that would cross the cap and names the bytes to free in its deny reason.

The rule: layer classification is itself a judgment call, and getting it wrong wastes the next investment. The 30-second pause to ask *"which layer is broken — is the signal absent, the triage missing, or the activation skipped?"* is cheap compared to building a fix at the wrong altitude.

### User pushback as a system signal

Mentioned incidentally in `/meta learn`, sniff-test, and `/me learn-session` specs as one signal among many — but it deserves first-class treatment because it is, empirically, the *highest-fidelity* signal the system has.

Reasoning: every other signal (agent miss, defer-with-trigger added, LARP marker, hook fire) is generated by the system itself, and the system's calibration is what's being tested. User pushback is exogenous — it can't be tuned by the same calibration that produced the bug. When the user questions a claim's certainty, the number of defers, or a question that looking would have answered, the message is: *the system's internal quality gate didn't catch this, but external observation did*. That class of signal is irreplaceable.

How the system uses it today:

- **`/meta learn` signal catalog** treats pushback as a primary signal class (alongside agents-launched, defer-with-trigger, LARP markers). 
- **`sniff-test` Check 4** explicitly handles frustration markers (exasperated interjections, a complaint of going in circles, an order to stop or to fix it properly) with the rule: RE-EXAMINE first, then either fix the specific error AND name it OR push back with substantive disagreement in ≤1 line. NEVER capitulate without re-examination.
- **`/me learn-session` Step 1** scans for pushback events alongside directional preferences and tool-friction flags. Cross-session pattern detection.
- **The user profile's verification-trigger phrasings section** codifies conditional approvals and comparative questions about another system as STOP-and-verify cues rather than approval-with-caveats.

The structural failure mode this guards against: a system trained on internal signals only will converge to whatever internal calibration produces. External observation is the only thing that breaks the loop. ~30% of recent L# lessons (informal MEMORY scan, ~2026-05; undated and not re-derivable) trace to a pushback event in their evidence chain (informal count from MEMORY scan) — without that signal, those lessons wouldn't exist and the bugs they catch would still be live.

Anti-pattern: treating pushback as a *cost* to minimize ("I should have asked fewer questions" / "I should have presented fewer options"). The cost-to-minimize is *unproductive* pushback (the user repeating themselves because we didn't listen). *Productive* pushback (the user catching a class we missed) is the system working as designed. The discipline is to make the productive kind cheap and the unproductive kind rare — sniff-test triggers + active-recall + verification-trigger phrasings all serve that.

### The memory → rule → hook promotion ladder

Already mentioned in Lectures 4 and 5; worth restating in the layer-aware frame:

- **Memory** entry = Curate layer. Captures the lesson; relies on retrieval.
- **Rule** file = Enforce layer (weak). Always loaded when matching; relies on orchestrator attention.
- **Hook** = Enforce layer (strong). Fires regardless of orchestrator state.

Each rung up narrows the failure window. The system progressively promotes when evidence accumulates: a feedback memory recurs N times → it becomes a rule line → after another N recurrences it becomes a hook warn → after an observation window with no false positives it can become a hook block (the warn-before-block floor is one warn-mode session; the shipped gates each set a stricter bar of their own, typically five clean runs).

Concrete example (the `hover:` without `focus-visible:` pattern): tracked across six separate flow audits (6 recurrences). Now lives as a `components.md` rule line + a pre-push hook that **HARD-blocks** staged `hover:`-without-`focus-visible:` additions (promoted warn-mode → hard gate on 2026-05-27 — grep `.githooks/pre-push` for `focus-visible HARD gate`; since 2026-06-18 the check itself lives in `scripts/focus-visible-staged-check.sh`, so the gate is self-testable).

### Defer discipline with triggers (defer-with-trigger gold pattern, default-SHIP pre-synthesis gate, split-lens scope check, skeptical defer re-pass)

A four-lesson chain about *not* shipping incomplete work disguised as a "post-launch" decision. The rule: every defer must include:

1. **A defer reason** matching one of three valid categories: needs production data, needs user decision, has real dependency on unbuilt systems.
2. **A LOC estimate** of what the fix would touch.
3. **A trigger condition** — not "post-launch", but "first storage cost spike" or "A/B once the paid tier gives a usable sample."
4. **Promotion to `todo.txt`** with all three.

`/audit-check` Check 8 enforces this — every "deferred" item in a feature tracker must appear in `todo.txt` with the trigger format. If not, the check fails.

The deeper insight (defer-sweep 3-part test): deferral rationale is itself susceptible to hallucination. A defer that cites "needs prod data" but where the fix is <10 LOC and the current state has a catastrophic blast radius (safety-critical moderation, plan-allowance grants, data integrity) should be promoted regardless of "which fix is optimal" uncertainty. A defensible partial improvement beats a broken status quo.

### Parallel-session coordination (parallel-session coordination and successors)

A pattern peculiar to our system: the user often runs *multiple* Claude Code sessions in parallel against the same repo (each on a different piece of work). Git state is shared. Memory files are shared. The orchestrator must be aware that:

- `git status` may show files this session never touched (parallel session staged them).
- `git add -A` is *banned* — the safety net against accidentally including another session's WIP.
- `git stash` is banned for the same reason.
- Before staging, run `git diff --staged --name-only` to check if a parallel session pre-staged files.
- **There is no safe commit VERB, and this was measured the hard way.** The obvious two each defend one axis and are
  blind on the other: `git commit -o <path>` narrows the FILE SET and then RE-READS THE WORKTREE for that path, so it
  is immune to a peer's staged *other* files and takes a peer's concurrent write to *your* path; a BARE commit is the
  exact mirror — immune to the worktree write, and it takes the whole per-repo index including anything a peer staged.
  Both were measured sweeping peers' work, hours apart, by seats that had gated correctly first.

**`scripts/safe-commit.sh` is the shipped control**, and it is the answer to the paragraph above rather than a
convenience wrapper. It runs FOUR gates IN THE SAME PROCESS as the commit — a foreign-PATH gate (the staged set must
equal the paths you declared), an index-vs-worktree drift gate, a DELETE-COLUMN gate, and (since 2026-09-05) a parse of
the staged blobs, because the first three read path sets and line counts while `tsc` and pre-push compile the
worktree, so nothing else reads the bytes being committed — all in one process because a check from a previous tool
call is already stale by the time you commit. In the tool's DEFAULT mode the drift gate is structurally silent (`git
add` makes index and worktree identical); on your own paths only the delete-column and parse gates can still bite. It **REFUSES and never repairs**: an earlier auto-restore design died inside a
`while read` over a process substitution and destroyed a peer's staged state, so the shipped version prints, exits
non-zero, and leaves the repair to a human. `--add N` / `--del N` are declared by the caller and compared against the
real diff. ⚠️ That catches a DELETION sweep by default and an ADDITIVE one only if you pass `--add`, which is opt-in —
the tool's own comment notes that `--add` would NOT have caught the recorded additive sweep on its own, because its
author would not have passed it. An earlier revision of this sentence claimed the comparison "turns a silent sweep into a refusal" full stop;
that over-claimed, and the source refuted it two comments above the flag it described.

It **NARROWS, never CLOSES.** There is no lock between the gate and the commit, so a peer staging in that window still
enters; same-process makes it microseconds instead of ~60 seconds. **And when BOTH collisions are live at once there
is no gated verb at all** — GATE 1 refuses while a peer holds a foreign path staged, and you may neither unstage
their work nor hold (an uncommitted line is the only state with no history). The disposition is to DISCLOSE: gate
both numstat columns by hand in the same command as the commit, and say out loud that you did. Three seats reached for an absolute word here and
all three retracted it. ⛔ **But the sentence that stood here — "git has no commit-exactly-this-verified-index primitive" — was itself REFUTED on 2026-08-23 by this fleet's own practice: a PRIVATE index DOES close it.** The correction lives in the commit doctrine (`.claude/orchestrator/commit-doctrine.md`, delivered on the first commit-shaped call of each compaction epoch), and `scripts/private-index-commit.sh` ships the recipe. `export GIT_INDEX_FILE=<scratch>` → `git read-tree $HEAD0` → `git add -- <declared paths>` → `write-tree` → `commit-tree` → `update-ref "$(git symbolic-ref HEAD)" $NEW $OLD` (the recipe spelled `refs/heads/main` until 2026-09-08 — from a `dev` checkout that moves production), where `update-ref <new> <old>` is a compare-and-swap that FAILS rather than clobbers if a peer commits in the window. The shared index is never read or written, so foreign staged paths cannot enter by construction (measured: 9+ commits in one session, zero incidents). ⛔ **AND THE RECIPE HAS A MANDATORY LAST STEP THIS PARAGRAPH DROPPED UNTIL 2026-08-24: `git reset -q -- <every path the commit changed>`** (a rename is both endpoints; derive with `git diff-tree --no-commit-id --name-only -r HEAD`). Without it the shared index still holds the PRE-commit blobs for your paths, and until it is re-pointed at HEAD **a peer's next bare `git commit` REVERTS your change** (measured 2026-08-23: 128 status lines on the just-committed paths until the reset ran). An abbreviated safety recipe is more dangerous than none — it reads as complete. The residual seam is the CONTENT axis — `git add` still reads the worktree for your declared paths. **"Narrows, never closes" remains true of the SHARED-index path only.** A clean run is also not evidence,
because clean commits look identical whether the race is absent or merely did not fire.

The recurrence this control exists to stop is METHOD, not verb: four seats in one evening hand-rolled their own gate
from the most recent correction instead of grepping for the shipped one, which is why the commit doctrine now
routes to it by name.

These are codified in project memory and also enforced by `bash-safety-warn.sh` (warns on `git add -A` and `git stash`).

The git-discipline rules above are the *commit-time* defense. There is also a *capture-time* layer: the **session-manifest system** (`scripts/session-manifest.py`, 6,444 lines on 2026-09-14 — re-derive with `wc -l`, codified as a recorded lesson). Each session writes a cached snapshot of its work-subject to `.claude/state/active-sessions/<sid>.md`, self-identifying via `CLAUDE_CODE_SESSION_ID` and failing closed without it (since 2026-07-10): a headless caller names its session with `--session`, `write` refuses to guess, and `check-overlap` degrades to blocking itself. The old most-recent-jsonl-mtime fallback was removed because it answers correctly only for whichever session is busiest. Nineteen modes — `write` (snapshot own state), `read` (peer summaries), `who` (peer roster, backs `/peers`), `whose-edit` (file→session attribution — the canonical tool behind the uncommitted-authorship discipline), `prune` (drop manifests stale >24h), and `check-overlap`, a **tiered scope-overlap gate**: it HALTS with `exit 2` on code/migration-file overlap with a named peer (clobber risk) unless `--allow-overlap` is passed, WARNs (`exit 0`) on coordination-file overlap (`messages/*.json`, trackers), and logs every fire to `.claude/logs/scope-overlap-fires.jsonl`. Wired into four surfaces: `/orient` (peer-summary + prune), `/wrap` (final-state snapshot), `/agent-work` Step 5a (pre-dispatch snapshot), and `/expert-review`'s Scope Confirmation Gate step 2a (a mandatory check-overlap that can *block* a Scope Proposal — exit 2, owner must coordinate or `--allow-overlap`). (2026-06-09 join with the sibling session-lifecycle layer: `check-overlap` + `read` now consult the `session-finished-<sid>` markers — a peer that has EXITED is dropped from the manifest channel so the gate stops defending against already-wrapped-and-closed peers; the git working-tree channel still backstops any uncommitted edits it left behind, and WRAPPED-but-not-exited peers stay defended since `/wrap` is repeatable. `prune` is also wired into the `SessionStart` gate now, so dead manifests clear without waiting for the next `/orient`.) A later mode, **`hub-discover`** (2026-07-08), is the PULL side of cross-session `--code` review-hub discovery: a booting peer reads the durable `review-hub-active-<sid>` marker at SessionStart to find a live review hub — the zero-staleness backstop past the 72h mail TTL, complementing the hub's PUSH-side 48h `--to all` re-broadcast that keeps its availability announcement fresh. This is the system's primary *decision-collision* defense: git discipline (the bare-commit-sweeps-the-index lesson) stops one session clobbering another's files; the manifest stops two sessions reaching contradictory design decisions on the same surface. Companion `scripts/parallel-session-scan.py` reconstructs peer work-subjects from session jsonls; both tools self-ID via `CLAUDE_CODE_SESSION_ID` to avoid a most-recent-mtime race that once mislabeled the current session as a peer.

**`fleet-claim` — the fleet's mutual-exclusion primitive.** Detection and attribution still leave one problem open: N peers can each independently decide to do the *same* work. `fleet-claim <token>` serialises on a named token — the write was LAST-writer-wins (a plain truncating `open()`) until 2026-10-12, so the claim was READ BACK and a loser was told rather than congratulated; a new claim is now an exclusive create (`os.link`) under a fleet-wide lock, with an atomic replace for `--force` and succession, so of two seats racing one token exactly one write lands. So a fleet-wide gate — a red build, a broken migration, a lint sweep — gets claimed once instead of re-run N times (five sessions ran `npm run lint` against one 8-error file in a single night before this existed). Paired with `hub-discover`'s review-hub vacancy notice, it converts the review-delegation ladder from a herd into an **election**: when the hub retires, every peer independently reads "no hub," broadcasts, gets no ack — *because every peer is in that same state* — and self-runs the same review with its own multi-agent panel. One review, N panels, and each member's reasoning is individually sound, which is why the broadcast→await→self-run ladder cannot detect it. The claim covers the **work**, never the **truth**: correcting a claimant's analysis by mail stays open and cheap; what the claim forecloses is re-running the gate and re-broadcasting the same finding. One counter-intuitive detail worth carrying — a **REFUSED** claim means *read `--list`*, not "a peer owns it." The guard near-matches on stop-words: a near-match against a PEER's live claim refuses (rc 3 — read `--list` before deferring), while one against your OWN sibling row proceeds with an ℹ️ (2026-07-27); believing REFUSED at face value once deadlocked two seats into deferring to each other.

**`scripts/session_status.py` — one derivation, three consolidated sites (seven importers at 2026-10-19 — re-derive with `rg -l -e 'import session_status' -e 'from session_status' scripts/*.py`).** The question "is this session EXITED / WRAPPED / ACTIVE?" had been hand-written at three sites (`session-manifest.py`, `session-lifecycle.py`, `parallel-session-scan.py`) and had already diverged on five independent axes: which predicate reads liveness (jsonl mtime vs. records), which clock the marker uses (file mtime vs. content epoch), whether an inferred-resume arm exists, and what a stale marker resolves to (short-circuit ACTIVE vs. fall through to WRAPPED). Every row was defensible in isolation, and the set of them meant `/peers`, `/expert-review`'s injected brief, and the overlap gate could disagree about whether a seat was alive. It is now a single importable leaf module — no CLI, no argparse, no import-time side effects, and one `git rev-parse` call made only when `repo_root()` is invoked (2026-10-10) — that all three delegate to, and the consolidation shook out two real classification defects on the way. Hand-synced twins are the failure mode; a shared leaf is the only shape that cannot drift.

**`/board` (`scripts/fleet-board.py`, 2026-10-15; also `/peers --board`)** renders one read-only card per open seat — lifecycle, subject, last commit, review loops, holds, plan currency, owner-pending rows — every cell derived on that render, nothing stored; alive-or-not comes from the harness's own `claude agents --json` list, never a file time.

### Cross-session messaging — the deliver-and-surface layer (2026-06-19)

The manifest system above *detects* collisions; it has no way for one session to *hand* something to another. That gap closed 2026-06-19 with **session-mail** (`scripts/session-manifest.py` `mail-send` / `mail-check` / `mail-prune`). A session writes a handoff to the git-ignored `.claude/state/session-mail/` mailbox — one file per message, written atomically (temp + `os.rename`, a POSIX CAS) — addressed to a peer's 8-hex session id or `--to all`. `session-start.sh` surfaces a sibling's unread mail into the recipient's context at SessionStart (and `/wrap` Step 0 peeks mid-session); archive-on-read + a 24h/72h TTL prune keep it from re-surfacing or accreting. A third surfacing layer landed 2026-06-21: **`mail-listen`** — a surface-only real-time Monitor stream (the `Monitor` tool at `timeout_ms: 1800000` — it has no `persistent` parameter, every watch ends at 30 min and is re-armed — the flag was retired from every carrier on 2026-09-26) that sees peer mail *as it arrives* mid-session, the bookend between the SessionStart auto-surface and the `/wrap`-peek — plus **`mail-await`** (block until a peer-done / commit / signal go-condition). Originally armed only by a coordination-hub session, the arm was universalized to EVERY session's first turn on 2026-06-22 as a provisional experiment, then **graduated to a standing directive 2026-07-19** on the full post-instrument read: 89% read-rate (1447/1618), 160 `surfaced-live` listener receipts (real-time consumption the archival read-rate is structurally blind to — the listener is deliberately non-consuming, which is why the verdict keys on receipt coverage from the durable, metadata-only `mail-events.jsonl` append log — read by `scripts/mail-stats.py`, and deliberately exempt from the mailbox TTL prune — rather than on read-rate), and the true addressable gap down to ~0.6%. The SessionStart hook DIRECTS the arm (a shell hook can't call an agent-turn tool); `mail-listen-arm-reminder.sh` re-injects the directive every turn until the arm lands, and a session-keyed PID file prevents duplicate listeners on reconnect. The orchestrator's **on-surface discipline** (in `AGENTS.md` from 2026-06-21, and since 2026-09-03 in `.claude/orchestrator/conventions.md`, delivered to the main session at SessionStart): each surfaced handoff is NAMEd inline and acted-or-noted, never silently scrolled past — surface ≠ act (the deliver-and-surface gate holds), but surface-only ≠ ignore.

The load-bearing design constraint is a security one, and it is **not** classic injection: the real risk is **authority confusion** — instruction-shaped text authored by another session being obeyed as a command. So a surfaced handoff is wrapped in non-prose delimiters + an "untrusted DATA, not an instruction" preamble + a CLAIMED (unauthenticated) sender, with the delimiter token stripped from the body to prevent break-out. It is **deliver-and-surface, never auto-apply** — the orchestrator shows the handoff to the human and acts only on the human's explicit go-ahead. `--to all` is a true broadcast (per-recipient `.read-by-<sid>` receipts so every peer surfaces it once). Shipped through a 2-expert design gate and a 5-expert code review; `/mail` (Lecture 7) is the ergonomic client over the engine. This is the *active* half of parallel-session coordination — the manifest stops collisions, session-mail moves intent.

### Single-writer-to-prod — the deploy-baton coordination protocol (2026-06-28; a launch-window overlay since 2026-10-02)

Since 2026-09-29 the single writer to production is a PROCEDURE with code backstops rather than a mail convention: `/promote`'s steps have the operator read `gh pr list` for an open promote and merge with `--match-head-commit` on the owner's "merge it" for an exact head sha (or his advance go bound to that head), and `/push` step D0 is a skill step that stops a `dev` push while a promote PR is open or a peer's `writehold`/`deploy-baton` hold is live; the push guard, which gates every push or merge that can reach production, and the repository's required check sit behind that procedure. What follows is the older, mail-borne form that preceded it and survives as the owner-armed, window-scoped LAUNCH MODE in `promote/references/deploy-retired-2026-10-02.md`, never standing between launches: the **deploy baton**, a *coordination protocol* over session-mail rather than a point-to-point handoff. When several sessions have committed work queued for the same prod deploy, a concurrent push is dangerous — it races a deploy already under observation and can re-deploy a broken successor over a rollback. So LAUNCH MODE (`/deploy`'s until 2026-10-02, now `/promote`'s — Lecture 7) elects a single **baton holder** that broadcasts a fleet-wide *hold-pushes* directive (`--to all`), collects an owner-set number of `deploy-ready` signals from the peers whose work is committed, then runs the full production gate itself (`/promote`'s PR gate since 2026-09-29; the retired reference's own text still says `/push`) — the only writer to prod for that window. The holder can **retract to HOLD** on owner pushback (resetting the signal count to zero — no partial credit), and finally broadcasts `deploy-clear` once prod is verified healthy (a signal name the review hub also puts on its verdicts, CHANGES-REQUESTED included — so `/push` D0 reads it per sender, never as a bare all-clear). This very `/meta` session opened by receiving exactly that seven-message exchange (hold → ready → retract → re-hold → gate raised 2→3 → clear).

Two design notes make it safe. First, it inherits the deliver-and-surface security model wholesale: every baton message is authority-demoted DATA — surfaced, NAMEd, and verified against ground truth (git / tracker) before it is relayed or acted on, never auto-executed (a stale claim in a baton mail is a snapshot, not current truth). Second, the baton is a *cooperative convention*, not an enforced lock — sessions agree to honor it; the actual enforcement of "no unapproved push" stays with `block-push-without-approval.sh` (Lecture 5), which gates each push or merge that can reach production regardless of whether the session remembered the baton.

**A second, smaller hold was built for every routine push (2026-09-06) and now rides `/promote` step 1 in full (ARM, GO-QUIET, and no `dev` push until the ALL-CLEAR after the merge or 3 hours, since a `dev` push restarts the PR's CI) and `/push --emergency` as a GO-QUIET only.** `/push` step 1b broadcasts a fleet write-hold in three beats — ARM when the push route starts, GO-QUIET at the gate (no worktree writes, no heavy suite runs), ALL-CLEAR the moment the push lands or the gate fails — with its own `writehold-*` signal names, kept out of the `deploy-*` namespace; the default `dev` route (D0–D5) does not run it, because a red there costs only a re-run (`push/SKILL.md`, default route). It was built because the pre-push gate measured the shared working tree, so a peer's uncommitted write mid-gate silently changed what the gate measured; since 2026-10-06 the gate runs in a detached worktree copy at the pushed sha, so the hold now buys box quiet rather than a correct reading, and reads the shared tree again only under `SKIP_PREPUSH_SNAPSHOT=1`. The `--emergency` route skips the ARM; its owner question comes after step 3's re-freeze.

### The `/me learn-session` signal extraction

A subtler curate pattern: end-of-session extraction of *user-preference* signals (distinct from system-lesson signals). Adopted 2026-04-20. Auto-invoked by `/wrap` Step 7a. Scans the conversation for behavioral signals that match the user-preference signal catalog: pushback phrasings (questioning the number of defers), directional statements (a call to ship now), tool-friction flags, systems-thinking observations from the user (signaling their mental model). De-duplicates against the user profile and existing feedback memories. Classifies surviving candidates as profile-level or feedback-level.

This pattern's existence is itself a curate-layer insight: user preferences accumulate session over session, and without an explicit extraction step they get re-litigated each time the user has to repeat the same correction.

### The comparison-only tier (added 2026-08-02): catalogued ≠ expert

Not every system worth a row earns a dispatchable expert. Since 2026-08-02 the comparison file carries a tier for systems worth a matrix row and nothing more. Admission to the expert tier runs on three tests: **A1** a distinctive delta at HEAD on the default path, **A2** a nameable consult-demand (what question would we actually route to it?), **A3** an integrity floor (the prior-art rows of 2026-10-09 were judged by a four-prong roster test — alive upstream, code-backed on a differentiator we hold, a lens no roster member has, substance to calibrate against repeatedly). **Scale is a revisit-*cadence* input, never an *admission* input**: a large, widely used system can sit in the comparison-only tier, and a small one can be an expert.

The tier exists because the alternative framings are both wrong. Omitting a large system reads as not having looked; cataloguing it as an expert implies a consult-worthiness the admission bar says it does not have. A comparison-only row says what is true (we looked, we know what it does, and there is no question we would route to it), and it carries promotion triggers checked at the monthly scout.

### Bidirectional adoption methodology (lessons-as-procedure)

Three lessons codified 2026-05-17 form a workflow for any future cross-project port. Reading them together as a *procedure* surfaces the bidirectional pattern more cleanly than the per-lesson framing.

**Step 1 — READ BOTH SYSTEMS BEFORE PROPOSING (READ-BEFORE-PORT discipline).** Before drafting any port plan, read (a) target project's relevant skill spec + MEMORY.md, especially `anti-scope` / `rejected` / `deliberately not` sections; (b) source project's same surface to verify pattern origin. Two failure modes this prevents:

- *Anti-scope conflict:* shipping a pattern into a project that explicitly rejected it.
- *False-gap reciprocity:* shipping a "this is missing" port for a pattern that originated in the target project.

Both are avoided by ~2 minutes of pre-port reading. A conditional hedge attached to the approval of a port plan is codified among the user profile's verification-trigger phrasings as a STOP-and-verify signal.

**Step 2 — EXAMINE BOTH DIRECTIONS (bidirectional reciprocity).** When comparing two systems, ALWAYS examine A→B AND B→A. Single-direction analysis misses reverse-direction opportunities. Spend ≥5 min on the reverse direction before declaring the port plan complete. Skip only when systems are at obviously different scale where reverse-direction yields nothing — even then, document the skip rationale.

**Step 3 — DEFAULT TO ACTIVATES-WHEN-X MARKERS FOR UNMET-DEPENDENCY CHECKS (ACTIVATES-when-X markers).** When porting a skill to a less-developed target, three choices for handling components with unmet dependencies in the target's current state: (a) DROP the check entirely (lossy — re-port needed when phase transitions); (b) SCOPE DOWN the spec to exclude the dependent check (lossy — same re-port problem); (c) KEEP the structure but mark `**ACTIVATES when {concrete trigger condition} lands.**` + current-state substitute. Default to (c). The check activates the moment the condition becomes true, no re-port.

**Trajectory-driven calibration.** When the user signals a project trajectory (for instance, that a project may grow well beyond its current scale), calibrate infrastructure for the FUTURE state, not just the current state. A conditional invitation to add infrastructure if new context warrants it is an invitation to recalibrate, not a directive.

> **TL;DR.** Refresh triggers (when to update), cadence (per-session housekeeping via `/wrap` Step 7d; periodic audit via `/meta architecture-audit`; 90-day strategic review). The doc serves three purposes from the Preface — external map (for return-after-context-loss + onboarding), stable baseline (for "what changed and was it good?" comparisons), and articulator-of-theory (forcing implicit decisions into explicit form). All three degrade as the system evolves; without a maintenance discipline they degrade silently until someone reads cold and notices stale counts.

### Refresh triggers (when to update)

Update the doc on ANY of these conditions:

1. **New skill / hook / rule / command added** that affects the corresponding lecture's enumeration (Lectures 2, 4, 5, 6, 7). Counts in the Preface go stale immediately; the lecture's list section goes stale on the next read.
2. **New /meta subcommand added** — update Lecture 8 entry-points list AND the count ("sixteen primary entry points" → N+1).
3. **New external system catalogued** — the main ideas adopted from it go on the credits page (`docs/where-the-ideas-came-from.md`), smaller ones in the files that carry them.
4. **L# range advances by ≥10 numbered lessons** — Preface count + Lecture 8 + Appendix B all reference the L-range. Stale claims (a quoted lesson range hundreds of lessons behind the actual one) mislead future readers. Note: the L-range moves quickly; pick a refresh threshold that matches your tolerance for staleness vs. update frequency.
5. **Improvement vector ships** — record the ship in `meta/CHANGELOG.md` (not in this doc). If the vector resolves a fragility item, update the corresponding entry in `state.md`.
6. **Architectural decision reverses or evolves** — if a Lecture's described approach changes (e.g., we adopt a previously-rejected pattern, or we deprecate an established pattern), the lecture body needs revision, not just inline markers.

Triggers 1-4 are mechanical (count + list updates, ~5-15 LOC each). Triggers 5-6 require lecture-body revision (~30-100 LOC). Mechanical updates can ship inline same-commit; lecture-body revisions should go through `/meta` invocation for review.

## Appendix A — Glossary

- **ACTIVATES-when-X markers** — pattern for lossless skill ports across phase boundaries (ACTIVATES-when-X markers). When a target system lacks a dependency, keep the skill check structurally + mark `**ACTIVATES when {concrete trigger condition} lands**` + provide a current-state substitute. The check activates the moment the condition becomes true — no re-port needed.
- **Adoption Queue** — trigger-gated workspace-infrastructure patterns to ship next. It is its own file now, `meta/ADOPTION-QUEUE.md`, not a section inside `meta/MEMORY.md`. Complements the product backlog and the ops checklist. Read-only display via `/meta queue`.
- **Auto-fire** — pattern where a skill fires when its trigger conditions match, NOT only on owner invocation. Shipped on `sniff-test`, which now carries **9 trigger conditions** (the ninth, codified-preference application surface, is the one that reaches a short draft no other trigger touches); auto-fire is the default for any safety/audit/quality-gate skill.
- **Bidirectional reciprocity** — when comparing two systems, examine A→B AND B→A. Single-direction analysis misses reverse opportunities (bidirectional reciprocity). ≥5 min on reverse direction before declaring port plan complete.
- **Calibrated skepticism** — frontmatter `skepticism: low|medium|high` declaration that biases panel composition. Adopted from wan-huiyan/agent-review-panel.
- **Capture / Curate / Enforce** — the three layers every system action lives in. Capture is passive signal collection; Curate is active triage; Enforce is mechanical activation at composition time. The principle: classify the failure mode before proposing a fix.
- **D + I + S rubric** — Durability + Impact + Scope, each 0–3. **Total ≥6 mints a numbered `L#`** — a `RULES.md` row is a *further* test, earned only when the lesson also has a concrete trigger, a sub-15-second action, and generalizes across contexts; plenty of ≥6 lessons never get one. 4–5 enters the watch-tier register (`WATCH-TIER.md` + its shards), auto-promoting on a second occurrence; ≤3 drops. Adopted from alirezarezvani.
- **Defer-with-trigger** — every deferred work item must have a reason (one of 3 valid categories), a LOC estimate, and a trigger condition (not "post-launch"). Enforced by `/audit-check` Check 8.
- **Evidence-class labels** — labels attached to audit findings indicating evidence strength. **Three, not four:** `[CONVERGED]` (2+ experts, independent evidence each), `[SINGLE-SOURCE]` (one expert; the default, and omittable — explicitly *not* a downgrade), `[DISPUTED]` (2+ experts disagree, which triggers the dispute step). There is no `UNVERIFIED` label — the word appears in the skill only to mark an incomplete fan-out. `[SINGLE-SOURCE]` and `[DISPUTED]` are a partial adoption of wan-huiyan's epistemic-label system (eight labels at adoption, meta v2.8.2; 12 in the spec's label line / 15 in the README table at v3.9.1); `[CONVERGED]` came with the severity-promotion rule adopted from alirezarezvani.
- **L{N}** — a numbered lesson, whose body lives in a `meta/MEMORY-ARCHIVE-*.md` shard with a digest row in the `MEMORY.md` router. The N is **allocated** by `scripts/lesson-mint.mjs`, not derived from the current maximum — `maxL` is a read, not a reservation, so two concurrent sessions deriving `maxL+1` would collide (Lecture 8). Numbering is therefore monotonic but not gapless, and a freed number is never reassigned. RULES.md rows cite L{N} back to the lesson body. Per L# topic-tag convention the going-forward convention is to append a topic tag — `L<N> (topic)` rather than a bare `L<N>`. ⚠️ *Written with a real number on both sides, this example destroys itself: the annotation sweep that maintains the convention re-tags the "bare" half too, leaving two identical strings and a sentence that contrasts nothing. It stood that way here for months. The placeholder form is deliberate — the sweep cannot match it.*
- **sub-agent MEMORY blocks** — the specific lesson that subagents cannot directly write to skill MEMORY.md. Enforced by `block-subagent-memory-write.sh`. Bypass via `/tmp/claude-meta-mem-allow` marker — orchestrator only; a sub-agent payload is refused it since 2026-10-10.
- **LARP markers** — human-consultant role-play leaking into agent output: "~Nh / N days / N weeks / takes N min" in recommendations, plus "post-launch" and authority-hedging. Per the LARP-markers lesson these carry a consultant's incentive layer from training data and have no counterpart in agent execution — convert to LOC / file-count / tool-call count, or delete. *(The glossary read "language-as-resemblance-pattern" here; that expansion appears nowhere else in the repo and was invented by this entry.)*
- **Panel Playbook** — a per-audit record of which experts were on the panel and how the audit went. Its sections live across the meta memory shards — so grep the skill **directory**, not `MEMORY.md`. Used to bias future panel composition. Each entry: panel size, experts, contrarian rotation, defer-promotion rate, finding-to-noise ratio per expert.
- **Parallel session** — running multiple Claude Code sessions against the same repo concurrently. Triggers special git/memory coordination rules (parallel-session coordination + pre-stage check + sub-agent MEMORY blocks + no `git stash` / no `git add -A`).
- **Process log** — artifact written for `full` and `--final-audit` panels of 7+ experts, and for **any panel of 3+ when a verdict truncates** or when the orchestrator's context is ≥~80% at dispatch / a compaction fires mid-panel (2026-07-11). It holds verbatim per-expert output plus a synthesis-mapping footer, and synthesis **reads it back** — that read-back is the point, since the retention failure it fixes is a finding lost between expert and synthesis. It captures no timing. Adopted from wan-huiyan/agent-review-panel v2.7.2 (panel-size trigger broadened ≥9→≥7 on 2026-06-14, made read-back the same day).
- **READ-BEFORE-PORT discipline** — codified as a numbered lesson. Before drafting any cross-project port plan, read the target's relevant SKILL.md + MEMORY.md (especially anti-scope / rejected sections). Catches two failure modes: anti-scope conflict + false-gap reciprocity. ~2 min cost prevents wrong ports.
- **`/wrap` 3-part defer test** — every defer added this session must pass: (a) cited evidence verifies on grep, (b) inverted "ship unless…" framing survives, (c) blast-radius + effort weighting promotes obvious wins.
- **Skepticism (low|medium|high)** — frontmatter field on the expert's **SKILL.md**; agent files carry none. Biases panel composition. The copy's experts split 6 high / 21 medium / 6 low; the high set is security, QA, legal, uncle-bob, the engagement psychologist and haines-churn-prevention.
- **Sycophancy detection** — orchestrator-level gate against second-round agreements that reverse first-round positions without new evidence. Codified in user pushback signal + **sniff-test Check 2** (position-flip under rebuttal), with Check 4 as its frustration-marker companion (re-examine, don't capitulate), plus `/expert-review`'s verdict-flip-needs-new-evidence gate. Required because the model defaults to agreeable on rebuttal pressure (Kim 2025).
- **Three-tier model strategy** — the wshobson-derived frontmatter convention: Opus for orchestration + complex synthesis, Sonnet for most experts, Haiku for utility. As *declared*, our roster is 56 `inherit` (it was 50 opus / 6 sonnet / 0 haiku until the definitions stopped fixing a model). As *run*, it has been superseded by the fleet model-routing policy, which has since been amended repeatedly (at least ten amendments on record in the policy file) and no longer resembles the one-line summary this entry used to carry: the orchestrator runs Fable for judgment sessions and Opus for procedural ones; **review panels are Opus at inherited effort with a mandatory Fable ladder — ≥1 Fable seat at 3+ seats, ≥2 at 6+, ≥3 at 9+, and only the review hub chooses whether to spend one**; reads and short implementation are Opus while long-running builders go to Fable; and a breaker is never routed below its builder's tier in a working-session panel — for hub reviews the rule gives way (Lecture 6).
- **Trajectory-driven calibration** — when the owner signals a project trajectory (for instance, that a project may grow well beyond its current scale), calibrate infrastructure for the FUTURE state, not current state. Cue is often an invitation-not-directive (a conditional offer to add something if the context has changed).
- **Trigger-index** — the table at the top of `project-memory/MEMORY.md` mapping "if about to do X" to "check Y first". Active-recall layer for the orchestrator. ⛔ **Both of its former companions have moved out from under it since the exhortation cut.** `.claude/rules/active-recall.md` (the ~34-row Band-U hot tier) is no longer always-loaded — it was `paths:`-scoped to the rules ARCHIVE on 2026-09-07, so it now reaches a seat only during rule archaeology. Band-O is still a file (`.claude/orchestrator/active-recall-orchestrator.md`) but its per-turn injection is switched **off** via `SKIP_BAND_O_INJECT=1`, so `band-o-inject.sh`'s three registrations are inert. And `meta/RULES.md` is a two-tier router since 2026-09-04, with the rows in `RULES-SHARD-*.md` beside it — grep the directory, because the router alone reads a clean zero for a live rule. The index itself also shed 25 rows on 2026-09-09 and a further 20 on 2026-09-25 to `.claude/orchestrator/conventions.md` (a plane move, not a cut: they still load, for the main session only).
- **Verification-trigger phrasings** — owner-side phrasings (a conditional approval, or a question comparing this system with another) that signal STOP-and-verify intent rather than approval-with-caveats. Codified in the user profile from 2026-05-17 session evidence.
