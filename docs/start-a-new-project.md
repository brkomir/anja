# Start a new project from Anja

This page takes you from copying Anja into your repository to your first working session. It has two paths:

- **[The minimum first success](#the-minimum-first-success)**: the shortest route, with the copy as shipped, to one session that plans on disk, commits through a guard, and has its change reviewed by agents that did not write it. The clean-up waits for later.
- **[Full adoption](#full-adoption-and-customization)**: what you supply, what to take out, the eight-step first run, how to start smaller than the source project did, and how to turn off the multi-session plumbing if you work alone.

When you finish either one, the hooks refuse or warn at the costly moment, a working plan carries each session across a compaction, and a change can be reviewed by agents that did not write it.

## Before you start

- **A working example, not an installer.** You copy the parts you want into your own repository and edit them. There is no plugin form, because the copy is one project's `.claude/` tree, scripts and git hook as they ran, wired through that project's own settings file; its skills, agents and hooks sit under `.claude/`, not where Claude Code looks for a plugin's parts (`skills/`, `agents/` and `hooks/hooks.json` at the plugin's root), so Claude Code's plugin commands cannot install it. The full setup is the eight steps under "First run": copy the machinery, edit the settings, wire the git hooks, set up project memory, run the smoke suite, run the scripts' self-tests, read what is still red, and open your first session.
- **Tools.** Claude Code, git 2.31 or later (`scripts/setup-project-memory.sh` uses `git rev-parse --path-format`), bash, Python 3, Node.js and jq. The hooks are bash and Python scripts, and many of them use jq; the scripts under `scripts/` are bash, Python and Node.
- **Systems.** Built on macOS; its hook tests also ran on Linux; Windows has not been tried.
- **What opening a session runs.** Opening the copy in Claude Code runs its hooks. They are scripts that run with your full user permissions: in an interactive session once you trust the folder (or a parent folder whose trust covers it), under `claude -p` or the Agent SDK with no prompt at all, and in a repository you have already trusted with no new prompt once you copy them in. Read `.claude/settings.json` first, or start with `claude --settings '{"disableAllHooks": true}'`. With the hooks on, the start-up hooks give the main session the orchestrator files at every start, resume, `/clear` and compaction, and on the first turn, before your task, tell the agent to open a working plan under `plans/` and to start a background listener for mail from other sessions. The first commit-shaped command in each context window is refused once while the commit rules arrive, and the agent then runs it again. The table under "Start smaller than the source project did" gives the size of each delivery and the two switches that turn them off.

## What you are taking

Anja is a working `.claude/` tree: hooks, rules, skills, agents and scripts, plus its pre-commit git hook and the notes on the git hooks it ran. It ran from March to October 2026 on one production application, the source project, which was built with it. It ships as it ran, with that application's own files taken out. The copy lists 461 files. They are 34 agent definitions plus the shared agent primer, 153 skill files (87 of them `SKILL.md`), 65 hook scripts with their 5 helper libraries and 3 fixtures, 9 rule files, 4 orchestrator files, 4 commands, 8 templates, 3 documents, the shell-traps table, 5 settings and notice files under `.claude/`, 133 files under `scripts/`, the git hooks' README and `pre-commit` hook, and 31 files written for the copy (the root README, LICENSE, NOTICE, TRADEMARK, CONTRIBUTING and CODEOWNERS, the `.claude/.gitignore`, eight pages under `docs/`, four starter registers and a `CLAUDE.md` starter under `docs/starters/`, and ten diagrams and the logo under `docs/images/`). `.claude/settings.json` wires 58 of the 65 hook scripts, and 2 more run because another hook calls them. The other 5 ship unwired (the three that step 2 says when to switch on, and two that ran from the source project's `pre-push` hook), and `docs/repository-map.md` names the event each was written for. The `pre-push` hook is not in the copy. The project's own source, tests, trackers, memory and logs are also left out, and "What you supply" below says what fills each gap. A good deal of the text still describes the source project. Read it as a working example of the mechanisms, not as a template you can drop in unchanged.

## The minimum first success

This path uses only what ships, and only the parts a first session needs. It leaves the clean-up under "What to replace or remove after copying", the trackers and the optional pieces for full adoption. Read "What opening a session runs" under "Before you start" before step 6.

1. **Copy `.claude/`, `.githooks/` and `scripts/` into the root of your repository**, with this repository's `LICENSE` and `NOTICE`, as step 1 of [the first run](#first-run) describes, including what it says about merging into an existing `.claude/settings.json` or `scripts/`. Keep the settings as shipped for this path, the seven switches from ["One session at a time"](#one-session-at-a-time) included: one of them stops the commit rules arriving, and step 6 relies on them. Add the switches after step 8 if you will run one session at a time. *Expect:* nothing runs yet; the hooks run when a session opens.
2. **Create `CLAUDE.md`.** Copy `docs/starters/CLAUDE.starter.md` to the root of your repository as `CLAUDE.md` and fill in what you can. *Expect:* every session loads it, and its table tells each session which path-scoped rule files exist.
3. **Wire the git hooks:** `git config core.hooksPath .githooks`. *Expect:* the shipped `pre-commit` hook runs on your commits.
4. **Set up project memory.** Create `.claude/project-memory/` with a short `MEMORY.md` index in it, then run `./scripts/setup-project-memory.sh`. Read its header and step 4 of the first run first: if Claude Code already holds memory for this checkout, the script moves those files into the directory. *Expect:* it prints the repository's memory directory and the harness path it links there; without the directory it stops with an error.
5. **Run the smoke suite**, `./scripts/smoke-test-hooks.sh`. It takes minutes. *Expect:* red arms, and a closing summary that lists them. In a fresh repository holding only the copy it passed 2,049 arms and failed 169; in your repository, with your own files and steps 2 to 4 done, the count may differ. The suite tests the hooks and does not switch any of them on or off, so a red arm does not stop this path. Step 7 of [the first run](#first-run) says what each group of red arms drives and what to do about it.
6. **Open Claude Code in the repository, and ask for one small change to a file you name, committed.** *Expect:* on the first turn, before your task, the session is told to open a working plan under `plans/` and to start a background listener for mail from other sessions; its first commit-shaped command is refused once while the commit rules arrive, and it then runs the command again. (With the seven switches of "One session at a time" set, the listener directive and the commit rules never arrive: the first commit is not refused, and nothing then tells the session to commit through the guard, so the guarded commit this step expects does not happen. That is why step 1 keeps them off until this path is done.) Those rules tell it to commit through `scripts/safe-commit.sh`, which stages exactly the paths it names and refuses if anything else is staged.
7. **Have the change reviewed:** `/expert-review --code --last 1` (the commit needs an earlier commit beneath it). For Claude Code's own review instead, type `/review`, the bundled alias that a project `code-review` skill does not replace (the vendor's skills page, read 2026-10-21). *Expect:* with no other session running, the review runs as fresh helper agents given only the commit, so none of them wrote it. It picks its reviewers from the paths the commit changed (see "The paths the review panel is picked by" below). The verdict and its findings come back in the session's reply and in its working plan under `plans/`; the skill's Code Review step 6 and its code-review reference also ask it to write them to `.claude/reviews/<full-commit-sha>.md` and commit that file, so check for the file (two non-interactive runs on a fresh copy, before that step existed, returned the verdict and wrote no file; a third run, with it, wrote and committed the file).
8. **Look at the plan:** `/working-plan` brings the session's working plan up to date and shows it whole. *Expect:* one file, `plans/session-…md`. After a compaction, `/post-compact` rebuilds the session's hand-off state from it.

That is a first success: a guard acted at the commit, a plan on disk carries the session, and agents that did not write the change reviewed it. What this path leaves as shipped is the subject of full adoption: the source project's rule files, domain experts, review paths, pins and keyword map are still in place (`migrations.md` loads in every session), the red arms are unread, and the files the other commands read do not exist yet.

## Full adoption and customization

Full adoption makes the copy yours. The sections below follow its order: what you supply, what to take out, the eight-step first run, starting smaller than the source project did, and turning off the multi-session plumbing if you work alone.

## What you supply

Each line names the file or directory, then what in the copy reads it. Only `CLAUDE.md` and the project memory directory (step 4) are worth creating before your first session; add the others when you start using the command that reads them.

- **`CLAUDE.md`** (project root, not shipped). This is the entry file the harness loads into every session. Three hooks treat it as always-loaded: `check-memory-budget.sh` checks its size against a byte pin in `.claude/band-pins.json`, `block-subagent-always-loaded-write.sh` stops a sub-agent from writing to it, and `always-loaded-claim-warn.sh` warns on edits that make claims in it. `scripts/band/narrative-mass.py` and the corpus-drift probe in `scripts/probes/` read it when it exists. In the source project it worked as a router. Its table told each session which path-scoped rule files exist, and nothing else can do that job, because the harness strips a rule file's frontmatter before injecting it. A neutral starter with that table, built from the copy's own rule files, ships as `docs/starters/CLAUDE.starter.md`: copy it to your root as `CLAUDE.md` and fill in the blanks.
- **`AGENTS.md`** (not shipped, optional). The source project included it from `CLAUDE.md`. The same budget hook, write guard and claim hook read it, and they act only when a session writes to it, so write one only if you want a second instruction file beside `CLAUDE.md`. Most of its original content now lives in `.claude/orchestrator/conventions.md`, which says so at the top.
- **A way to deliver the orchestrator files.** The four files in `.claude/orchestrator/` hold rules that only the main session can act on, and the source project delivered each one to the main session alone: `orchestrator-inject.sh` carried the conventions and the session doctrine at session start (the launcher `scripts/claude-main.sh` puts the same two into the system prompt instead), `commit-doctrine-inject.sh` carried the commit doctrine on the first commit-shaped command, and `band-o-inject.sh` carried the active-recall rows on every turn. All of them ship. All three are wired in `.claude/settings.json`, and the settings' `env` block switches `band-o-inject.sh` off. Keep that wiring, write your own delivery, or include the files from `CLAUDE.md`. Including them puts them in every sub-agent's context too, which is the cost "Start smaller than the source project did" warns about below; its table gives the size of each delivery.
- **A todo file (`todo.txt`).** `/orient` counts its open items and checks their deferral triggers. `/summary`, `/wrap` and `/expert-review` read rows from it and add rows to it.
- **A backlog (`BACKLOG.md`).** `/wrap` sweeps it at the end of a session.
- **A decisions log (`DECISIONS.md`).** `/wrap` step 3a sweeps it through the `/decisions` skill. `/meta` and `/expert-review` cite it.
- **An ideas file (`IDEAS.md`).** `/summary` searches it, alongside the other trackers.
- **A manual test plan (`QA_TESTING_PLAN.md`).** `/expert-review` appends manual-test entries to its Part 7, and `/meta qa-plan-audit` consolidates them.
- **A plans directory (`plans/`).** `/summary`, `/working-plan` and `/post-compact` each write one working plan per session to `plans/session-…md`.
- **The project memory directory (`.claude/project-memory/`, with a `MEMORY.md` index).** `check-memory-budget.sh` caps the index. `warn-large-tracker-read.sh` warns when a session reads a large memory file whole. `trigger-index-match.sh` matches each prompt against keywords and points at memory entries. Its keyword map lives inside the script, so you rewrite it for your own memory. `/wrap` and `/meta` write to the directory.
- **The audit registers (optional), from the starters.** `/flows`, `/features`, `/surfaces` and `/ops` read four registers in the project memory directory, and `/audit-check` reads a flow, feature or ops row before it lets you mark that row complete. A starter for each ships in `docs/starters/` (`project_critical_flows.md`, `project_feature_audits.md`, `project_surface_audits.md` and `project_ops_register.md`). Copy each one you want, keeping its name, into `.claude/project-memory/` after step 4, before the first run of the command that reads it. The fifth starter, `CLAUDE.starter.md`, goes to your root as `CLAUDE.md` (the first line of this list).
- **The skills' memory files (`.claude/skills/<name>/MEMORY.md`).** The copy ships none. Under the agent primer's memory-read protocol, every dispatched agent reads its own file first. Agents don't edit these files themselves. They return a memory-update block, and the main session saves it. `/meta` reads these files across the whole tree. The corpus-drift probe also expects `/meta`'s own files (`.claude/skills/meta/RULES.md` and its `MEMORY*.md` and `WATCH-TIER*.md` files) and prints MISSING for each one it can't find. `scripts/architecture-counts.mjs` reads the same `RULES.md` and stops with an error unless it is in the router form `scripts/rules-tier-split.mjs` writes.
- **The state and log directories (`.claude/state/`, `.claude/logs/`).** The hooks create them at run time, and the settings file links them into every worktree (the logs directory only while nothing under it is tracked: once the two audit ledgers are committed, a worktree checkout holds a real logs directory and Claude Code skips that link, so hooks there write their logs locally; measured on Claude Code 2.1.306, 2026-10-21). `session-start.sh` writes state, and several hooks append their fires to logs. Two telemetry probes in `scripts/probes/` stop with an error until `.claude/logs/architecture-doc-drift.jsonl` exists. The copy's own `.claude/.gitignore` already keeps both directories out of git, with `.claude/worktrees/` and `.claude/settings.local.json` (all but the two audit ledgers under `.claude/logs/`, which it re-includes by name for the expert-review skill): the logs record fragments of commands and of what was typed, and the state directory holds session mail and compaction checkpoints. Keep that file when you copy the tree.
- **A locale bundle (`messages/*.json`)**, but only if your project translates its interface. The agent primer has a rule for adding top-level keys to `messages/en.json`, and `/orient`, `/agent-work` and `/expert-review` refer to the bundle.
- **The product context file (`.agents/product-marketing-context.md`, not shipped).** This is the product context every expert agent definition points to.
- **Your test entry points.** The agent primer names `npm run test:integration` and `./scripts/e2e-local.sh` as the right way to run tests. The second one is not in the copy. `scripts/integration-test.sh` ships, but it sources a diagnostic script and a column-permissions snapshot query that belonged to the source project's database. Remove those two steps or supply your own.
- **A pre-push git hook (optional).** The copy ships the pre-commit hook and not the pre-push one, and several shipped hooks and skills expect a pre-push hook to run the gates they describe. Write your own (step 3), or leave it out.
- **Path placeholders.** Some scripts carry `<repo-root>`, `<home>` or `<project-key>` in code where a path to your repository, your home directory or your project's transcript directory belongs. Fill these in before you rely on one. `scripts/band-o-echo-scan.py`, which `session-start.sh` runs at every start, reads such a path and finds nothing until you do.
- **A CI workflow (optional).** The copy ships none. `/promote` opens a pull request and waits for its full CI run, and `docs/github-settings.md` says to require the smoke suite's check once your CI runs it, so write a workflow that runs `scripts/smoke-test-hooks.sh` if you want either.

## What to replace or remove after copying

Step 1 copies the machinery whole. Take out or replace what belongs to the source project before step 5 runs the smoke suite, so its red arms describe the tree you mean to keep. Copy the mechanisms, and leave out anything that reads as the source project's history:

- **Dated provenance inside rules and documents.** That covers "this read X until <date>" corrections, figures measured on the source project, and incident stories. The directive in a rule is the mechanism; the date and the number behind it are history. The rule files' own appending convention sends incident records to an archive, and that archive is not in the copy.
- **Counts in `.claude/docs/architecture.md` and `.claude/docs/state.md`.** The architecture document says itself that its counts drift. Generate counts for your own tree with `scripts/architecture-counts.mjs`, once `/meta`'s own files (`.claude/skills/meta/RULES.md` in the router form `scripts/rules-tier-split.mjs` writes, see "What you supply") are in place: without them it stops with an error.
- **The values in `.claude/band-pins.json`.** They pin the source project's files, including 10 rule files that are not in the copy. Once your own files exist, delete `.claude/band-pins.json` and run `bash .claude/hooks/check-memory-budget.sh --refresh-pins`: on an existing file that command only lowers pins, and most shipped rule files are already larger than the source project's pins.
- **The stack-specific rule files**: `nextjs.md`, `tests-e2e.md`, `tests-unit.md` and `typescript.md`, scoped to one web application's layout (`src/app/**`, `tests/**`; `typescript.md` also matches `scripts/**` and the build config, so it loads whenever a session reads one of the copy's own scripts), and `migrations.md`, which is not scoped and loads in every session. Keep each only if your stack matches; keep `migrations.md` only if your project applies SQL migrations to a Postgres database, which is what it was written for.
- **The domain experts** built for the source product. Keep the pattern and the generator (`scripts/generate-expert-agents.mjs`), and write experts for your own domain.
- **The paths the review panel is picked by.** `/expert-review --code` chooses reviewers from each expert's `applies_when:` paths and from the routing table in `.claude/skills/expert-review/SKILL.md`. They name the source project's layout (`src/**`, `tests/**` and its migrations folder); point them at yours, or a review of code outside those folders may go without the code-design expert.
- **The two parked rule files**, `active-recall.md` and `behavioral-anti-patterns.md`. They are a record of a rulebook style that a measured cut retired, not a starting point.
- **The keyword map in `trigger-index-match.sh`, and the `skillOverrides` block in the settings file.** Both name the source project's own entries.
- **The reviewers in `CODEOWNERS`.** Step 1 leaves the file behind. If you keep it, or run your own copy of this repository, put your own reviewers in it before you turn on the rule that requires a code owner's review ([github-settings.md](github-settings.md)): it names the source project's maintainer as owner of `.claude/hooks/`, `.claude/settings.json`, `.githooks/` and `scripts/`.

## First run

1. **Copy the machinery, not this repository's front page.** Copy `.claude/`, `.githooks/` and `scripts/` into the root of your repository, merging into what is already there and never overwriting your own files; an existing `scripts/` may hold files of the same name, so check before you copy. If your project already has a `.claude/settings.json`, keep it: merge the copy's `hooks`, `env`, `statusLine`, `worktree` and `skillOverrides` blocks and its `skillListingBudgetFraction` key into it, plus any `permissions` entries you want, and leave your own entries in place, such as any `enabledPlugins` entry. Without the `hooks` block nothing in the copy runs, and nothing tells you so. Step 2 then edits the merged file. Leave this repository's `README.md`, `CONTRIBUTING.md`, `CODEOWNERS`, `TRADEMARK.md` and `docs/` behind: they describe the copy, not your project (from `docs/starters/`, take only the starters "What you supply" names). Keep this repository's `LICENSE` and `NOTICE` with the files you copied, beside your project's own licence rather than in place of it, and keep `.claude/NOTICE` and `.claude/third-party-origins.md` in place: the root files carry the copy's own licence and notice, and the two under `.claude/` carry the licence notices for the adapted outside text in several skill and agent files. Then take out or replace what "What to replace or remove after copying" lists, before step 5.
2. **Edit `.claude/settings.json`.** Every hook command finds the repository root itself through `CLAUDE_PROJECT_DIR`, so you don't need to change any hook paths. These are the blocks to change:
   - `permissions.allow` pre-approves reads, a few read-only `git` and shell commands, and edits to the skills' memory files and the agent definitions. It pre-approves none of your toolchain's commands; add your own checks here. The three `git` rows match `git status`, `git log` and `git diff` themselves and nothing longer, so `git difftool`, which can run any program you name, still asks; and `permissions.ask` makes any `git` command that writes a file through `--output` ask you first. Nothing stops Claude reading your `.env` files: Claude Code denies no path until you add a `Read` deny rule for it, and its permissions page (read 2026-10-21) gives `Read(./.env)` as the example. Such a rule covers Claude's file tools and the file commands it recognizes in Bash, not a script that opens the file itself; only the sandbox blocks every process.
   - `worktree.symlinkDirectories` links `node_modules` into each worktree. Keep the two `.claude/` entries and change the rest to fit your stack.
   - `skillOverrides` makes each of the copy's 33 domain experts user-invocable only, which keeps them out of the skill listing.
   - `env` sets `SKIP_BAND_O_INJECT=1`. It keeps the per-turn rule injection switched off, which is the state the next section describes. Leave it set unless you mean to measure that injection yourself. It also sets `CLAUDE_BASH_MAINTAIN_PROJECT_WORKING_DIR=1`, which returns the main session's shell to the directory the session started in after each command. Two more switches go in the same block if you want them: `SKIP_ORCHESTRATOR_INJECT=1` stops the orchestrator files arriving at session start, and `SKIP_COMMIT_DOCTRINE_INJECT=1` stops the commit rules arriving with the first commit, and that commit being refused once.
   - `statusLine` runs `scripts/statusline.py`, which shows the prompt-cache countdown, context fill, plan usage and sub-agent count, and on every refresh writes `.claude/state/statusline-<the session id's first 8 characters>.json`. To keep your own status line, point `statusLine.command` at it. The keep-warm gate then loses its countdown, usage-limit and context checks and times its pings from the transcript instead (keep-warm itself is off until `.claude/state/keep-warm-enabled` exists; section 2 of [saving-the-cache.md](saving-the-cache.md) says how to switch it on); to keep those checks, have your status line write the same file (`write_state` in `scripts/statusline.py` lists the fields). If you also want this status line in your other projects, copy a committed version to `~/.claude/statusline.py` (`git -C <your repo> show <branch>:scripts/statusline.py > ~/.claude/statusline.py`) and never symlink it into a working tree: every other project would then run that tree's unreviewed edits every 30 seconds. One row, the Fable model's weekly usage, needs a lookup that is off by default, because it reads your Claude Code login token (on macOS from the Keychain, falling back to Claude Code's credentials file when the Keychain returns nothing; on other systems from that file) and sends it to an Anthropic address that is not publicly documented and can change without notice. Anthropic's terms for Claude Code (its legal and compliance page, read 2026-10-12) say a subscription login is meant for Claude Code and Anthropic's own apps, and that Anthropic may enforce that without warning; whether this lookup counts is Anthropic's call, so turn it on only if you accept that risk to your account. To turn it on, start the command with `STATUSLINE_USAGE_FETCH=1 ` (`"command": "STATUSLINE_USAGE_FETCH=1 python3 …"`); without it nothing reads the token and that row is not shown.
   - Three hooks ship switched off, with no entry under `hooks`: `grep-blowup-warn.sh`, `agent-dispatch-memory-guard.sh` and `agent-memory-brief-warn.sh`. Wire `grep-blowup-warn.sh` (before a shell call) once a grep with a variable-width quantifier before an alternation has run your machine short of memory; it blocks that shape, and its warn arm fires on any recursive grep from an absolute path, so expect noise there. Wire `agent-dispatch-memory-guard.sh` (before a sub-agent dispatch, macOS only) once parallel agent waves have pushed the machine into heavy swap; it refuses a dispatch above a swap-plus-compressor threshold. Wire `agent-memory-brief-warn.sh` (before a sub-agent dispatch) once your expert agents keep memory files; it warns when a brief leaves out the agent's memory path.
3. **Git hooks.** `.githooks/README.md` explains the wiring (`git config core.hooksPath .githooks`). It also explains why a hooks path that silently drifts turns off every gate. The `pre-commit` hook it describes ships; the `pre-push` hook does not. Write your own `pre-push`, or leave it out.
4. **Project memory.** Create `.claude/project-memory/` with a `MEMORY.md` index in it, then run `scripts/setup-project-memory.sh`, which links the harness's per-project memory location to that directory so the memory is versioned with the code. Read its header first. The script stops if the directory is missing, and if Claude Code already holds memory for this checkout, it moves those files into `.claude/project-memory/`, where they become tracked content; read them before your next commit. Use the script rather than the native `autoMemoryDirectory` setting: `/features` and `/ops` read their registers through the harness's own memory path, which only the script's link points at your directory. Keep the index short: the harness loads only the first 200 lines or 25 KB of it, whichever comes first (the vendor page "How Claude remembers your project", read 2026-10-21). Then copy in any register starters you want ("What you supply", the audit registers).
5. **Run the smoke suite**, `./scripts/smoke-test-hooks.sh`. It sends a firing payload and a safe payload to each hook and checks that the settings wiring holds together. It also checks that the agent definitions contain their required clauses. It takes minutes, not seconds. The suite's header records 3 minutes 34 seconds to 3 minutes 48 seconds for a full local run in the source project. `--list` numbers its sections, and `--for <changed file>` runs only the sections that drive that file. A partial run is a reviewer's shortcut, not a gate.
6. **Run the scripts' self-tests.** About 60 of the copied scripts and hooks accept a `--self-test` flag that runs the script against its own fixtures. Two examples are `node scripts/skill-lint.mjs --self-test` and `scripts/safe-commit.sh --self-test`. On the copy the first prints 64 pass / 1 fail: the failing arm walks the memory files and needs at least one skill `MEMORY*.md` and one file in `.claude/project-memory/`. Step 4 supplies the second; the copy ships none of the first, so the arm stays red until your first skill memory file exists.
7. **Expect red arms, and read each one before you fix anything.** On a tree that has none of your files yet, a red arm usually means something it drives is missing, not that a hook is broken. The suite drives every member it finds in `.claude/hooks/`, `.claude/agents/`, `.claude/skills/`, `.claude/rules/` and `scripts/lib/`. Run on 2026-10-27 in a fresh repository holding only the copy as it stood that day, as a single commit with no project files and no installed packages, it passed 2,049 arms and failed 169. Each of the 169 was traced to what it drives:
   - **125 drive files the copy does not ship.** 91 of them drive the `pre-push` hook. Most of those check the source project's own hook line by line, with its messages and exit codes, so writing your own `pre-push` turns only a few of them green; rewrite or drop the rest. The other 34 drive `scripts/check-copy-test-orphans.py` (12), `.claude/hooks/expand-before-code-warn.sh` (7), `scripts/promote-precheck.sh` (6), `scripts/pre-deploy-check.sh` (5), two of the source project's rule files, its interface-text rules (2 arms expect a hook to warn when a session grows that file past its size limits) and its database rules (1 arm expects a hook to name that file when a session creates a file in the source tree's database folder), and `scripts/check-auth-actions.sh` (1).

## Start smaller than the source project did

The rule is simple: start with the least that works, and make every addition earn its place.

- **Start with the hooks and `bash-environment.md`.** In this copy two rule files are unscoped, and both load in every session and in every sub-agent except the built-in Explore and Plan agents: `bash-environment.md` at about 34 KB, measured facts about the shell and the Bash tool, and `migrations.md` at about 20 KB. Keep `migrations.md` only if your project applies SQL migrations to a Postgres database, which is what it was written for; otherwise delete it. The source project loaded a third unscoped file, its security rules, which the copy does not ship. The other seven rule files carry `paths:` frontmatter, so they load only when the session reads, writes or edits a matching file. Two of those seven, `active-recall.md` and `behavioral-anti-patterns.md`, are scoped to an archive directory that is not in the copy, so they never load (see "What to replace or remove after copying").
- **Add a rule only when a measurement earns it.** A rule that records an observed failure, its tell and its fix earns its bytes. A rule that only urges care doesn't.
- **Promote a guard from warn mode to block mode only after its fires are logged.** Every new hook starts in warn mode, and the fires it logs under `.claude/logs/` are the evidence for promoting it. Set the bar per guard, and per arm within a guard. A string-matching guard gets most of its false positives from text that mentions the pattern without running it, such as fixtures, documents and commit messages. Those false positives peak in the burst of writing that follows its own promotion.
- **Keep every always-loaded byte under suspicion.** Each sub-agent dispatch pays for the whole always-loaded set, every time. The copy's figures below are rounded (KB means 1,000 bytes) and checked against the copy's files at every copy commit; the source project's figure is exact:
  - In the source project, the rule set was 615,113 bytes across 19 files on 2026-10-10.
  - The copy ships 9 of those files, about 327 KB in total.

## One session at a time

The copy was built where several Claude Code sessions worked on one branch at once and passed work to each other by mail, with one of them reviewing the others' commits. Two or three sessions on one project, however small, keep that setup as shipped: the mail listener lets one session reach another, the commit checks protect the git index they share, and one of them can run `/review-hub` and do the reviewing.

If you never run two sessions at once in a repository, that plumbing has nothing to do. Seven switches in the settings' `env` block turn it off:

```json
"SKIP_MAIL_LISTEN_ARM_REMINDER": "1",
"SKIP_MAIL_SEND_CARRIER_WARN": "1",
"SKIP_MAIL_RELAY_CHECK": "1",
"SKIP_DELEGATE_REVIEW_WARN": "1",
"SKIP_STANDBY_RESUME_CHECK": "1",
"SKIP_COMMIT_PATHSPEC_WARN": "1",
"SKIP_COMMIT_DOCTRINE_INJECT": "1"
```

- **The mail listener.** The session is no longer told at its start, and on every prompt after it, to arm a listener for mail from other sessions.
- **The mail checks.** The warnings on how a mail is written and on relaying a mail's claims unchecked stay quiet.
- **The review hand-off.** The warning to send a code review to a review session by mail stays quiet. The review itself does not change: `/expert-review --code` checks whether any other session is around, and when none is, it reviews with fresh helper agents in the same session.
- **Standby.** The resume steps for a session parked with `/standby` are not injected.
- **Commits.** The warning on a commit with no pathspec, and the commit rules that arrive with the first commit and refuse it once, are both written for a git index several sessions share.

Everything else stays on: the save before a compaction and the recovery after it, the readouts that derive their numbers live, the expert panels and their memory, and the path a correction takes from a lesson to a rule to a guard that earns its right to refuse from its own fire log. Two of these start switched off however many sessions you run: keep-warm needs `.claude/state/keep-warm-enabled` (section 2 of [saving-the-cache.md](saving-the-cache.md)), and the automatic save before a compaction needs `.claude/state/auto-precompact-enabled`.

A hook reminds you to run `/expert-review --code` after a commit only when the commit touches `src/` and the repository has an `origin/main` or `origin/dev` branch. Anywhere else, run it yourself after a commit you want reviewed.

The commands you will use most are large. Each run of `/summary`, `/meta`, `/expert-review` or `/wrap` loads the command's instruction file, between about 20 and 148 KB, plus the reference files it tells the model to read, and the work it does adds to that. In the source project's own sessions a run grew the context by about 44,000 tokens for `/summary` (the median of 15 runs) and by about 56,000 to 58,000 for `/meta`, `/expert-review` and `/wrap` (10, 4 and 2 to 3 runs). On a model with a 200,000-token window that is about a quarter of the window per run, so expect compactions sooner; `/pre-compact` and `/post-compact` save and rebuild the session's state around them.

## The first week

The session rhythm the skills encode is orient, work, summary, learn, wrap. Each line below paraphrases the skill's own `description:`.

- **`/orient`** gives a quick orientation at the start of a session: what is happening, what is pending, and where to start.
- **`/summary`** gives a mid-session readout of where the session has landed, what is blocked and what is in flight. It derives every number live and writes one file, the session's working plan.
- **`/working-plan`** brings the working plan up to date and shows it whole.
- **`/post-compact`** rebuilds hand-off state after the context has been compacted. It writes only the working plan and never acts on what it recovered.
- **`/deep-pass`** scans the transcript of a very long session in parallel. It runs when a compaction happened and the transcript is too large to scan inline.
- **`/meta learn`** extracts lessons at the end of a session; `/wrap` runs it for you. It scans the conversation for pushback, praise, verdict flips and deferrals, and proposes memory and skill changes. The rest of `/meta` covers the health of the whole expert and memory system: reviews, memory audits, pattern synthesis and a self-audit.
- **`/wrap`** is the end-of-session checklist: nothing left hanging, and every decision persisted.

Among the other skills in the copy (`/help` maps a task to its command):

- **`/expert-review`** consults several experts on one question, and with `--code` it runs the code-review panel.
- **`/agent-work`** runs one to five specialist agents on code in parallel.
- **`/audit-check`** verifies that an audit is complete before it is marked done.
- **`/sniff-test`** audits a draft before it is sent.
- **`/report`** builds one self-contained HTML page.
- **`/mail`** sends and reads hand-offs between sessions.
- **`/standby`** parks a session.
- **`/autorun`** schedules a work order to run later.
- **`/review-hub`** turns a session into the standing reviewer for its peers.

Some steps of `/orient`, `/summary` and `/wrap` call a script the copy does not ship: `scripts/migration-notation-reconcile.mjs`, `scripts/i18n-prose-drift.mjs` and `scripts/non-git-writes.py`. A step that calls one of them has nothing to run until you write it or remove the step.

**The review rule:** someone who did not write a change reviews it, meaning a fresh context briefed to find what is wrong. `/review-hub` and `/expert-review --code` carry this rule out. `CONTRIBUTING.md` says how it applies to changes to this copy.

**Migrations wait for that review.** `scripts/run-migration.mjs` applies a file to a database that is not on your machine only when the commit that last changed the file has an approving review on record: a committed `.claude/reviews/<full-commit-sha>.md` whose first line opens with an approving word (`APPROVED`, `APPROVE` or `FOLD-VERIFIED`) and nothing qualifying it, and whose `Reviewed-by:` line names who reviewed it. That is the record `/expert-review --code` leaves after reviewing a commit; its fresh helper agents are the reviewers, so it can run in the same session that wrote the migration. The check reads the record and cannot tell who really wrote it, so it stops a careless apply, not a deliberately false record. A file that deletes or rewrites rows, drops a table or column, or changes a column's type also needs your words, given with `--owner-destructive-yes`. If your project has no code review, set `MIGRATION_REVIEW_GATE=off` where the runner runs, for example in the settings' `env` block; the check on destructive files stays on.
