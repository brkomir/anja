# Anja's mechanisms beside Claude Code's own features

Anja grew between March and October 2026 inside one harness, Claude Code, while the maintainer built the source project, a photography critique application. Over the same months the harness shipped features that do some of the same jobs: some arrived after Anja had built its own, and some came first, with Anja built beside them or on top of them. This page goes through each such mechanism and says whether the native feature now does the job.

Anja does not claim primitives the harness lacks. Its hooks, skills, sub-agents, memory directory, path-scoped rules and timers are Claude Code's own, and the rows below say so. What Anja adds is an integrated engineering operating model on top of them: who delegates to whom, how several sessions share one branch in one checkout, how review is kept apart from authorship, how a session recovers after a compaction, which guards have earned the right to refuse, and how a correction becomes a lesson, a rule and then a guard. The table compares one mechanism with one feature at a time; the operating model is what the mechanisms add up to, and no single row captures it.

Each row has one of three statuses:

- **superseded**: the native feature does the job, and the mechanism can go.
- **overlapping**: both run, and each covers something the other does not.
- **complementary**: the mechanism is built on the native feature.

Sources: the copy's own files, and the Claude Code documentation pages named in each paragraph, read on 2026-10-10; the agent-teams and skill-validation rows rest on the pages "Orchestrate teams of Claude Code sessions" and "Extend Claude with skills", read on 2026-10-20. The documentation describes current versions, so a figure from a vendor page may change with a later release.

The verdict first: on what was read, **no mechanism in the copy is fully superseded**. Several now overlap a native feature, and a new project should start from the native feature and add the mechanism only for the gap named in its row. What no native feature covers, from the rows below: a mailbox that reaches a session that is not running, broadcasts and keeps a record; a check that two sessions sharing one working tree are not editing the same files; waiting on a commit or an explicit go signal; separating the session that wrote a change from the ones that review it, routing reviewers by domain and mailing verdicts across sessions; and doctrine that reaches the main session and, at launch, no sub-agent, which the copy delivers with its own `SessionStart` hook. A status records the choice a new project faces today, not which side came first; the notes give the order where it is known.

## Notes on each row

**Session mail.** The copy built its mailbox first: the mail skill's own comparison table gives its first commit as 2026-05-25, and the architecture document dates the deliver-and-surface engine to 2026-06-19. Claude Code's cross-session messaging arrived in the week of 3–7 August 2026 (the vendor's "What's new" page for that week). The copy already says the two are not redundant. The mail skill keeps a side-by-side table (mail survives the receiving session's death, supports a broadcast to every session, and leaves a stored, expiring record) and has the rule that anything which must outlive a session goes by mail. The vendor page "Message your other Claude Code sessions" confirms the native side's shape: plain text only, delivery to live sessions, at most 50 queued messages, a message from another session can never approve a permission prompt, and it says nothing about broadcast. One cell of the copy's table read too strongly until 2026-10-21: it said a native message leaves "none at all" as a record afterwards, where the vendor page says a one-line preview of each delivered message stays in the receiving conversation; the cell now says that. The two designs share one security idea: treat another session's text as data and never as an instruction. The copy wraps each message in an untrusted-data envelope; natively, the vendor page states one part of it: a message from another session can never approve a permission prompt.

**The mail listener.** The listener is built on the native `Monitor` tool, which arrived in the week of 6–10 April 2026. The architecture document dates the listener to 2026-06-21. The `Monitor` tool's own description, as read when this page was written, caps a watch at 30 minutes, which is why the mail skill re-arms the listener on every expiry. Native messages need no listener at all, so the listener survives only as long as the file mailbox does.

**Waiting on a peer.** `mail-await` runs as a background Bash command, which the harness re-invokes the session for when the command exits; that part is native behaviour the copy builds on. Its `--peer-done` mode overlaps the vendor's idle notice, documented on the same messaging page: one notice, sessions on this machine only, the main conversation only, dropped after 12 hours, and both sessions on version 2.1.236 or later. The `--on-commit` and `--signal` modes have no native equivalent in the pages read.

**Keep-warm.** The vendor page "How Claude Code uses prompt caching" says the main conversation gets a one-hour cache lifetime on a Claude subscription within its included usage and five minutes otherwise, that every cache hit resets the timer, and that `promptCacheTtl` chooses between five minutes and one hour. None of the pages read documents a keep-alive. The copy's orchestrator conventions describe a 15-minute timer for the one-hour cache. The keep-warm skill, its gate script and its tool-deny hook ship, and the settings file wires both hooks. `session-start.sh` directs a session to arm the timer only when the skill exists, both hooks are wired, and a switch file exists: `.claude/state/keep-warm-enabled` for every session, or `.claude/state/keep-warm-pilot-<the session id's first 8 characters>` for one. The copy ships no switch file, so keep-warm stays off until you create one.

**The timed one-shot run.** `/autorun` is a guarded prompt around the native `CronCreate` tool. One sentence in the copy's skill was stale until 2026-10-21. It said a scheduled job is "GONE if the session closes (nothing on disk)", but the vendor page "Run prompts on a schedule" says resuming a session restores its scheduled tasks, except recurring tasks past their seven-day expiry and one-shot tasks whose time has already passed; the skill now says that. The practical advice in the skill holds either way, because a one-shot that comes due while the session is closed is not restored: keep the session open until the job fires.

**Post-compact recovery.** The vendor page "Explore the context window" lists what survives compaction:

- the project-root `CLAUDE.md`, the unscoped rules and auto memory are re-injected from disk;
- up to five recently edited files are re-read;
- skill bodies are re-injected, capped at 5,000 tokens each and 25,000 in total;
- path-scoped rules and nested `CLAUDE.md` files load again only on demand;
- `SessionStart` hooks that match `compact` run, and their output is added.

The copy's `session-start.sh` uses exactly that last channel to direct `/post-compact`. Its header records that `PostCompact` hook output never reached the model; the hooks reference gives `PostCompact` no decision control and lists it for side effects such as logging. The skill adds what the native summary does not promise: the last exchanges, a hand-off state, a working plan, and a check of whether a mutating step already ran before it is repeated.

**Memory.** The architecture document calls the project memory directory "the auto-memory system Claude Code provides natively", relocated into the repository by a symlink. The vendor page "How Claude remembers your project" now documents `autoMemoryDirectory`, a setting that moves that directory. The value must be an absolute path (or one under the home directory), so a path that works for every clone of a repository still needs a symlink or a per-machine setting. The script that recreates the symlink, `scripts/setup-project-memory.sh`, ships with the copy. The same vendor page describes a native check after every `MEMORY.md` write, which overlaps the first of the budget gate's three arms. On per-expert memory: the 33 agent definitions in the copy point at their own memory file and forbid the agent to write it; none uses the native `memory` field. The vendor page "Create custom subagents" says that field injects the first 200 lines or 25 KB of the agent's `MEMORY.md` at startup and enables the agent's own writes. That is the opposite of the copy's rule, which exists because, by the agent files' own account, an agent writing its memory as a late tool call sometimes ended its run with a terse confirmation in place of its verdict.

**Path-scoped rules.** Of the nine rule files the copy ships, seven carry `paths:` frontmatter. The vendor's compaction table says a scoped rule loaded mid-session is summarized away by compaction and returns only when a matching file is touched again. The copy's own notes measured 4 of 7 compactions bringing a scoped file back and 3 leaving it out (the [evidence page](evidence.md)); the notes do not say whether those four had touched a matching file again.

**Hooks.** The copy's `settings.json` wires 112 hook commands on nine events (`InstructionsLoaded`, `PostToolUse`, `PreCompact`, `PreToolUse`, `SessionEnd`, `SessionStart`, `Stop`, `SubagentStart`, `UserPromptSubmit`). The copy ships 65 hook scripts at the top of `.claude/hooks/`; those 112 commands run 58 of them, and 2 more run because another hook calls them. The other 5 ship unwired: three switched off on purpose (the start page says when to wire each), and two the source project ran from its `pre-push` git hook, which the copy does not ship. The architecture document names nine events wired in the original system, against the 33 the vendor documents. The rule the copy relies on is confirmed by the hooks reference: `additionalContext` is wrapped in a system reminder and reaches the model on its next request. Whether a native permission deny rule (rules that match tool parameters arrived in the week of 15–19 June 2026) could replace any particular guard was not checked guard by guard.

**Review.** The review hub was founded in a session on 2026-06-25 (the review-hub skill). That was after the native `/code-review` command, which arrived in the week of 18–22 May 2026, and after ultrareview's research preview in the week of 20–24 April 2026. So it was built beside a native feature, not before one. The copy's code-review skill called the native review "project-blind" until 2026-10-21; it now says what the native review reads. That label held for neither the local command nor the managed review: the local command's vendor page, read on 2026-10-21, says the local `/code-review` follows `CLAUDE.md` (and does not read `REVIEW.md`), and the vendor page "Customize Code Review" says the managed pull-request review reads `CLAUDE.md` and `REVIEW.md`. The ultrareview page, read the same day, does not say whether that review reads either file. The vendor page "Find bugs with ultrareview" says each finding is independently reproduced and verified, which overlaps the hub's step of verifying findings at file and line. What the pages read do not describe is the hub's separation of the agent that wrote a change from the agents that review it, its routing of reviewers by expert domain, or verdicts mailed back across sessions.

**Worktree isolation.** The copy's `settings.json` sets `worktree.baseRef` to `head` and lists directories to symlink into each worktree; both are native settings ("All settings"). The copy's unit-test rules record that four of five agents dispatched with isolation ran without a worktree. The vendor's "What's new" page for 3–7 August 2026 says isolation was then extended to block Bash commands and git redirects that reach the main checkout, and the worktrees page now documents a cleanup sweep. The copy's measurement was not repeated against the current harness, so its "verify your own plane" rule stays, and it costs one command.

**Always-loaded rules.** The copy does not ship a `CLAUDE.md` or an `AGENTS.md`; its user supplies the project instruction file. It ships two unscoped rule files and the orchestrator doctrine files. The hooks that delivered that doctrine to the main session in the original system ship too, all of them wired; the settings' `env` block switches one of them off (the start page says which). The vendor page "Create custom subagents" says a sub-agent receives the whole instruction hierarchy, and offers `omitClaudeMd` to drop it for one agent definition. That is coarser than the copy's design, which keeps the shared rules in every agent and the orchestrator doctrine out at launch; a sub-agent's own compaction re-fires `SessionStart` inside it, and the doctrine arrives then.

## What could not be verified

- The dates when the sub-agent `memory` field, `autoMemoryDirectory`, `omitClaudeMd` and native `AGENTS.md` reading arrived. None appears in the "What's new" pages read, so whether each mechanism was built before or beside them is not stated.
- The arrival dates of five native features were not looked up, so their rows give no order: `SendMessage` with `notify_when_idle` (the `mail-await` row), the prompt-cache lifetime the keep-warm timer leans on, the native `MEMORY.md` size check (the memory budget gate row), agent teams, and the native skill checks (`claude plugin validate`, `claude plugin eval`, `/skill-doctor`).
- Whether the copy's worktree-isolation failure rate still holds on the current harness.
- The managed Code Review and ultrareview depend on the account plan and configuration, so they were not run here.
- Whether ultrareview reads `CLAUDE.md` or `REVIEW.md`. Its vendor page does not say.
- `CronCreate` and `CronList` were not available when this page was checked, and `ListAgents` was called once, on 2026-10-21, for the busy/idle marking noted in its row. Their behaviour is otherwise taken from the vendor pages and from the copy's skills, not from a call.
